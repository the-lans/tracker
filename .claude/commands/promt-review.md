Выступи в роли опытного ревьювера по бекенду Python и фронтенду. Найди все значимые ошибки в коде. Мелкие неточности без влияния на функционал не обсуждай. Пиши только по-настоящему важные замечания! Сверься также с правилами разработки. Если значительных ошибок нет — так и напиши. Выведи замечания нумерованным списком. Не останавливайся, пока не выявишь всё.
Категории ошибок для проверки:
 - **Логические ошибки** — неверные условия, off-by-one, инвертированная логика, мутируемые дефолтные аргументы
 - **Валидация и типы** — отсутствие проверок None/пустых значений, неявные приведения типов, доверие внешним данным без валидации
 - **Работа с БД** — SQL-инъекции, отсутствие транзакций, N+1 запросы, незакрытые сессии, отсутствие SELECT FOR UPDATE, .all() без LIMIT
 - **Аутентификация и авторизация** — IDOR, некорректная проверка JWT, небезопасное сравнение паролей, отсутствие проверки прав
 - **Интеграции** — отсутствие timeout/retry, игнорирование HTTP-статусов, незащищённая передача секретов
 - **Обработка исключений** — проглатывание ошибок, слишком широкий except, потеря traceback при re-raise
 - **Race conditions** — check-then-act без блокировки, общее состояние без Lock, неидемпотентные обработчики
 - **Граничные значения** — деление на 0, индексация без проверки длины, пустые итерируемые, naive vs aware datetime
 - **Состояние и сайд-эффекты** — мутация аргументов, глобальное изменяемое состояние, кэш без инвалидации
 - **Производительность** — N+1 без eager load, синхронные вызовы в async-контексте, отсутствие пула соединений
 - **Конфигурация** — захардкоженные секреты, отсутствие валидации env-переменных при старте
 - **Сериализация** — datetime без isoformat, потеря точности float для денег, возврат ORM-объекта без сериализации
 - **Платежи/биллинг — транзакционные границы и side-эффекты** (для любого платёжного, billing- или денежного/грантового сервиса, независимо от фреймворка и стека — Django, FastAPI+SQLAlchemy, что угодно):
   - Side-эффект (событие, таск очереди, вебхук, письмо и т.п.) отправляется сразу после выхода из локального транзакционного блока функции, а не после РЕАЛЬНОГО коммита — проверь, не может ли эта функция быть вызвана изнутри уже открытой транзакции вызывающего кода (не только напрямую саму по себе). Если может — эффект нужно откладывать до фактического коммита самой внешней транзакции (в Django — `transaction.on_commit(..., robust=True)`; в SQLAlchemy — хук сессии типа `after_commit`/событие `session.commit()`; в любом другом стеке — эквивалентный "выполнить после коммита" механизм, а не прямой вызов)
   - Валидация конфига/входных данных стоит ПЕРЕД проверкой идемпотентности ("уже применено" — флаг на записи, unique-ключ, дедуп-таблица) внутри одной операции — из-за этого повторная доставка/ретрай уже обработанной операции падает вместо тихого no-op, если конфиг успел стать невалидным между первым и повторным вызовом
   - Поиск записи для рефанда/реверса/отмены — по текущему значению МУТИРУЕМОГО конфига/настройки, а не по неизменяемым полям самой записи (тип, сохранённые в момент создания метаданные и т.п.) — при изменении конфига старые записи молча становятся недостижимы для отмены, часто вообще без строки в логе
   - Код читает/сохраняет поле сущности уже ПОСЛЕ вызова вложенной функции, которая сама независимо перечитывает и сохраняет ту же сущность (например, под своей блокировкой/новым запросом) — второй save/update в исходном (устаревшем) объекте затирает то, что записала вложенная функция
   - Ретрай/redelivery ПОСЛЕ ЧАСТИЧНОГО сбоя — операция успела частично примениться (например, начисление прошло, а следующий шаг в той же функции упал), после чего её ретраят или доставляют повторно: проверяй именно этот путь отдельно, а не только "два подряд успешных вызова одного и того же входа"
   - Одна и та же бизнес-логика (начисление, рефанд, роутинг покупки/платежа) продублирована в нескольких местах (несколько провайдеров платежей, несколько версий API, несколько каналов доставки) — исправление в одной ветке не гарантирует исправления в остальных, проверяй каждую отдельно
   - Идентичная или почти идентичная функция кредита/дебета баланса (или другой денежной операции) скопирована в соседний файл того же домена вместо переиспользования общего хелпера

Для каждого замечания выведи нумерованный блок строго в формате:

**№N. Проблема:** [что не так, где именно — файл/функция/строка]
**Категория:** [одна из категорий выше или своя]
**Риск:** [что может пойти не так на практике]

Не предлагай решение как "правильный код целиком" — только направление и суть исправления, достаточные для понимания подхода.
