# Развёртывание и обновление Tracker

Пошаговый сценарий для человека и LLM-агента (разделы 20.2, 20.4, 20.6–20.7 ТЗ).
Подходит для любого доменного имени, указывающего на ваш сервер. Основная
платформа — AlmaLinux/Rocky Linux; также предусмотрена Ubuntu/Debian.
Первая установка выполняется на сервере через `deploy/install.sh`, в том числе
агентом по SSH. GitHub Actions обновляет уже установленный сервер.

## Запуск через навык

Откройте репозиторий в локальном агенте и попросите, например:

- Codex: `$tracker-deploy Установи Tracker на tracker.example.org. Сервер — …, доступы в …`.
- Claude Code: `/tracker-deploy Установи Tracker на tracker.example.org. Сервер — …, доступы в …`.

Навыки находятся в `.agents/skills/tracker-deploy/SKILL.md` (Codex) и
`.claude/skills/tracker-deploy/SKILL.md` (Claude Code). Если агент не видит новый
навык, перезапустите сессию в репозитории либо явно попросите прочитать его файл.
Оба навыка используют этот документ как общий сценарий. Форматы расположения
навыков: [Codex](https://learn.chatgpt.com/docs/build-skills),
[Claude Code](https://code.claude.com/docs/en/skills).

## 1. Собрать параметры и определить режим

Сначала проверьте запрос, текущий контекст и указанный пользователем файл доступов.
Не просите повторно то, что уже известно. Недостающие параметры уточняйте по мере
необходимости; не просите пароли в публичном чате.

| Параметр | Как получить / значение по умолчанию |
|---|---|
| Режим | Новая установка, обновление, смена домена, только CI/CD или консультация |
| Домен | Полное имя без `https://`, порта и пути; для IDN использовать ASCII/punycode |
| SSH | IP/имя, реальный порт, пользователь, ключ или способ безопасного ввода пароля |
| Права | root или доступный sudo; проверить на сервере |
| ОС | Определить через `/etc/os-release`, не угадывать по хостеру |
| Каталог | `/opt/tracker`, если пользователь не выбрал другой `INSTALL_DIR` |
| Код | Источник репозитория, ветка `main` и целевой SHA; проверить, что нужные исправления слиты |
| Google OAuth | Web application Client ID и Secret для выбранного домена |
| Администратор | Google email первого администратора; уточнить, если адресов несколько |
| TLS email | Можно использовать email администратора, сообщив об этом |
| Параллелизм и swap | Согласованные значения пользователя или текущие настройки сервера |
| GitHub | Репозиторий и нужна ли настройка CI/CD сейчас; environment — `production` |
| Бэкапы | Встроенные локальные дампы; полный бэкап в S3 — настройка в UI, если пользователь дал хранилище и пароль шифрования |

Для агента: поручение развернуть приложение разрешает необходимые обычные действия
на указанном сервере. Работайте до результата, не запрашивая одобрение каждого
шага. Консультационный запрос не разрешает менять сервер. Не удаляйте чужие
контейнеры, данные или DNS-записи для освобождения ресурсов. При конфликте с
существующим приложением покажите конфликт и уточните целевую установку.

## 2. Проверить состояние до изменений

Подключитесь по SSH с проверкой ключа хоста. Для нового хоста сверяйте отпечаток
через консоль провайдера или другой доверенный канал; `ssh-keyscan` сам по себе
не подтверждает подлинность. Секреты читайте программно из указанного файла
или через защищённый ввод. Не выводите файл доступов, `.env`, `docker inspect`
с окружением, `docker compose config` целиком или команды с паролями в лог.
Не передавайте секреты в аргументах shell, URL и Git. Если пользователь просит
сохранить новые секреты, дополните указанный файл с правами `600`, не затирая
старые значения, и проверьте, что он не попадёт в коммит.

Соберите состояние:

```bash
cat /etc/os-release
id
free -h
swapon --show
df -h /
ss -lntup
command -v docker
# Если Docker уже есть:
docker version
docker compose version
docker ps --format '{{.Names}} {{.Status}} {{.Ports}}'
```

Проверьте файрвол и облачные сетевые правила. В существующем каталоге Tracker
посмотрите статус Git, origin, SHA, наличие `.env` и локальных Compose overrides.
Не выполняйте `git reset --hard`, не заменяйте `.env` и не меняйте ключи шифрования.

- Есть работающий Tracker: используйте маршрут обновления, а не новую установку.
- Есть незавершённая установка: найдите последний успешный этап и причину сбоя.
  Сохраните `.env` и данные, повторите только нужные этапы после исправления.
  Если `.env` существует, установщик пропускает генерацию секретов: пустые значения
  нужно заполнить, сохранив уже заданные; одного повторного запуска недостаточно.
- Сервер пуст: продолжайте первичную установку.

Образы собираются на сервере, включая Go-прокси и frontend. Проверьте место
с учётом образов, build cache, swap, репозиториев задач и бэкапов. Результаты
локальных замеров — [docs/benchmarks/2026-11-02/report.md](benchmarks/2026-11-02/report.md):
это ориентир для небольшой нагрузки, а не гарантия для любых сборок и агентов.
`docker-compose.prod.yml` установщик автоматически не применяет.

## 3. Проверить DNS

Проверяйте фактическую авторитетную зону, а не только панель регистратора:

```bash
# Выполнять на машине, где доступен dig; DOMAIN — выбранное полное имя.
dig "$DOMAIN" A +noall +answer +authority
dig "$DOMAIN" AAAA +noall +answer +authority
dig "$DOMAIN" NS +noall +answer +authority
dig "$DOMAIN" CAA +noall +answer
```

Найдите делегирование родительской зоны через NS/SOA, при необходимости `dig +trace`.
Сравните ответы авторитетных серверов и публичных резолверов. A должна вести
на IPv4 сервера; если AAAA есть, IPv6 тоже должен работать на этом сервере.
При CNAME проверьте всю цепочку. Учитывайте CAA имени и родительских доменов.

Если регистратор, DNS-провайдер и хостер разные, запись в неавторитетной панели
не действует. Предпочитайте добавить A/AAAA в уже действующую зону. Для отдельного
поддомена NS-делегирование нужно создать в родительской зоне; настройка зоны у
хостера сама этого не делает. Не переносите NS всего домена ради одного поддомена
без такого выбора пользователя: это затронет другие сайты и почту.

Если нет доступа к DNS-панели, сообщите пользователю точные поля: панель активного
DNS-провайдера → нужная зона → тип A, имя поддомена, IP сервера. После сохранения
проверьте DNS сами. При NXDOMAIN покажите, какой сервер отвечает и какую запись
нужно исправить; не выдавайте любое расхождение за «подождать сутки».

## 4. Подготовить Linux, файрвол и swap

### Пакеты и Docker

`install.sh` устанавливает недостающие git, curl, OpenSSL и CA-сертификаты через
apt или dnf; Docker — через RPM-репозиторий для AlmaLinux/Rocky Linux и
`get.docker.com` для распознаваемых им дистрибутивов, включая Ubuntu/Debian.
Требуется Docker Engine 26+ с Compose plugin. Не переустанавливайте работающий
Docker и не меняйте SELinux/AppArmor для обхода ошибки без диагностики.

Если сервер минимальный и curl отсутствует, сначала установите его через пакетный
менеджер, чтобы скачать установщик. После установки проверьте запуск Docker
и автозапуск службы; на systemd используется `systemctl enable --now docker`.

### Файрвол

Сохраните реальный SSH-порт до включения файрвола. При изменении удалённого
доступа оставьте текущую сессию, предусмотрите временный возврат предыдущих
правил и проверьте второе SSH-подключение до отмены возврата. Не делайте flush
существующих правил и не включайте второй менеджер файрвола параллельно первому.

- AlmaLinux/Rocky Linux: используйте установленный firewalld; если его нет,
  установите пакет `firewalld` через dnf. Выберите активную зону внешнего интерфейса.
  До запуска firewalld разрешите SSH-порт в постоянной конфигурации; затем
  запустите службу, проверьте SSH и примените остальные правила через `firewall-cmd`.
- Ubuntu/Debian: сохраните имеющийся менеджер. Если файрвола ещё нет, можно
  установить UFW через apt, разрешить SSH-порт и только затем выполнить `ufw enable`.
  На сервере с существующими nftables/iptables адаптируйте текущие правила.

Разрешите SSH на фактическом порту, HTTP 80/TCP, HTTPS 443/TCP и SFTP
`${SFTP_PORT:-2222}/TCP`, если он нужен. 443/UDP нужен только при публикации QUIC,
которую базовый Compose не включает. Те же порты проверьте в панели провайдера.
Если SFTP не нужен, отключите его публикацию через локальный override:
одного закрытия порта в хостовом файрволе для Docker недостаточно.

Docker может публиковать порты в обход обычных правил хостового файрвола.
В актуальном Compose backend привязан к `127.0.0.1:8000`, PostgreSQL, Redis и
LLM-прокси наружу не публикуются. Проверяйте итоговые публикации после запуска.
Для старого checkout сначала исправьте публикацию 8000 локальным override или
обновите код; не полагайтесь только на закрытие порта в UFW/firewalld.

### Swap и параллелизм

Проверьте существующий swap, свободное место и тип файловой системы. Не заменяйте
работающий swap вслепую: для расширения часто проще добавить отдельный swap-файл.
Для обычной ext4/XFS без ограничений swap-файлов можно создать файл через
`fallocate` (или `dd`, если необходим), выставить `600`, выполнить `mkswap`,
`swapon` и добавить единственную запись в `/etc/fstab`. На Btrfs используйте
поддерживаемую файловой системой процедуру. Проверьте `swapon --show` и fstab.
Размер выбирайте по ресурсам и запросу пользователя; swap не заменяет RAM.

Для небольшого сервера задайте `SESSION_WORKER_CONCURRENCY` в `.env` по нужному
числу одновременных задач. Обычный worker по умолчанию создаёт процессы по числу
CPU; если нужен один процесс, используйте локальный `docker-compose.override.yml`:

```yaml
services:
  worker:
    command: ["celery", "-A", "tasks.celery_app", "worker", "-Q", "celery", "--concurrency", "1", "-l", "info"]
```

Сохраняйте существующие override-настройки; файл не нужно перезаписывать целиком.

## 5. Подготовить Google OAuth

Единственный способ входа — Google. Создайте клиента типа **Web application**
в [Google Cloud Console](https://console.cloud.google.com/apis/credentials).
В **Authorized JavaScript origins** добавьте ровно `https://` и выбранный домен
([официальная инструкция Google](https://developers.google.com/identity/gsi/web/guides/get-google-api-clientid)).
Tracker принимает Google ID token; специальный redirect URI приложения не нужен.

Если это ручной шаг, проведите пользователя последовательно: выбрать Google Cloud
project → настроить OAuth consent screen/audience → при режиме Testing добавить
нужные test users → создать Web client → добавить origin → сохранить Client ID
и Secret в согласованном защищённом файле. Не просите пароль Google-аккаунта.
После каждого блока уточняйте только недостающий результат, а не весь список заново.
Email администратора — адрес аккаунта, с которым пользователь будет входить.

## 6. Выполнить первую установку

Команды ниже выполняются **на целевом сервере**, от root или через sudo.
Проверьте содержимое скачанного скрипта и источник перед запуском.

```bash
curl -fsSL https://raw.githubusercontent.com/the-lans/tracker/main/deploy/install.sh -o install.sh
sudo bash install.sh
```

Для другого каталога передайте `INSTALL_DIR` в окружение процесса установщика,
например `sudo env INSTALL_DIR=/srv/tracker bash install.sh`.
Скрипт клонирует `the-lans/tracker` в `main`; это не параметр выбора произвольного
fork. Если пользователь использует fork, сначала проверьте/подготовьте правильный
checkout в целевом каталоге: установщик не клонирует заново существующий `.git`.
Он также не обновляет автоматически заранее клонированный checkout при первой
установке — проверьте origin и SHA самостоятельно.

Установщик запрашивает по порядку:

1. Домен без схемы и пути.
2. Email для TLS.
3. Google Client ID.
4. Google Client Secret (ввод скрыт).
5. Email первого администратора.

Агент может заполнить ответы сам через защищённый stdin или PTY; пользователь
вводит только отсутствующие данные. Передавайте секреты из файла/хранилища
программно, без shell-интерполяции и без логирования stdin. При передаче через
PTY отключите echo на время передачи секрета. Если используете временный файл
ответов, создайте его с `600` вне Git и удалите после использования.
Не запускайте сборку отдельно до записи OAuth Client ID: значение встраивается
в frontend при чтении конфигурации Compose перед сборкой.

Скрипт генерирует `.env` с правами `600`, проверяет обязательные значения,
собирает все сервисы, script-раннеры и `tracker-session`, запускает PostgreSQL/Redis,
применяет миграции, заполняет allowlist администратора и фоновые расписания,
запускает приложение. `.env` — состояние сервера, не шаблон для перезаписи.

Сборку лучше запускать с защищённым логом и возможностью переподключения
(`tmux` либо фоновый процесс с сохранением exit code). Проверяйте прогресс,
а не только наличие процесса. Успех установщика не доказывает работоспособность
всего стека: выполните следующий раздел.

## 7. Проверить результат

На сервере перейдите в каталог установки и проверьте:

```bash
docker compose ps
docker compose exec -T worker celery -A tasks.celery_app inspect ping --timeout=5
```

Должны ответить **два разных узла**: worker и session-worker. Сопоставьте имена
узлов с контейнерами; наличие одного `pong` недостаточно. Проверьте, что оба
воркера и beat остаются запущенными без цикла рестартов; backend, PostgreSQL,
Redis, cliproxy, llm-gateway и SFTP (если используется) проходят healthcheck.
`cliproxy-init` штатно завершается с кодом 0. При ошибке смотрите ограниченный
фрагмент лога проблемного сервиса с маскированием секретов.

С внешней машины выполните проверку из CI, передав реальный SHA установленного кода:

```bash
DEPLOY_DOMAIN="$DOMAIN" bash .github/scripts/verify_deployment.sh "$DEPLOYED_SHA"
```

Она проверяет доверенный HTTPS, SHA в `/api/health` и HTML фронтенда. Дополнительно
проверьте загрузку JS/CSS и HTTP → HTTPS, сертификат для выбранного имени,
публикации портов и отсутствие внешнего доступа к 8000, 5432, 6379, 8317, 8320.
Сверьте OAuth Client ID из `.env` с собранным frontend, не выводя секреты.
Если в checkout есть локальные правки, явно сообщите: SHA в health их не отражает.

Попросите пользователя открыть сайт и войти под выбранным Google email. Скрипт
добавляет email в allowlist; первый вошедший пользователь получает роль admin.
Подключение Claude/Codex выполняется в UI «LLM-аккаунты» → добавить → «Войти».
Не подменяйте проверку OAuth выдачей себе токена приложения и не запускайте
платные API или тестовые задачи без соответствующего поручения.

Проверьте встроенный бэкап:

```bash
docker compose exec -T backup /usr/local/bin/backup.sh
docker compose exec -T backup sh -c 'for f in /backups/*.sql.gz; do gzip -t "$f" || exit; done'
```

Это локальный дамп PostgreSQL, не проверка восстановления и не S3-бэкап.
Для восстановления требуются также `.env` и volumes приложения; см.
[docs/migration.md](migration.md).

Полный бэкап в S3 настраивает администратор в UI: «Администрирование» →
«Системные настройки» → «Резервное копирование в S3» (endpoint, регион, бакет,
ключи, папка, число хранимых копий, пароль шифрования). Пароль шифрования
пользователь задаёт и хранит сам — не придумывайте его за него и не
сохраняйте у себя. После сохранения: «Проверить подключение», затем на вкладке
«Периодические задачи» — «Запустить сейчас» у «Резервное копирование в S3» и
«Проверка восстановления из S3»; оба запуска должны закончиться «Успешно», в
папке бакета — копия, `restore.sh` и `RESTORE.md`. Не считайте бэкап
настроенным без такой проверки.

Сервис `backup-worker` читает `.env` сервера из каталога `TRACKER_ENV_DIR`
(по умолчанию — каталог установки, где лежит `docker-compose.yml`). Задавайте
переменную, только если `.env` хранится в другом каталоге.

## 8. Настроить GitHub Actions

Этот этап выполняйте, если пользователь поручил настройку CI/CD. Если он просит
только подготовить значения для ручного внесения, подготовьте их и покажите
точное место в GitHub, не меняя настройки репозитория за него.

### Пользователь и ключ развёртывания

На сервере один раз создайте пользователя (или используйте уже подготовленного):

```bash
id deploy >/dev/null 2>&1 || useradd --create-home --shell /bin/bash deploy
usermod -aG docker deploy
chown -R deploy:deploy "$INSTALL_DIR"
install -d -m 700 -o deploy -g deploy /home/deploy/.ssh
```

Группа docker даёт права уровня root на хосте. Не меняйте владельца чужого
каталога: `INSTALL_DIR` должен указывать на проверенный checkout Tracker.
Не заменяйте работающий deploy-ключ без необходимости. Новый ключ создайте
на доверенной машине вне репозитория с `umask 077`:

```bash
ssh-keygen -t ed25519 -N "" -C tracker-deploy -f "$DEPLOY_KEY_FILE"
```

Открытый ключ добавьте одной строкой в `/home/deploy/.ssh/authorized_keys`,
сохранив существующие строки. Замените `/opt/tracker` реальным `INSTALL_DIR`:

```text
command="/opt/tracker/deploy/ci_deploy.sh",no-port-forwarding,no-agent-forwarding,no-X11-forwarding,no-pty ssh-ed25519 AAAA… tracker-deploy
```

Выставьте владельца `deploy:deploy`, права `600` у authorized_keys. Проверьте
новое SSH-подключение с этим ключом и командой `previous-ref`.
Ответ «обновлений ещё не было» с кодом 1 до первого обновления — ожидаем;
`Permission denied`, таймаут и ошибка проверки хоста — не успех.

### Проверенный known_hosts

Соберите ключ хоста для фактических SSH-адреса и порта:

```bash
ssh-keyscan -t ed25519 -p "$SSH_PORT" "$SSH_HOST" > "$KNOWN_HOSTS_FILE"
ssh-keygen -lf "$KNOWN_HOSTS_FILE"
```

Сравните с `ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub` через уже доверенную
сессию или консоль провайдера. При нестандартном порте строка known_hosts должна
использовать форму `[host]:port`. Не отключайте StrictHostKeyChecking.

### Environment production

Откройте **репозиторий → Settings → Environments → production** (создайте, если нет).
Workflow использует именно это environment. Названия ниже фиксированы,
значения домена и SSH-адреса выбираются для текущего развёртывания.

| Имя | Где | Значение |
|---|---|---|
| `DEPLOY_HOST` | Environment variables | Проверенный IP или имя для SSH |
| `DEPLOY_PORT` | Environment variables | SSH-порт, по умолчанию `22` |
| `DEPLOY_USER` | Environment variables | `deploy` или выбранный пользователь |
| `DEPLOY_DOMAIN` | Environment variables | Домен из `.env`, без `https://` и пути |
| `DEPLOY_WAIT_IDLE_MINUTES` | Environment variables | Ожидание живых сессий; по умолчанию `60`, допустимо 1–1440 |
| `DEPLOY_ENABLED` | Environment variables | `true`, включить последним после подготовки |
| `DEPLOY_SSH_PRIVATE_KEY` | Environment secrets | Весь закрытый ключ, включая строки BEGIN/END |
| `DEPLOY_SSH_KNOWN_HOSTS` | Environment secrets | Проверенная строка known_hosts для DEPLOY_HOST/PORT |

При новой настройке оставьте `DEPLOY_ENABLED=false`, пока не проверены сервер,
SSH и целевой SHA в `main`. Уже работающую конфигурацию сначала изучите:
не перенаправляйте существующее `production` на другой сервер без такого поручения.
Один `production` в текущем workflow обслуживает один целевой сервер/домен.
Для независимых параллельных установок потребуется адаптировать workflow.

Если разрешено настроить GitHub автоматически и доступен авторизованный `gh`,
проверьте аккаунт и целевой репозиторий. Пример передачи значений (environment
предварительно должен существовать):

```bash
gh variable set DEPLOY_HOST --repo "$GH_REPO" --env production --body "$SSH_HOST"
gh variable set DEPLOY_DOMAIN --repo "$GH_REPO" --env production --body "$DOMAIN"
gh secret set DEPLOY_SSH_PRIVATE_KEY --repo "$GH_REPO" --env production < "$DEPLOY_KEY_FILE"
gh secret set DEPLOY_SSH_KNOWN_HOSTS --repo "$GH_REPO" --env production < "$KNOWN_HOSTS_FILE"
```

Остальные переменные задаются аналогично таблице. Проверяйте имена секретов,
не пытайтесь читать их значения из GitHub. Секреты приложения из `.env` в Actions
не нужны: они остаются на сервере. Временную копию deploy-ключа удаляйте только
после передачи в GitHub или сохранения в согласованном пользователем хранилище
и после проверки SSH. Сохранённые самим пользователем ключи не удаляйте.

По выбору пользователя настройте Required reviewers и Deployment branches только
`main`; защита ветки с обязательным CI задаётся отдельно. Не добавляйте новые
обязательные ручные подтверждения, если пользователь просит автоматический деплой.

### Проверить Actions

Включите `DEPLOY_ENABLED=true`. Запустите **Actions → Deploy → Run workflow → main**
либо, при разрешённом автоматическом запуске:

```bash
gh workflow run deploy.yml --repo "$GH_REPO" --ref main
```

Дождитесь результата задания и повторите проверки раздела 7.
Если запуск/изменение GitHub недоступны агенту, дайте пользователю ровно эти поля
и действия, затем проверьте результат доступными средствами.

## 9. Как работают обновление и откат

Успешный CI на **push в main** запускает Deploy. Он подключается по ограниченному
SSH-ключу, отправляет `deploy <sha> --wait-idle <минуты>` и вызывает
`install.sh --update --ref <sha>`. Коммит должен входить в историю `origin/main`.
Обновление блокирует новые задачи, ждёт завершения живых сессий, включая активные
чаты в «Уточняется» (`chat_active=true`), пересобирает все образы, снимает дамп БД,
применяет миграции и перезапускает сервисы.
CI отдельно проверяет production-образ backend без dev-зависимостей, frontend
и остальные проверки проекта.

При обновлении работайте от пользователя, которому принадлежит каталог:

```bash
cd "$INSTALL_DIR"
deploy/install.sh --update --wait-idle 60
# Конкретный коммит из origin/main:
deploy/install.sh --update --ref "$TARGET_SHA" --wait-idle 60
```

Не меняйте локальные overrides и ключи `.env`, если это не требуется запросом.
При конфликте checkout с локальными правками разберите diff; не затирайте их.
Код 3 — обновление отменено до перехода на новый код; откат не нужен. Другой
ненулевой код требует диагностики по последнему успешному этапу. Не повторяйте
бесконечно ту же команду: устраните подтверждённую причину или запросите конкретный
недостающий доступ/решение.

Workflow ждёт до пяти минут SHA и HTML фронтенда. При неудаче после начала
изменений он пытается вернуть код и образы на `.deploy/previous_ref`.
**Схема БД при этом остаётся новой.** Это не полное восстановление из бэкапа;
несовместимые миграции требуют отдельного плана восстановления.
Ручной откат после оценки совместимости и необходимости остановки задач:

```bash
deploy/install.sh --update --ref "$(cat .deploy/previous_ref)" --wait-idle 60
```

Флаг `force` в Actions и `--force` у SSH-команды снимают ожидание живых сессий.
У самого `install.sh` флага `--force` нет: пропуск `--wait-idle` означает отсутствие
ожидания. Не прерывайте задачи принудительно без такого поручения пользователя.

## 10. Смена домена и завершение работы агента

Для смены домена сохраните данные, `.env` и ключи. Подготовьте DNS нового имени,
добавьте новый Google origin и измените только связанные настройки (`DOMAIN`,
при необходимости контакты TLS/OAuth и `DEPLOY_DOMAIN`). Пересоздайте сервисы,
использующие изменённое окружение; при смене OAuth Client ID пересоберите frontend.
Проверьте новый HTTPS и вход. Старый origin/DNS удаляйте только по поручению.
Не запускайте первичную установку поверх работающего сервера ради смены домена.

При ручном шаге агент сообщает конкретное место в панели, поля и ожидаемый
результат, ждёт нужный ответ и после него самостоятельно проверяет изменение.
Пока ждёт DNS/OAuth/доступы, выполняет независимую подготовку. Недостающий ответ
не заменяется предположением или таймаутом.

Итог: URL, email администратора, SHA и локальные отличия, статус HTTPS/UI/воркеров/
бэкапов, открытые порты, состояние автоматического деплоя и оставшиеся действия.
Не включайте секреты в отчёт. Отдельно отмечайте, если вход пользователя,
реальное выполнение LLM-задач, S3 или восстановление не проверялись.

## Учётные данные Git для рабочих репозиториев

После обновления откройте «Администрирование → Учётные данные Git». Для GitLab
Personal Access Token создайте HTTPS-доступ с именем хоста, логином `oauth2` и
токеном. Выберите запись в нужных репозиториях с HTTPS URL. Токен не требуется
добавлять в `.env`, переменные задач или GitHub Actions. API и UI репозитория
больше не принимают старое поле `deploy_key`; используйте `git_credential_id`.
Миграция рассчитана на новую установку и удаляет прежнее поле SSH-ключа без
переноса значений. Сохранение старых данных и совместимость старой версии не предусмотрены.
При откате схемы учётные данные Git удаляются, прежнее поле восстанавливается
пустым. Автоматический откат только кода к версии со старым полем несовместим
с этой схемой; перед обновлением сохраните резервную копию.

## Обновление с командами библиотеки

Обновление применяет миграции `d7a41e9b5206` (имена команд и зашифрованные снимки
вызовов) и `e6b8c20d1749` (`tasks.manual_requests_closed`). Существующие промты
получают пустое имя команды и версию 1, задачи — открытый приём ручных запросов.
Дополнительные переменные окружения, файлы команд или настройка LLM-аккаунтов не
нужны. Снимки используют действующий `SECRET_ENCRYPTION_KEY`; его следует сохранять
при переносе и восстановлении сервера вместе с обычной конфигурацией Tracker.

Используйте штатное обновление после завершения активных сессий: backend и воркеры
должны работать с одной версией схемы. Обновлять схему под продолжающими работу
старыми воркерами нельзя. Проверка после обновления: назначьте текстовому промту
или скрипту имя команды, вызовите её из активной задачи с аргументами, проверьте
результат и номер версии в диалоге, отмену ожидающего и остановку выполняющегося
вызова. Перед финальным пушем UI показывает закрытие приёма новых запросов.

При откате миграции команд ожидающие вызовы отменяются, чтобы прежняя версия кода
не выполнила изменённый текст вместо сохранённого снимка. Откат выполняется после
завершения активных сессий, с резервной копией по общей процедуре выше.
