# Ручное E2E-тестирование трекера

Сценарии ручной проверки пользовательского пути в браузере: от создания задачи
до проверки кода в рабочей ветке. На каждом шаге сверяются четыре источника:
интерфейс, статусы задачи, логи (structlog, `node_logs`, `app_logs`) и итог в
Git. Требования, на которые ссылаются кейсы, — `docs/technical_specification.md`.

Кейсы разбиты по приоритету:

| Приоритет | Что входит | Когда проходить |
|---|---|---|
| P0 | Основной путь: задача с разнородными нодами от создания до проверки кода | Каждый прогон перед релизом |
| P1 | Частые ветвления: сбой и перезапуск, пауза, ручные запросы, вопросы агента | Перед релизом, если менялась соответствующая часть |
| P2 | Редкие и сервисные сценарии | По необходимости |

Вне документа: нагрузка, безопасность (её проверяют ревью и pytest), миграции
(`alembic upgrade/downgrade`), установка `deploy/install.sh`.

## 1. Подготовка стенда

### 1.1 Стек трекера

Настройки стенда — `scripts/qa/qa.env` (в `.gitignore`), шаблон с описанием
каждого значения — `scripts/qa/qa.env.example`. Вручную задаётся только
OAuth-клиент Google (Web application, в Authorized JavaScript origins —
`https://localhost`, e-mail администратора — в тестовых пользователях).
Остальные секреты `.env` (ключ шифрования, пароли, VAPID-ключи Web Push)
`stand.sh env` генерирует сам. Стек стенда — отдельный compose-проект
`tracker-qa` (`COMPOSE_PROJECT_NAME` в `.env`): его volume и сеть не
пересекаются с другим стеком трекера на машине.

1. Создать настройки и `.env` трекера (`DOMAIN=localhost`); Client ID Google
   встраивается в сборку фронтенда из `GOOGLE_OAUTH_CLIENT_ID`:
   ```bash
   cp scripts/qa/qa.env.example scripts/qa/qa.env   # вписать GOOGLE_OAUTH_* и QA_ADMIN_EMAIL
   scripts/qa/stand.sh env
   ```
   Повторный запуск безопасен: он переносит в `.env` новые значения из
   `qa.env`, а сгенерированные секреты не меняет — ими уже зашифрованы данные
   в volume.
2. Собрать образы раннеров и сессии, поднять стек и заполнить начальные
   данные — первого администратора и периодические задачи (CLAUDE.md, раздел 4):
   ```bash
   docker build -t tracker-runner-python:latest runners/tracker-runner-python/
   docker build -t tracker-runner-bash:latest runners/tracker-runner-bash/
   docker build -t tracker-session:latest runners/tracker-session/
   docker compose up -d --build
   scripts/qa/stand.sh seed
   ```
   После правки `GOOGLE_OAUTH_*` — `scripts/qa/stand.sh env && docker compose
   up -d --build`: без пересборки фронтенд не знает Client ID.
3. Доверить браузеру локальный сертификат Caddy — без этого service worker не
   регистрируется и Web Push не работает:
   ```bash
   scripts/qa/stand.sh trust     # печатает команду добавления в системное хранилище
   ```
   После добавления сертификата перезапустить браузер.
4. Поднять git-хост и мок (раздел 1.2) и заполнить справочники (раздел 1.3):
   ```bash
   scripts/qa/stand.sh up
   scripts/qa/stand.sh data
   ```
5. Войти в Claude в каталоге LLM-аккаунта «QA» (`QA_CLAUDE_ACCOUNT_DIR`):
   ```bash
   docker compose exec -e CLAUDE_CONFIG_DIR=/data/claude-accounts/qa worker claude auth login
   docker compose exec -e CLAUDE_CONFIG_DIR=/data/claude-accounts/qa worker claude auth status
   ```
6. Открыть `https://localhost`, войти через Google e-mail'ом из
   `QA_ADMIN_EMAIL` и разрешить уведомления на запрос браузера.

### 1.2 Git-хост и моки внешних сервисов

Тесты используют локальный git-хост по SSH и мок Jira/GitLab API — настоящие
сервисы не нужны. `scripts/qa/stand.sh up` подключает оба контейнера к сети
compose (`QA_NETWORK`, порт мока на хосте — `QA_MOCKS_PORT`).

| Что | Значение |
|---|---|
| Адрес репозитория | `ssh://git@qa-git/srv/git/qa/qa-calc.git`, базовая ветка `main` |
| Deploy key | `.qa/deploy_key` (приватный ключ) |
| Jira URL | `http://qa-mocks:8090` |
| GitLab URL и токен | `http://qa-mocks:8090`, токен `qa-token` (мок принимает любой) |

Репозиторий `qa-calc` (заготовка — `scripts/qa/seed/qa-calc`): `calc.py` с
`add`/`subtract`/`multiply`, тесты на `unittest` (`python3 -m unittest -v`),
README с формулировкой задачи — добавить `divide`.

Мок отвечает только на то, что вызывает трекер:

- Jira: задача `QA-2` с вложением `requirements.md`; любой другой ключ — 404;
- GitLab: состояние MR по ветке. По умолчанию MR нет; слить ветку в `main` и
  отметить MR как `merged` — `scripts/qa/stand.sh merge feature/<код>`;
- журнал обращений трекера: `curl -s http://localhost:8090/_qa/requests`.

Проверка кода из рабочей ветки на хосте:

```bash
scripts/qa/stand.sh export
git clone -b feature/RR-QA-1 .qa/qa-calc.git .qa/check && (cd .qa/check && python3 -m unittest -v)
```

После тестирования — `scripts/qa/stand.sh down` (удаляет git-хост, мок и
каталог `.qa/`) и `docker compose down -v` (стек трекера вместе с данными).

### 1.3 Справочники

`scripts/qa/stand.sh data` (`scripts/qa/seed_qa_data.py`) заводит всё, что
нужно кейсам; повторный запуск добавляет только недостающее. Записи
принадлежат администратору из `QA_ADMIN_EMAIL`: вход через Google находит его
по e-mail.

| Раздел | Запись | Зачем |
|---|---|---|
| LLM-аккаунты | «QA», каталог `QA_CLAUDE_ACCOUNT_DIR` | Сессия задачи |
| Репозитории | `qa-calc` — адрес и deploy key из раздела 1.2 | Клон, ветка задачи, push |
| Системные настройки | Jira URL, GitLab URL и токен — мок | E2E-18, E2E-23, E2E-29 |
| Переменные окружения | `QA_GREETING` = `Привет из QA` (глобальная) | Рендер `{{env.*}}` |
| Переменные окружения | `QA_TOKEN` = `qa-secret-123`, секрет | Маскирование в предпросмотре и логах |
| Библиотека промтов | «Ревью изменений» — `plain_prompt`: «Сделай ревью изменений в ветке {{task.code}}: перечисли риски и пропущенные тесты» | Ручной запуск из библиотеки |
| Библиотека промтов | «Статус репозитория» — `slash_command`: `/status` | Слэш-команда из библиотеки |
| Пайплайны | «QA: фича с тестами» (раздел 2) | Кейсы P0 и P1 |

### 1.4 Наблюдение во время прогона

Держать открытыми три окна:

1. **Браузер** — страница задачи: вкладки «Обзор», «Диалог», «Логи».
2. **Терминал с логами** backend-сервисов (JSON structlog):
   ```bash
   docker compose logs -f --no-log-prefix backend worker session-worker | grep '<task_id>'
   ```
   `task_id` — из адреса страницы задачи; его несут все события обработки
   задачи, включая клонирование, сессию и скрипт-ноды. Ожидаемые события по
   шагам указаны в кейсах.
3. **Админка → «Мониторинг»** — `app_logs` (фильтр по задаче) и активные
   Celery-задачи.

Запросы к БД для сверки (выполнять как есть, только чтение):

```bash
docker compose exec postgres sh -c 'psql -U "$POSTGRES_USER" -d "$POSTGRES_DB"'
```
```sql
-- История нод задачи в порядке выполнения
SELECT n.name, l.trigger_type, l.attempt_number, l.status, l.started_at, l.finished_at
FROM node_logs l JOIN nodes n ON n.id = l.node_id
WHERE l.task_id = '<task_id>' ORDER BY l.started_at;

-- Статус задачи и точка перезапуска
SELECT status, last_failed_order_index, reset_at, session_id FROM tasks WHERE id = '<task_id>';

-- Снимок нод задачи
SELECT tn.order_index, n.name, n.node_type, n.task_id IS NOT NULL AS custom, tn.is_enabled, tn.pause_after
FROM task_nodes tn JOIN nodes n ON n.id = tn.node_id
WHERE tn.task_id = '<task_id>' ORDER BY tn.order_index;
```

### 1.5 Фиксация результата

Для каждого шага: **ожидаемое → фактическое → доказательство** (скриншот,
строка лога, результат запроса). Отклонение — дефект по шаблону раздела 6.

## 2. Эталонный пайплайн «QA: фича с тестами»

Создаётся `scripts/qa/stand.sh data` (тексты скриптов — `scripts/qa/pipeline/`)
и используется в кейсах P0 и P1. В нём все
пять типов нод, и вывод каждой ноды передаётся в следующую.

| # | Название | Тип | Содержимое |
|---|---|---|---|
| 0 | Сбор контекста | Скрипт, bash | скрипт 0 ниже |
| 1 | План | Режим планирования | «Спланируй добавление в `calc.py` функции `divide(left, right)`: при делении на ноль — `ZeroDivisionError` с понятным сообщением; нужны тесты в `test_calc.py`. Контекст репозитория: {{node.script_output}}» |
| 2 | Реализация | Обычный промт | «Реализуй задачу {{task.code}} по утверждённому плану: {{node.plan_text}}. В README добавь строку: {{env.QA_GREETING}}. Запусти `python3 -m unittest -v`, затем закоммить изменения в текущую ветку: `git -c user.name="QA Agent" -c user.email=qa-agent@example.com commit -am "feat: add divide"`.» |
| 3 | Тесты | Скрипт, python | скрипт 3 ниже |
| 4 | Очистка контекста | Очистить контекст | — |
| 5 | Итог | Обычный промт | «Кратко перечисли, что изменено в ветке задачи {{task.code}}, по выводу тестов: {{node.script_output}}» |

Трекер сам не коммитит: push отправляет то, что закоммитил агент, поэтому
промт «Реализация» явно просит коммит. Автор коммита задан в самой команде:
в контейнере сессии нет git-идентичности, и `git commit` без неё завершается
ошибкой `unable to auto-detect email address`. Раннеры script-нод — минимальные образы:
в bash-раннере нет `git`, в python-раннере нет `pytest`, поэтому тесты
`qa-calc` написаны на `unittest`.

**Скрипт 0 (bash)** — вывод попадает в `{{node.script_output}}`, файл — в артефакты:
```bash
set -euo pipefail
cd "$TASK_REPOS_PATH/qa-calc"
echo "Файлы:"; ls -1
echo "README:"; cat README.md
echo "Проверка сети:"; (getent hosts example.com && echo "СЕТЬ ЕСТЬ") || echo "сети нет"
ls -1 > "$TASK_ARTIFACTS_PATH/qa-context.txt"
```

**Скрипт 3 (python)** — ненулевой код возврата означает сбой ноды. Файл
`fail-tests` в артефактах задачи принудительно роняет ноду — так кейс E2E-11
управляет сбоем без правки кода:
```python
import os
import subprocess
import sys

if os.path.exists(os.path.join(os.environ["TASK_ARTIFACTS_PATH"], "fail-tests")):
    print("fail-tests найден в артефактах — сбой по сценарию QA")
    sys.exit(1)

repo = os.path.join(os.environ["TASK_REPOS_PATH"], "qa-calc")
result = subprocess.run(
    [sys.executable, "-m", "unittest", "-v"],
    cwd=repo,
    capture_output=True,
    text=True,
)
print(result.stdout + result.stderr)
sys.exit(result.returncode)
```

У ноды «Тесты» `max_retries = 2`, `retry_base_delay_seconds = 5` (для кейса
E2E-11).

## 3. P0 — основной путь

Кейсы E2E-01…E2E-10 проходятся подряд на одной задаче `RR-QA-1`.

### E2E-01. Создание задачи

1. «Новая задача»: код `RR-QA-1`, название «Деление в калькуляторе»,
   описание «Добавить divide с защитой от деления на ноль», репозиторий
   `qa-calc` с ролью «чтение и запись», базовая ветка `main`, LLM-аккаунт.
2. Код с пробелом (`RR QA-1`) — форма не отправляется, поле подсвечено
   красным, под ним «Код задачи не должен содержать пробелов».
3. После создания — выбрать пайплайн «QA: фича с тестами».

**Ожидается**
- Задача в статусе «Новая», в карточке нод — шесть нод в порядке пайплайна,
  у каждой тип под названием, все включены.
- Лог: `pipeline_bound_to_task` с `pipeline_id`.
- Предпросмотр в диалоге своего промта задачи («+ Промт» в карточке нод) с
  текстом `Код {{task.code}}, {{env.QA_GREETING}}, {{env.QA_TOKEN}}`
  показывает `RR-QA-1`, «Привет из QA» и замаскированный секрет (`••••••`).
  Предпросмотр в конструкторе пайплайна задачи не знает и только проверяет
  переменные.

### E2E-02. Настройка прогона под задачу

1. Попробовать отключить ноду «Сбор контекста» — предупреждение о зависимой
   ноде «План» (`{{node.script_output}}`). Отменить.
2. Поставить «⏸ пауза после» у ноды «Реализация».
3. «+ Промт» после ноды «План»: название «Граничные случаи», тип «промт»,
   текст «Перечисли граничные случаи для divide и проверь, что план их
   покрывает». Сохранить.
4. Проверить, что у ноды «Очистка контекста» нет переключателя паузы.
5. Открыть пайплайн «QA: фича с тестами» в «Пайплайнах».

**Ожидается**
- Свой промт стоит между «План» и «Реализация», помечен «свой промт», у него
  есть «Изменить» и «Удалить».
- Пайплайн-шаблон не изменился: в нём по-прежнему шесть нод, без паузы.
- Логи: `task_node_pause_toggled` (`pause_after: true`), `custom_task_node_added`
  с `order_index: 2`.
- SQL «Снимок нод задачи»: семь строк, свой промт с `custom = true`.

### E2E-03. Запуск и скрипт-нода

1. «Запустить задачу».

**Ожидается**
- Статусы: «Новая» → «В очереди» → «В работе» (без перезагрузки страницы).
- Логи по порядку: `task_status_transitioned` (`new → queued`, затем
  `queued → in_progress`), `repository_cloned`, `task_workspace_prepared`,
  `session_connected`, `script_node_finished`.
- «Диалог»: блок вывода скрипта со списком файлов и README; строка проверки
  сети — «сети нет» (раздел 19.3: script-контейнер без сети).
- «Обзор» → «Артефакты»: появился `qa-context.txt`.
- `node_logs`: запись ноды «Сбор контекста», `trigger_type = pipeline`,
  `attempt_number = 1`, `status = success`.

### E2E-04. Ревью плана

1. Дождаться окончания ноды «План».
2. Нажать «Доработать план», ввести «Добавь тест на отрицательные числа».
3. После нового плана выбрать «Принять план, подтверждать каждое действие».

**Ожидается**
- Статус «Ревью плана», над виджетом — полный текст плана, три варианта:
  «Принять план и продолжить автоматически», «Принять план, подтверждать
  каждое действие», «Доработать план».
- Пока идёт `plan_prompt`, агент не правит файлы (раздел 9.5).
- «Доработать план» не расходует retry: в `node_logs` нет новой попытки с
  `attempt_number = 2` из-за доработки (раздел 11.7, правило 7 CLAUDE.md).
- После принятия ход ноды «План» заканчивается без правок: агент отвечает,
  что план принят и реализация будет в следующем запросе; запись «Плана» в
  `node_logs` — `success`, одна попытка.
- Затем `session_permission_mode_changed` (`default`), задача снова
  «В работе».

### E2E-05. Свой промт и реализация с подтверждением действий

1. Свой промт «Граничные случаи» выполняется сразу после плана.
2. На ноде «Реализация» агент запрашивает разрешение на правку файла — виджет
   «Разрешить» / «Запретить». Один раз нажать «Запретить», затем на повторный
   запрос — «Разрешить» (и на последующие).

**Ожидается**
- Запросы «Разрешить» / «Запретить» приходят только в ноде «Реализация»;
  до неё файлы репозитория не меняются.
- Ответы агента выводятся потоково, блоки свёрнуты до превью.
- «Логи» → нода «Реализация»: `rendered_prompt` содержит код задачи, текст
  `{{node.plan_text}}` (утверждённый план) и «Привет из QA»; секретов в
  открытом виде нет.
- Статус при ожидании разрешения — «Ждёт ответа», после ответа — «В работе».

### E2E-06. Пауза после ноды и диалог

1. После успешной «Реализации» задача встаёт на паузу.
2. На вкладке «Диалог» отправить свободный промт: «Покажи `git diff --stat` и
   последний коммит».
3. Нажать «Продолжить».

**Ожидается**
- Статус «На паузе»; логи: `pipeline_paused_after_node`, `task_paused_after_node`.
- Свободный промт выполняется сразу (не «В очереди»); в «Логах» запись с
  триггером «Свободный промт» (`freeform_manual`); в ответе — коммит
  `feat: add divide`.
- После «Продолжить» — `task_resumed`, задача «В работе», следующая нода —
  «Тесты».

### E2E-07. Тесты, очистка контекста, итог

**Ожидается**
- «Тесты»: вывод `unittest` со всеми тестами `OK`, включая новые для `divide`.
- «Очистка контекста»: `session_context_cleared`, задача продолжает работу в
  новой сессии без участия пользователя.
- «Итог»: ответ опирается на вывод тестов (`{{node.script_output}}` — вывод
  ближайшей предыдущей скрипт-ноды «Тесты»), а не на прежний диалог.

### E2E-08. Завершение

**Ожидается**
- `repository_pushed` с `branch_name: feature/RR-QA-1`, затем
  `task_status_transitioned` → `done`, статус «Готово».
- Статус на странице задачи и на дашборде меняется без перезагрузки; Web Push
  «Задача выполнена», если подписка включена (уведомления внутри интерфейса
  ТЗ не предусматривает).
- `node_logs`: у каждой включённой ноды пайплайна (включая свой промт) есть
  `success` (раздел 17.5).
- «Мониторинг» → `app_logs` по задаче: нет записей уровня «ошибка»/«критично».

### E2E-09. Проверка результата в Git и по SFTP

1. `scripts/qa/stand.sh export`, клонировать ветку `feature/RR-QA-1`
   (раздел 1.2).
2. В клоне ветки проверить: `git log --oneline origin/main..HEAD`,
   `git diff origin/main`, `python3 -m unittest -v`.
3. Если SFTP настроен (логин в «Пользователях», ключ в профиле):
   `sshfs -p 2222 <логин>@<домен>:/ ~/tracker -o reconnect`.

**Ожидается**
- В ветке коммит `feat: add divide` с автором «AI Tracker»; `divide` делит и бросает
  `ZeroDivisionError` при нуле; новые тесты проходят; в README — строка
  «Привет из QA».
- В `main` git-хоста изменений нет.

### E2E-11. Сбой ноды, retry и перезапуск

Подготовка: задача `RR-QA-3` по пайплайну «QA: фича с тестами», без паузы.
До запуска загрузить в «Артефакты» пустой файл `fail-tests`.

1. Запустить задачу и дождаться сбоя ноды «Тесты».
2. Проверить, какие ноды и позиции вставки доступны.
3. Вставить свой промт после «Тесты»: «Перечисли, какие тесты были запущены».
4. Удалить `fail-tests` в «Артефактах» и нажать «Перезапустить с текущей ноды».

**Ожидается**
- Две попытки «Тестов» с задержкой: `node_retry_scheduled`, затем
  `node_failed_exhausted_retries`; в `node_logs` — `attempt_number` 1 и 2,
  обе `failed`, в выводе — «fail-tests найден в артефактах».
- Статус «Ошибка», на карточке «Сбой на ноде №N» (N — номер «Тестов»),
  `last_failed_order_index` = `order_index` «Тестов».
- Ноды до «Тестов» и сами «Тесты» заблокированы с пояснением «уже выполнено»;
  чекбоксы и «+ Промт» — только после «Тестов»; «+ Промт» перед «Тестами»
  нет. Свободный промт в «Ошибке» недоступен: сессия не активна (раздел 8.2).
- «Артефакты» в «Ошибке» доступны для удаления.
- Перезапуск начинает с «Тестов» (ноды до них не повторяются), затем
  выполняет вставленный промт и остальные ноды; итог — «Готово».

Код, из-за которого падают тесты, в «Ошибке» исправить нельзя: свободный
промт недоступен, а свой промт встаёт только после упавшей ноды. Чтобы
исправлять код перед повтором тестов, ставят «⏸ пауза после» на ноду перед
ними заранее (E2E-06) или возвращают задачу в новые (E2E-17).
