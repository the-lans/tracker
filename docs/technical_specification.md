## 1. Назначение и общая концепция

### 1.1 Что такое продукт

AI-трекер задач — веб-приложение для управления автоматизированными задачами разработки, которые выполняются автономным AI-агентом (Claude Code) через программное управление сессиями. Пользователь создаёт задачу, привязывает к ней один или несколько Git-репозиториев, выбирает пайплайн (последовательность шагов-нод) и запускает выполнение — вручную или по расписанию. Каждая нода пайплайна — это промт, слэш-команда, изолированный скрипт, служебная очистка контекста сессии, либо нода режима планирования, формирующая план реализации перед началом активных изменений. Помимо пайплайна, задача располагает собственной библиотекой параметризированных промтов, выполняемых многократно и в произвольный момент.

### 1.2 Ключевые пользовательские сценарии

1. Пользователь создаёт задачу, указывает репозитории (с ролями read-only/read-write), выбирает пайплайн и LLM-аккаунт.
2. При выборе пайплайна пользователь видит список его нод и может отключить любые ноды именно для этой задачи, не изменяя переиспользуемый пайплайн-шаблон.
3. Пользователь либо запускает выполнение немедленно, либо назначает дату и время автоматического запуска.
4. Пайплайн последовательно выполняет включённые ноды; ответ или вывод предыдущей ноды подставляется в следующую через шаблонные переменные.
5. Если пайплайн содержит ноду режима планирования, выполнение приостанавливается по завершении формирования плана: если пользователь заранее включил автопринятие плана — выполнение продолжается автоматически; если нет — задача переходит в статус ожидания решения по плану, и пользователь выбирает дальнейшее действие через виджет выбора в интерфейсе.
6. Если LLM-агенту в любой другой момент требуется уточнение (в том числе с вариантами ответа) — задача переходит в статус ожидания ввода, пользователь отвечает через поле трекера, через виджет выбора или напрямую через `claude.ai/code`.
7. В любой момент, независимо от состояния пайплайна, пользователь может выполнить произвольный системный промт из библиотеки задачи, остановить его, либо ввести собственный параметризированный промт в свободное текстовое поле. Если сессия занята выполнением ноды пайплайна — запрос ставится в очередь и выполняется автоматически, как только сессия освобождается.
8. Если нода пайплайна или системный промт обращается к браузеру через MCP-инструмент (например, Playwright), эта задача не конфликтует с любой другой параллельно выполняющейся задачей за общий браузерный профиль — у каждой задачи собственный изолированный профиль инструмента.
9. Если веб-мост к `claude.ai/code` обрывается, пользователь нажимает кнопку переподключения на карточке задачи.
10. После завершения задачи изменения запушены в соответствующие ветки Git-репозиториев; рабочая директория репозиториев вручную очищается пользователем после проверки результата.
11. Администратор управляет списком разрешённых пользователей, LLM-аккаунтами, шаблонами репозиториев, глобальными переменными окружения, библиотекой системных промтов, конфигурацией MCP-серверов и расписанием фоновых задач — всё через UI.

### 1.3 Технологический фундамент

- Управление сессиями Claude Code — исключительно через официальный **Claude Agent SDK для Python** (`claude-agent-sdk`), класс `ClaudeSDKClient`. Прямое управление CLI-процессом через псевдотерминал не используется.
- Каждая задача имеет ровно одну сессию Claude Code на весь свой жизненный цикл. Контекст сессии сохраняется между всеми нодами пайплайна, всеми запусками системных промтов и всеми свободными промтами, не очищается автоматически. Очистка происходит только по явному действию пользователя или ноде `clear_context`.
- Обращения к сессии всегда строго последовательны — сессия не принимает второй запрос, пока не завершён предыдущий (раздел 6).
- Каждая запущенная сессия одновременно доступна для просмотра и ручного вмешательства через веб-интерфейс `claude.ai/code` (мост `/remote-control`); оба канала ввода разрешены параллельно.
- MCP-инструменты, поддерживающие постоянное состояние выполнения (браузерные профили, файловые блокировки и аналогичные ресурсы с ограничением на единственного одновременного пользователя), обязаны конфигурироваться с изоляцией на уровне задачи — раздел 10.

## 2. Архитектура системы

### 2.1 Общая схема компонентов

| Компонент | Назначение |
|---|---|
| **Backend API** | REST/WebSocket API, бизнес-логика, оркестрация задач |
| **Frontend SPA** | Веб-интерфейс пользователя и администратора |
| **Celery Worker** | Асинхронное выполнение задач: запуск сессий Claude Code, скрипт-ноды, git-операции |
| **Celery Beat** | Планировщик периодических фоновых задач |
| **PostgreSQL** | Основное хранилище данных, включая логи и историю выполнения нод |
| **Redis** | Брокер сообщений Celery, кеш, распределённые блокировки, pub/sub для WebSocket |
| **Reverse Proxy (Caddy)** | Автоматический TLS, маршрутизация запросов |
| **Docker Runner-образы** | Изолированные окружения для script-нод (Python, Bash) |
| **User-Provisioner** | Privileged-сервис для управления системными Linux-пользователями |

### 2.2 Рекомендованный технологический стек

| Слой | Технология | Обоснование |
|---|---|---|
| Backend framework | FastAPI (async) | Совместим с асинхронным Claude Agent SDK; автогенерация OpenAPI-схемы |
| ORM и миграции | SQLAlchemy 2.x (async) + Alembic | Версионируемые, идемпотентные миграции |
| Фоновые задачи | Celery + Redis | Retry «из коробки», совместимость с динамическим расписанием через Celery Beat |
| База данных | PostgreSQL 15+ | `jsonb` для гибких полей, надёжные транзакции для критичных переходов статусов |
| Frontend | React 19 + Vite + TanStack Query + shadcn/ui | Меньше самописного кода синхронизации состояния с сервером |
| Real-time | WebSocket (нативный, через FastAPI) + Web Push | Транспорт поверх уже используемого Redis pub/sub |
| Логирование | `structlog` (структурированные JSON-логи) + запись критичных событий в PostgreSQL (`app_logs`) | Фильтрация в админ-панели без парсинга текстовых файлов |
| Контейнеризация | Docker + Docker Compose | Обязательное требование раздела 21 |

### 2.3 Принцип разделения backend/frontend

Backend и frontend — раздельные кодовые базы, взаимодействующие только через документированный HTTP/WebSocket API. Frontend не имеет прямого доступа к базе данных, файловой системе сервера или Docker. Все операции, требующие серверных привилегий (git-операции, запуск контейнеров, управление сессиями Claude Code), выполняются исключительно на backend-стороне.

### 2.4 Разделение ответственности backend-модулей

| Модуль | Ответственность |
|---|---|
| `api/` | HTTP-эндпоинты, валидация входных данных, сериализация ответов |
| `services/` | Бизнес-логика: оркестрация пайплайнов, работа с сессиями, git-операции |
| `db/` | ORM-модели, миграции |
| `clients/` | Обёртки над Claude Agent SDK, GitLab API, MCP-серверами |
| `tasks/` | Celery-задачи (асинхронные и периодические) |
| `ws/` | WebSocket-обработчики для real-time уведомлений |
| `logging/` | Единая точка конфигурации структурированного логирования и записи в `app_logs` |

#### Таблица `nodes` (ноды пайплайна и системные промты библиотеки — единая сущность)

Ключевое архитектурное решение: нода пайплайна и системный промт библиотеки — одна и та же сущность с одинаковым набором полей выполнения. Разница только в том, привязана ли нода к конкретному пайплайну (`pipeline_id` заполнен, `order_index` определяет порядок) или существует самостоятельно как переиспользуемый элемент библиотеки (`pipeline_id = NULL`).

| Поле | Тип | Описание |
|---|---|---|
| `id` | UUID | Первичный ключ |
| `pipeline_id` | FK → pipelines, **nullable** | `NULL` — нода является самостоятельным системным промтом библиотеки, не входит ни в один пайплайн |
| `order_index` | integer, nullable | Порядок выполнения внутри пайплайна; не используется, если `pipeline_id = NULL` |
| `name` | string | Название ноды/промта |
| `description` | text, nullable | Описание — обязательно для узлов библиотеки, чтобы пользователь понимал назначение при выборе из списка |
| `node_type` | enum (`plain_prompt`, `slash_command`, `script`, `clear_context`, `plan_prompt`) | Тип ноды |
| `prompt_template` | text, nullable | Параметризованный шаблон промта (для `plain_prompt` и `plan_prompt`); поддерживает подстановку `{{...}}` |
| `command_invocation` | string, nullable | Литеральная строка вызова слэш-команды вида `/имя аргументы` (для `slash_command`); **не проходит через шаблонизатор проекта** — передаётся в сессию как есть |

| `timeout_seconds` | integer | Таймаут выполнения, по умолчанию 600; применяется одинаково и к нодам пайплайна, и к запускам из библиотеки |

#### Таблица `task_nodes` (снимок нод пайплайна для конкретной задачи)

При привязке пайплайна к задаче для каждой ноды создаётся запись-снимок, позволяющая отключать конкретные ноды именно для данной задачи, не затрагивая сам пайплайн как переиспользуемый шаблон.

| Поле | Тип | Описание |
|---|---|---|
| `id` | UUID | Первичный ключ |
| `task_id` | FK → tasks | |
| `node_id` | FK → nodes | Ссылка на ноду пайплайна-шаблона |
| `order_index` | integer | Копия порядка на момент привязки (защищает от смещения порядка при последующем редактировании шаблона) |
| `is_enabled` | boolean, default `true` | Пользовательское включение/отключение ноды именно для этой задачи |
| `created_at` | timestamp | |

Требование к редактируемости: пока задача в статусе `new` — редактируется свободно. После первого перехода из `new` редактирование запрещено, **за исключением** статуса `failed`: в этом состоянии разрешено редактировать `is_enabled` только для нод, у которых `order_index` строго больше значения `tasks.last_failed_order_index` — то есть только для нод, ещё не приступавших к выполнению. Ноды с `order_index`, меньшим или равным точке сбоя, включая саму упавшую ноду, недоступны для редактирования.

### 3.2 Требования к целостности данных

- Удаление пайплайна, используемого хотя бы одной задачей, запрещено на уровне API — вместо удаления предлагается архивация.
- Удаление ноды-системного промта, привязанной хотя бы к одной задаче через `task_library_prompts`, запрещено — только архивация.
- Удаление репозитория, привязанного к активной задаче, запрещено.
- Все значения, помеченные как секретные, хранятся в БД в зашифрованном виде (симметричное шифрование с ключом из переменной окружения сервера, не в самой БД).
- При привязке пайплайна к задаче создание записей `task_nodes` обязано выполняться атомарно в одной транзакции вместе с изменением `tasks.pipeline_id` — частичное создание снимка недопустимо.
- Сохранение MCP-сервера с `has_stateful_resource = true` и `isolation_mode = none` (или `NULL`) запрещено на уровне валидации API — раздел 10.2.

## 4. Глобальный принцип: параметризованные промты и непараметризованные команды

Это сквозное правило, применяемое одинаково во всех частях системы — в нодах пайплайна (включая `plan_prompt`), в системных промтах библиотеки и в свободном пользовательском вводе.

| Категория ввода | Проходит через шаблонизатор `{{...}}` | Примеры |
|---|---|---|
| Обычный промт (`plain_prompt`, `plan_prompt`) | Да | `prompt_template` ноды пайплайна, текст системного промта библиотеки, текст в свободном поле ввода на странице задачи |
| Слэш-команда (`slash_command`, начинается с `/`) | **Нет** | `command_invocation` передаётся в сессию Claude Code буквально; аргументы команды (`$1`, `$2`, `$ARGUMENTS`) разворачивает сам Claude Code средствами файла команды в `.claude/commands/`, а не backend трекера |

**Практическое следствие:** если пользователю нужно передать в слэш-команду значение переменной задачи (например, код задачи), он обязан подставить это значение вручную при заполнении поля `command_invocation` на этапе создания ноды/промта — автоматическая подстановка `{{task.code}}` для слэш-команд не выполняется. Это ограничение фиксируется в подсказке интерфейса при выборе типа ноды «Слэш-команда», чтобы не создавать ложных ожиданий у пользователя.

- Рендеринг выполняется непосредственно перед отправкой в SDK или запуском контейнера — не заранее; для MCP-конфигурации с изоляцией (раздел 10) рендеринг выполняется перед стартом сессии задачи.

## 6. Управление сессиями Claude Code

### 6.1 Жизненный цикл сессии

- Сессия создаётся ровно один раз при первом запуске задачи (переход в статус `in_progress` из `new`/`queued`).
- Объект клиента сессии (`ClaudeSDKClient`) хранится как персистентная сущность в рамках выполнения Celery-задачи и переиспользуется всеми последующими нодами пайплайна, всеми запусками системных промтов и всеми свободными промтами до завершения задачи или явной команды очистки контекста.
- `session_id`, присваиваемый Claude Agent SDK, сохраняется в поле `tasks.session_id` сразу после создания сессии.
- При повторном запуске задачи после статуса `failed` используется уже существующий `session_id` — сессия не пересоздаётся, если явно не выбрана очистка контекста.

### 6.2 Строгая последовательность обращений к сессии

Один объект `ClaudeSDKClient` не может параллельно обрабатывать два запроса. Любое обращение к сессии — выполнение ноды пайплайна, запуск системного промта библиотеки, отправка свободного промта, ответ на `awaiting_input`/`plan_review` — обязано проходить через единый внутрипроцессный семафор (mutex) на уровне Celery-задачи, обслуживающей конкретную сессию. Детали обработки конкурентных ручных запросов описаны в разделе 7.3.

### 6.3 Доступ к сессии через `claude.ai/code`

- При старте задачи, наряду с созданием сессии через SDK, инициируется мост `/remote-control`, делающий сессию доступной для просмотра и ручного ввода через веб-интерфейс `claude.ai/code`.
- Оба канала ввода — веб-интерфейс `claude.ai/code` и любое из полей ввода трекера (ответ на `awaiting_input`, выбор в `plan_review`, запуск системного промта, свободный промт) — работают параллельно без ограничений и блокировок; ответственность за отсутствие дублирующей отправки лежит на пользователе.
- Сообщения, отправленные через `claude.ai/code`, должны отображаться в чат-ленте трекера с явной пометкой источника, чтобы не создавать впечатление появления ответа без причины.
- **Важное техническое допущение, подлежащее верификации на этапе реализации:** команда `/remote-control` в реальном использовании может подразумевать интерактивное продолжение текущей CLI-сессии, а не исключительно программный вызов через готовый API. Перед проектированием кнопки переподключения (раздел 6.5) и автоматического мониторинга (раздел 6.6) обязателен отдельный технический этап проверки: обладает ли процесс, управляемый через `ClaudeSDKClient`, предсказуемым программным способом установления/восстановления моста, или это требует эмуляции интерактивного ввода команды в поток стандартного ввода дочернего процесса. Результат проверки может потребовать корректировки внутренней реализации разделов 6.5–6.6 без изменения пользовательского сценария (кнопка и статус в UI остаются, меняется только внутренний механизм вызова).

### 6.4 Хранение истории диалога

- Полная история диалога сессии физически хранится Claude Code в формате построчного JSON, путь строится на основе изолированной конфигурационной директории (`CLAUDE_CONFIG_DIR`), привязанной к конкретному `llm_accounts.claude_config_dir`.
- Реплики дополнительно дублируются в `node_logs` в момент их получения — во избежание потери данных при удалении файлов истории по истечении срока хранения Claude Code.
- Срок автоматического удаления истории сессий на сервере должен быть переопределён в конфигурации (`~/.claude/settings.json` соответствующего `CLAUDE_CONFIG_DIR`) на значение не менее срока хранения задач в системе.

### 6.5 Ручное переподключение моста `remote-control`

На карточке задачи присутствует кнопка **«🔗 Переподключить удалённую сессию»**, доступная постоянно, независимо от текущего значения `remote_control_status`. Нажатие инициирует повторное выполнение процедуры установления моста `/remote-control` для активной сессии задачи — функционально это ручной аналог команды `/remote-control`, доступный без обращения к серверу. Кнопка не заменяет автоматический мониторинг (раздел 6.6), а дополняет его — пользователь может переподключиться профилактически, даже когда автоматика ещё не зафиксировала разрыв. Кнопка визуально акцентируется (например, изменением цвета) при `remote_control_status = disconnected`.

### 6.6 Автоматический мониторинг состояния моста

- Периодическая задача `check_remote_control_bridges` (раздел 16) проверяет состояние моста для всех задач в статусах `in_progress`/`awaiting_input`/`plan_review`.
- При обнаружении разрыва выполняется до двух автоматических попыток восстановления с задержкой.
- Если автоматическое восстановление не удалось — поле `remote_control_status` устанавливается в `disconnected`, пользователю отправляется уведомление.
- Статус моста отображается независимо от общего статуса задачи (задача может продолжать выполняться, даже если мост временно недоступен).

## 7. Библиотека системных промтов

### 7.1 Концепция

Системный промт — нода с `pipeline_id = NULL`, хранящаяся как переиспользуемый элемент, доступный для добавления в любую задачу. В отличие от нод пайплайна, системные промты не выполняются автоматически и не имеют фиксированного порядка — пользователь запускает их вручную, когда считает нужным, произвольное количество раз, в любой последовательности.

### 7.2 Управление библиотекой

- Создание, редактирование и архивация системных промтов доступны через отдельный раздел «Библиотека промтов» — форма идентична форме создания ноды пайплайна (раздел 3.1, таблица `nodes`), за исключением полей `order_index` и `is_skipped`, которые для библиотечных промтов не имеют смысла.
- Системный промт может иметь тип `plain_prompt`, `slash_command` или `script`. Типы `clear_context` и `plan_prompt` для библиотеки бессмысленны (это разовые пайплайн-действия) и не должны предлагаться при создании библиотечного промта.

### 7.3 Использование промта в задаче и очередь при занятой сессии

- Пользователь добавляет промт из общей библиотеки в список задачи (создаётся запись `task_library_prompts`); один и тот же промт может быть добавлен к разным задачам одновременно.
- Список системных промтов задачи отображается в виде таблицы: название промта, кнопка **▶ Выполнить**, кнопка **■ Остановить**, время последнего запуска, текущий статус.
- **Если сессия свободна** в момент нажатия «▶ Выполнить» — запрос выполняется немедленно, создаётся запись `node_logs` (`trigger_type = library_manual`).
- **Если сессия занята** выполнением ноды пайплайна или другим ручным запросом — запрос не отклоняется и не выполняется параллельно, а помещается в `task_manual_request_queue` со статусом `queued`; `task_library_prompts.last_run_status` для этого промта переводится в `queued`, что видно пользователю в таблице. То же правило действует для отправки свободного промта (раздел 8) — при занятой сессии текст сохраняется в очередь с `request_type = freeform_prompt`.
- Сразу по завершении текущего занимающего сессию обращения оркестратор обязан проверить очередь `task_manual_request_queue` и обработать самый старый по времени `queued`-запрос (`FIFO`) **прежде**, чем переходить к следующей ноде пайплайна — это обеспечивает предсказуемую очерёдность и не даёт ручным запросам пользователя «застревать» позади длинной цепочки автоматических нод.
- Пользователь может отменить ещё не обработанный запрос из очереди — статус меняется на `cancelled`, запрос не выполняется.
- Кнопка **■ Остановить** активна как для `running`, так и для `queued` состояния (во втором случае эквивалентна отмене из очереди).
- Повторный запуск одного и того же системного промта возможен неограниченное количество раз — `max_retries` к запускам из библиотеки не применяется: пользователь сам управляет количеством и моментом запуска.

### 7.4 Таймаут выполнения библиотечных промтов

Поле `timeout_seconds` ноды применяется к запускам из библиотеки точно так же, как к нодам пайплайна: если выполнение (ожидание ответа LLM или завершения скрипта) превышает установленное время, оно принудительно прерывается, соответствующая запись `node_logs` автоматически переводится в статус `failed`, `task_library_prompts.last_run_status` обновляется до `failed`. Разница с пайплайном — только в отсутствии последующего автоматического retry: пользователь при необходимости запускает промт заново вручную кнопкой «▶ Выполнить».

### 7.5 Выполнение в общей сессии

Выполнение системного промта происходит в той же активной сессии Claude Code, что и выполнение пайплайна задачи — контекст общий, с учётом строгой последовательности обращений (раздел 6.2) и очереди (раздел 7.3).

## 8. Свободный параметризованный промт на странице задачи

### 8.1 Назначение

Отдельно от библиотеки системных промтов, на странице задачи должно быть доступно текстовое поле для одноразового ввода параметризованного промта без сохранения его как переиспользуемой сущности — для случаев, когда пользователю нужно быстро что-то спросить или попросить сессию сделать разовое действие.

### 8.2 Требования к реализации

- Поле поддерживает подстановку тех же переменных, что определены в разделе 5, кроме `{{node.*}}` (нет привязки к конкретной предыдущей ноде).
- Перед отправкой пользователь может просмотреть, как выглядит текст после подстановки переменных.
- При свободной сессии запрос выполняется немедленно, создаётся запись `node_logs` с `trigger_type = freeform_manual`, `node_id = NULL`, `triggered_by` — текущий пользователь.
- При занятой сессии запрос ставится в очередь (раздел 7.3), пользователь видит визуальный индикатор «В очереди» рядом с полем ввода вместо немедленного результата.
- Отправленный текст и последующий ответ отображаются в общей чат-ленте сессии на равных с остальными типами сообщений, с визуальной пометкой источника («отправлено вручную»).
- Данное поле не привязано к какому-либо статусу задачи (в отличие от поля ответа при `awaiting_input`) — доступно для отправки в любой момент, пока сессия активна.

## 9. Режим планирования (Plan Mode)

### 9.1 Концепция

Отдельный тип ноды `plan_prompt` переводит активную сессию в режим планирования Claude Agent SDK (`permission_mode = "plan"`) перед отправкой рендеренного промта. В этом режиме агент вправе исследовать репозиторий и код, но не может редактировать файлы или выполнять изменяющие команды — только сформировать план реализации. Завершение планирования агент сигнализирует служебным вызовом инструмента `ExitPlanMode`, содержащим текст сформированного плана.

### 9.2 Обработка завершения планирования

Backend перехватывает вызов `ExitPlanMode` через механизм разрешений SDK (аналогично общему механизму раздела 10 — здесь имеется в виду универсальный виджет выбора, раздел 9.3 использует его инфраструктуру) и обрабатывает его по следующей логике:

1. **Если `tasks.auto_accept_plan = true`** (переключатель выставлен пользователем заранее, до или во время выполнения пайплайна, но до наступления момента завершения планирования) — backend автоматически подтверждает план, сохраняет его текст в `node_logs.pending_plan_text` соответствующей записи с итоговым статусом `success`, переключает `tasks.current_permission_mode` на выбранный по умолчанию рабочий режим, и пайплайн продолжает выполнение следующей ноды без остановки и без уведомления, кроме отметки в истории.
2. **Если `tasks.auto_accept_plan = false`** — задача переходит в статус `plan_review`, соответствующая запись `node_logs` получает статус `awaiting_decision`, поле `pending_plan_text` заполняется текстом плана, поле `pending_options` заполняется вариантами дальнейшего действия. Выполнение пайплайна приостанавливается до получения решения пользователя. Отправляется уведомление.

### 9.3 Варианты решения пользователя

Пользователю предлагается выбор через универсальный виджет выбора (см. отдельный раздел про механизм ниже в этом же разделе), включающий как минимум следующие варианты:

- **«Принять план и продолжить автоматически»** — эквивалентно ручному включению `auto_accept_plan` для дальнейшего выполнения оставшейся части пайплайна; после выбора этого варианта `current_permission_mode` переключается в `acceptEdits` или `bypassPermissions`.
- **«Принять план, подтверждать каждое действие»** — план принимается, но `current_permission_mode` остаётся `default`, что означает продолжение работы с запросом подтверждения на потенциально опасные операции.
- **«Доработать план»** — эквивалентно возврату `deny` в SDK по вызову `ExitPlanMode`; пользователь получает возможность ввести дополнительный текст с пожеланиями к доработке (переиспользуется то же текстовое поле ввода, что и для ответа на `awaiting_input`), этот текст передаётся сессии как фидбек, режим планирования не завершается, задача возвращается в `in_progress` с ожиданием нового вызова `ExitPlanMode`.

Пользователь выбирает вариант непосредственно в интерфейсе задачи, рядом с окном ввода — аналогично тому, как выбор происходил бы в CLI или в веб-интерфейсе `claude.ai/code`, если пользователь предпочёл ответить через тот канал.

### 9.4 Режим разрешений после утверждения плана

Конкретный `permission_mode`, устанавливаемый после утверждения плана, определяется выбором пользователя из предложенных вариантов (раздел 9.3), а не фиксированным значением в конфигурации ноды — уровень автономности дальнейшего выполнения осознанно выбирается пользователем в момент принятия конкретного плана, а не заранее на этапе конструирования пайплайна.

### 9.5 Ограничения ноды `plan_prompt`

- Доступна только внутри пайплайна (`pipeline_id` заполнен); как самостоятельный элемент библиотеки не существует (аналогично `clear_context`).
- Ссылка `{{node.plan_text}}` (раздел 5) доступна только в нодах, следующих за `plan_prompt`, и содержит финальный утверждённый текст плана.
- Ретрай применяется только к техническим сбоям вызова SDK (сетевые ошибки, таймаут ожидания ответа), но не к решению пользователя «Доработать план» — повторная доработка не считается неудачной попыткой и не расходует счётчик `max_retries`.

### 9.6 Универсальный виджет выбора — общий механизм для уточняющих вопросов агента

Механизм разрешений Claude Agent SDK вызывает единый программный callback перед выполнением любого проверяемого инструмента, включая как `ExitPlanMode` (описан выше), так и общий инструмент уточняющих вопросов с вариантами ответа (`AskUserQuestion`). Поскольку оба случая технически используют одну и ту же точку перехвата на стороне SDK, интерфейс трекера обязан обрабатывать их единым UI-механизмом, а не двумя изолированными реализациями:

- **Если `pending_options` заполнено** (агент предложил конкретные варианты ответа, включая случай завершения плана) — интерфейс отображает рядом с полем ввода набор кнопок по числу вариантов, с текстом из `pending_options[].label`. Выбор кнопки отправляет `pending_options[].id` как решение, дополнительное текстовое пояснение пользователь может ввести опционально.
- **Если `pending_options` пусто, но `pending_question` заполнен** — это обычный открытый уточняющий вопрос без вариантов; интерфейс отображает только текстовое поле ввода, без кнопок, что полностью соответствует стандартному поведению `awaiting_input`.
- Статус `plan_review` является, с точки зрения UI-рендеринга, частным случаем описанного механизма: он всегда сопровождается непустым `pending_options` и дополнительно — заполненным `pending_plan_text`, который отображается как выделенный блок плана над виджетом выбора, а не просто как обычная реплика в чат-ленте.
- Callback разрешений SDK, получив вызов инструмента с вариантами, обязан асинхронно дождаться решения пользователя, не блокируя при этом остальную систему — реализуется как ожидание на объекте синхронизации (`asyncio.Event`/эквивалент), разрешаемом обработчиком API-эндпоинта приёма решения пользователя.
- Ответ пользователя, полученный через любой из трёх каналов (кнопка выбора в трекере, текстовый ввод в трекере, действие через `claude.ai/code`), обязан транслироваться в один и тот же внутренний метод завершения ожидания — независимо от канала, откуда пришло решение.
- Если решение получено через `claude.ai/code`, соответствующий выбор отражается в `node_logs.user_input_text` и в чат-ленте с пометкой источника, аналогично прочим сообщениям.

## 10. Изоляция MCP-инструментов с состоянием (Playwright и аналогичные)

### 10.1 Проблема

Ряд MCP-серверов управляет ресурсом, допускающим единовременное использование только одним процессом — типовой пример: Playwright MCP по умолчанию хранит состояние браузера (cookies, авторизацию) в общем persistent-профиле на диске, который физически может удерживать только один запущенный экземпляр браузера одновременно. При параллельном выполнении нескольких задач трекера, каждая из которых пытается воспользоваться таким MCP-сервером с общей конфигурацией, вторая и последующие задачи получают ошибку блокировки профиля/ресурса, а не параллельное выполнение. Поскольку архитектура трекера прямо предполагает параллельное выполнение множества задач (в том числе под одним LLM-аккаунтом — раздел 19.5), эта проблема гарантированно проявится в продукте при использовании таких MCP-серверов без специальной настройки, а не является гипотетическим краевым случаем.

### 10.2 Обязательное правило конфигурации

- Каждый MCP-сервер в таблице `mcp_servers` обязан быть явно помечен полем `has_stateful_resource`. Администратор проставляет это значение при добавлении сервера в систему (раздел 15.5); для Playwright и любого MCP-сервера, управляющего браузерным профилем, файловой блокировкой или аналогичным единолично используемым ресурсом, значение обязано быть `true`.
- Если `has_stateful_resource = true`, поле `isolation_mode` обязано быть заполнено одним из двух допустимых значений — сохранение записи с `isolation_mode = NULL`/`none` в этом случае запрещено на уровне валидации API (раздел 3.2), форма администратора обязана явно требовать выбор режима изоляции прежде, чем разрешить сохранение такого MCP-сервера.
- **Режим `isolated_flag`** — MCP-сервер запускается с параметром эфемерного профиля (для Playwright — флаг изоляции, создающий временный in-memory профиль на каждый запуск браузера, без сохранения состояния между запусками). Подходит, если задачам не требуется сохранять авторизацию/cookies между отдельными вызовами инструмента в рамках одной сессии.
- **Режим `per_task_data_dir`** — MCP-сервер запускается с явным путём к директории профиля, рендерящимся из `isolation_path_template` (раздел 3.1) с подстановкой `{{task.repos_path}}` (раздел 5) — то есть физический профиль браузера/ресурса помещается внутрь директории репозиториев конкретной задачи (например, `tracker/repos/RR-XXXXX/.mcp-profiles/playwright/`), а не в общесистемную директорию. Подходит, если в рамках одной задачи требуется сохранять состояние браузера (например, авторизацию на тестовом стенде) между несколькими последовательными обращениями к инструменту.
- Выбор конкретного режима — ответственность администратора при настройке MCP-сервера, оба варианта гарантируют отсутствие конфликта между параллельно выполняющимися задачами, поскольку в обоих случаях у каждой задачи заведомо собственный, не пересекающийся с другими задачами ресурс.
- Общий persistent-профиль без изоляции, используемый одновременно несколькими задачами, запрещён конфигурацией системы — это не рекомендация, а обязательное требование, реализуемое валидацией на уровне API создания/редактирования MCP-сервера.

### 10.3 Жизненный цикл профиля в режиме `per_task_data_dir`

- Директория профиля создаётся автоматически при первом обращении задачи к соответствующему MCP-серверу — явного шага провижининга при старте задачи не требуется.
- Директория профиля физически расположена внутри `tracker/repos/{{task.code}}/`, и поэтому удаляется автоматически при очистке рабочей директории репозиториев задачи (ручной кнопкой, только в терминальном статусе) — отдельная логика очистки профилей MCP не создаётся, это естественное следствие уже принятой структуры директорий.

### 10.4 Осиротевшие процессы браузера

Принудительное прерывание выполнения (таймаут ноды, остановка пользователем, retry, сбой оркестратора) в момент, когда MCP-инструмент удерживает открытый процесс браузера, может оставить процесс работающим в фоне после завершения родительской задачи — независимо от выбранного режима изоляции, поскольку сам факт принудительного прерывания родительского процесса не гарантирует корректного закрытия дочернего процесса браузера. Осиротевший процесс браузера в режиме `per_task_data_dir` дополнительно может держать файловую блокировку профиля, препятствуя следующему запуску той же задачи после перезапуска ноды. Обслуживается периодической задачей `purge_orphaned_playwright_processes` (раздел 16.2) по аналогии с уже существующей `purge_orphaned_docker_containers`.

### 10.5 Ответственность backend при подготовке сессии задачи

Перед стартом сессии задачи backend обязан сформировать итоговую конфигурацию всех MCP-серверов, доступных через шаблон репозитория задачи (`templates.mcp_server_ids`), подставив в `isolation_path_template` фактическое значение `{{task.repos_path}}` для конкретной задачи, и передать получившуюся конфигурацию при инициализации `ClaudeSDKClient`. Ссылка на общесистемный путь профиля без подстановки переменной задачи в этой конфигурации является ошибкой реализации и обязана отлавливаться на этапе integration-тестирования (раздел 21.1).

## 11. Типы нод и механика их выполнения

### 11.1 Общий принцип

Тип ноды определяет способ выполнения, но не создаёт отдельную сущность в БД — все типы хранятся в единой таблице `nodes` с полем `node_type` (раздел 3.1).

### 11.2 Тип «Обычный промт» (`plain_prompt`)

Рендерится `prompt_template`, результат отправляется в активную сессию через метод отправки сообщения Claude Agent SDK. Ответ считывается потоково, сохраняется в `node_logs.llm_output_text`.

### 11.3 Тип «Слэш-команда» (`slash_command`)

Команда должна существовать как файл в `.claude/commands/` одного из репозиториев задачи, скопированный туда на этапе подготовки репозитория из шаблона. Значение поля `command_invocation` отправляется в сессию буквально, без обработки шаблонизатором проекта.

### 11.4 Тип «Скрипт» (`script`)

Выполняется без обращения к LLM, в изолированном Docker-контейнере.

- Контейнер запускается без сетевого доступа, без исключений.
- Контейнеру монтируется только директория репозиториев текущей задачи, в режиме read-write.
- Переменные окружения ноды передаются в контейнер явно.
- Текст скрипта записывается во временный файл в служебной поддиректории репозиториев задачи перед запуском.
- Образ и интерпретатор определяются полем `script_language`, могут быть переопределены полем `docker_image`.
- `stdout` и код возврата сохраняются в `node_logs`, доступны следующим нодам через `{{node.script_output}}`.
- Превышение `timeout_seconds` прерывает выполнение и запускает логику retry.

### 11.5 Тип «Очистить контекст сессии» (`clear_context`)

Доступен только внутри пайплайна. При выполнении текущая сессия SDK корректно завершается, создаётся новая сессия, новый `session_id` записывается в `tasks.session_id`. Недоступна, если существует хотя бы одна запись `node_logs` со статусом `running`/`awaiting_decision`.

### 11.6 Тип «Режим планирования» (`plan_prompt`)

Подробно описан в разделе 9. Сессия временно переводится в `permission_mode = "plan"`, по завершении — либо автоматически, либо по решению пользователя переключается в рабочий режим.

### 11.7 Логика повторных попыток (retry)

Применяется только к нодам, выполняемым в рамках пайплайна (`trigger_type = pipeline`); не применяется к запускам из библиотеки и к решению «Доработать план».

- Количество попыток — `max_retries` (по умолчанию 3), задержка растёт экспоненциально от `retry_base_delay_seconds`.
- Для `script`-нод повторная попытка пересоздаёт контейнер с нуля.
- Для `plain_prompt`/`slash_command`/`plan_prompt`-нод повторная попытка переиспользует ту же активную сессию.
- После исчерпания всех попыток задача переходит в `failed`, поле `tasks.last_failed_order_index` фиксируется значением `order_index` упавшей ноды.

## 12. Автоматический запуск задачи по расписанию

### 12.1 Пользовательский сценарий

На вкладке «Обзор» доступны поле даты/времени автозапуска (`scheduled_start_at`) и переключатель «Запускать автоматически» (`auto_start_enabled`). Пока переключатель выключен, поле даты неактивно и игнорируется системой, даже если ранее было заполнено.

### 12.2 Механизм проверки

Периодическая задача `check_scheduled_tasks_for_autostart` выполняется каждые 5 минут:

1. Выбирает все задачи со статусом `new`, `auto_start_enabled = true` и `scheduled_start_at <= текущее время`.
2. Для каждой найденной задачи инициирует тот же процесс запуска, что и ручная кнопка «Выполнить».
3. Немедленно после успешной постановки в очередь статус задачи меняется с `new` на `queued` — это обеспечивает идемпотентность: повторный проход периодической задачи в течение того же окна не найдёт задачу повторно.

### 12.3 Требования к обработке ошибок

Если инициация запуска для конкретной задачи завершилась ошибкой, это не должно прерывать обработку остальных задач в той же пачке — ошибка логируется в `app_logs` с привязкой к `task_id`, задача остаётся в статусе `new` для повторной попытки на следующем цикле, пользователю отправляется уведомление о неудачной попытке автозапуска.

## 13. Выбор нод пайплайна для конкретной задачи и история их выполнения

### 13.1 Отключение нод на уровне задачи

При выборе пайплайна на странице задачи интерфейс отображает полный список нод выбранного пайплайна в порядке `order_index`, каждая — с чекбоксом, включённым по умолчанию. Снятие галочки создаёт или обновляет соответствующую запись `task_nodes.is_enabled = false`.

### 13.2 Редактируемость после запуска и после сбоя

- Пока задача в статусе `new` — редактируется `is_enabled` для любой ноды.
- После первого запуска (переход из `new`) — редактирование запрещено полностью.
- **Исключение:** если задача находится в статусе `failed`, разрешено редактировать `is_enabled` только для нод с `order_index`, строго большим `tasks.last_failed_order_index` — то есть только для нод, ещё не приступавших к выполнению в рамках текущего прогона. Нода, на которой произошёл сбой, и все предшествующие ей недоступны для изменения — по ним уже существует зафиксированная история выполнения.

### 13.3 Поведение оркестратора при пропущенных нодах

Оркестратор пайплайна при выполнении итерирует по записям `task_nodes` в порядке `order_index`, пропуская записи с `is_enabled = false` без создания записи в `node_logs` для них. Переменные вида `{{node.script_output}}`, ссылающиеся на пропущенную ноду, должны быть отловлены на этапе валидации пайплайна как потенциальный риск — интерфейс обязан предупреждать пользователя при отключении ноды, если на её вывод ссылается любая из последующих активных нод.

### 13.4 История выполнения нод

Таблица `node_logs` является единой историей выполнения для всех источников — нод пайплайна, системных промтов библиотеки и свободных промтов.

- Каждая попытка выполнения ноды пайплайна создаёт отдельную запись `node_logs` с инкрементом `attempt_number` — история не перезаписывается.
- История доступна на вкладке «Логи» страницы задачи с фильтрацией по конкретной ноде, статусу и `trigger_type`.
- Для административного мониторинга должна быть доступна сводная выборка по всем задачам: какая нода, в какой задаче, когда и с каким итоговым статусом выполнялась — реализуется как отдельный отчётный view/эндпоинт поверх `node_logs`, без создания дублирующей таблицы.

## 14. Статусы задачи и переходы

### 14.1 Диаграмма статусов

```
new ──► queued ──► in_progress ──► done
                       │  ▲   │
                       │  │   ▼
                       │  │  plan_review ──► in_progress (после решения по плану)
                       │  │
                       ▼  │
                 awaiting_input ──► in_progress (после ответа/выбора)
                       │
                       ▼
                 rebase_conflict ──► in_progress (после автообработки)
                       │
                       ▼
                    failed ──► in_progress (кнопка "Перезапустить с текущей ноды")
```

### 14.2 Описание статусов

| Статус | Значение | Доступные действия пользователя |
|---|---|---|
| `new` | Задача создана, не запущена | Выполнить, редактировать поля и состав включённых нод |
| `queued` | Поставлена в очередь Celery | Отменить постановку |
| `in_progress` | Активно выполняется | Приостановить, остановить, запустить промт из библиотеки, отправить свободный промт |
| `plan_review` | Нода `plan_prompt` завершила формирование плана, ожидается решение пользователя | Выбор варианта через универсальный виджет выбора |
| `awaiting_input` | Ожидает ответа пользователя на текущей ноде (с вариантами выбора или свободным текстом) | Ввести ответ или выбрать вариант |
| `rebase_conflict` | Требуется разрешение конфликта при ребейзе на обновлённую базовую ветку | Автоматическая обработка, отображение прогресса |
| `failed` | Нода исчерпала попытки retry | Перезапустить с текущей ноды (с возможностью донастройки ещё не пройденных нод), очистить контекст, посмотреть трейс |
| `done` | Пайплайн выполнен полностью, изменения запушены | Очистить директорию репозиториев, дублировать задачу |

### 14.3 Требования к обработке переходов

- Переход в `plan_review` или `awaiting_input` обязан немедленно вызывать: обновление статуса в БД, WebSocket-событие для подключённых клиентов, push-уведомление подписанным пользователям, визуальную подсветку задачи на дашборде.
- Очистка рабочей директории репозиториев доступна пользователю только вручную, кнопкой в интерфейсе, и только когда статус задачи терминальный (`done` или `failed`). Автоматическое удаление директории запрещено.
- Директория пользовательских файлов задачи не подлежит удалению при очистке репозиториев — это раздельные директории с разным жизненным циклом.

### 15.2 Страница задачи — детальные требования

Страница обязана разделять на две независимые визуальные зоны, не влияющие на высоту друг друга: зону статичных данных задачи (поля, репозитории, переменные) и зону диалога (лента ввода/вывода сессии).

**Шапка задачи** дополнительно содержит:
- Кнопку **«🔗 Переподключить удалённую сессию»** — присутствует всегда, независимо от статуса моста, с визуальным акцентом при `remote_control_status = disconnected`.

**Вкладка «Обзор»** дополнительно содержит:
- Блок «Автозапуск»: переключатель `auto_start_enabled` и поле выбора даты/времени `scheduled_start_at`, поле неактивно, пока переключатель выключен.
- При выборе пайплайна — раскрывающийся список его нод в порядке выполнения, каждая строка с чекбоксом включения (по умолчанию включены все), редактируется только пока задача в статусе `new`; после `failed` чекбоксы доступны только для нод после точки последнего сбоя, остальные отображаются как заблокированные с пояснением «уже выполнено». При попытке отключить ноду, вывод которой используется последующей активной нодой — предупреждение с указанием конкретной зависимой ноды.
- Переключатель `auto_accept_plan` («Принять план и продолжить в auto режиме») — доступен как до запуска, так и во время выполнения задачи; учитывается в момент, когда очередная нода `plan_prompt` завершает формирование плана.
- Блок «Системные промты задачи»: таблица добавленных из библиотеки промтов (название, кнопка ▶/■, время последнего запуска, статус, включая `queued`), кнопка «+ Добавить промт из библиотеки».

**Вкладка «Выполнение»** дополнительно содержит:
- Свободное текстовое поле параметризованного промта, отдельное от поля ответа на `awaiting_input`/`plan_review` — визуально разграничены.
- Универсальный виджет выбора (раздел 9.6): при переходе в `plan_review` или в `awaiting_input` с непустыми вариантами — рядом с полем ввода отображается набор кнопок вместо (или в дополнение к) текстового поля. Для `plan_review` дополнительно отображается выделенный блок с полным текстом плана над виджетом выбора.
- Индикатор «В очереди» рядом с полем свободного ввода и в таблице системных промтов — когда запрос помещён в `task_manual_request_queue`.

**Требования к чат-ленте (вкладка «Выполнение»):**
- Реплики отображаются в хронологическом порядке, визуально различая: сообщения пользователя, ответы LLM, вывод скрипт-нод, блоки плана.
- Каждый блок вывода по умолчанию свёрнут до короткого превью с возможностью разворачивания по клику — полный текст не должен автоматически растягивать страницу.
- Поле ввода ответа зафиксировано (sticky) в нижней части чат-панели независимо от прокрутки ленты, активно только при статусе `awaiting_input`/`plan_review`, либо всегда — для свободного поля ввода (раздел 8).
- Предусмотрена возможность разворачивания всей чат-ленты в полноэкранный режим просмотра.
- Ответ, полученный со стороны сессии в процессе генерации, отображается потоково (по мере поступления от SDK), а не единым блоком после завершения.
- Каждая нода на вкладке «Выполнение» имеет отдельную кнопку открытия полного вывода именно этой ноды (в боковой панели или отдельном оверлее), независимо от общей чат-ленты — с возможностью копирования и скачивания текста.
- Сообщения, отправленные через `claude.ai/code`, помечены соответствующей меткой источника.

Интерфейс обязан корректно отображаться и оставаться полностью функциональным в диапазоне ширины экрана от 375px (мобильные устройства) до 2560px (широкие мониторы).

### 15.4 Конструктор пайплайна и редактор библиотеки промтов — требования к форме ноды

Общая форма для обоих контекстов (создание ноды пайплайна и создание системного промта библиотеки) — различие в наборе доступных полей:

| Поле формы | Пайплайн | Библиотека |
|---|---|---|
| Название, описание | Да | Да (описание обязательно) |
| Тип ноды | Все 5 типов (`plain_prompt`, `slash_command`, `script`, `clear_context`, `plan_prompt`) | Только `plain_prompt`, `slash_command`, `script` |
| Порядок выполнения | Да | Нет (не применимо) |
| Пропуск по умолчанию (`is_skipped`) | Да | Нет |
| Политика retry (`max_retries`, задержка) | Да (не применяется к `plan_prompt` при отказе пользователя от плана) | Нет (пользователь управляет запуском вручную) |
| Поле «Гайд» (URL Confluence) | Да | Да |
| Таймаут (`timeout_seconds`) | Да | Да (применяется идентично пайплайну) |

Подсказка по доступным переменным для вставки в текстовое поле промта не включает `{{node.*}}`, если форма открыта в контексте библиотеки или свободного ввода. Для поля `command_invocation` (слэш-команда) подсказка по переменным не отображается вовсе — явно указано текстом «команда передаётся в сессию без изменений». При выборе типа `plan_prompt` форма дополнительно отображает информационную подсказку о том, что нода доступна только внутри пайплайна и не может быть сохранена как элемент библиотеки.

## 16. Периодические фоновые задачи

### 16.1 Механизм хранения расписания

Расписание периодических задач хранится в таблице `periodic_tasks`, а не хардкодится в коде. Планировщик Celery Beat должен использовать динамический источник расписания, читающий записи из этой таблицы и подхватывающий изменения без перезапуска процесса Celery Beat. Изменение расписания выполняется через административный интерфейс, без деплоя.

### 16.2 Перечень задач для первичного заполнения (seed)

| Название | Описание | Период по умолчанию |
|---|---|---|
| `check_scheduled_tasks_for_autostart` | Находит задачи со статусом `new`, `auto_start_enabled = true` и наступившим `scheduled_start_at`, инициирует их запуск | Каждые 5 минут |
| `check_llm_account_limits` | Опрашивает статус каждого активного LLM-аккаунта, обновляет `llm_accounts.status` | Каждые 5 минут |
| `cleanup_stale_worktrees` | Находит задачи в терминальном статусе старше N дней с неочищенной директорией, отправляет напоминание | Раз в сутки |
| `detect_awaiting_input_timeout` | Повторно уведомляет автора задачи, находящейся в `awaiting_input`/`plan_review` дольше порога | Каждый час |
| `sync_gitlab_merge_status` | Обновляет `task_repositories.merge_status` по данным GitLab API | Каждые 10 минут |
| `rebase_child_branches_on_parent_merge` | Инициирует ребейз дочерних веток при обнаружении смерджа родительской | Каждые 10 минут |
| `purge_orphaned_docker_containers` | Останавливает зависшие контейнеры скрипт-нод, пережившие таймаут | Каждые 15 минут |
| `purge_orphaned_playwright_processes` | Находит и завершает осиротевшие процессы браузера (Playwright и аналогичные MCP-инструменты с состоянием), пережившие принудительное прерывание родительской задачи; при режиме `per_task_data_dir` дополнительно снимает файловую блокировку профиля, если она осталась висеть после завершения процесса | Каждые 15 минут |
| `rotate_task_logs` | Архивирует записи `node_logs` для задач старше установленного порога давности | Раз в неделю |
| `revoke_stale_sshfs_keys` | Помечает неиспользуемые SSH-ключи sshfs-доступа для ротации | Раз в сутки |
| `health_check_mcp_servers` | Обновляет `mcp_servers.is_healthy` | Каждые 10 минут |
| `deprovision_inactive_users` | Блокирует `os_username` для email, удалённых из `allowed_emails` | Раз в сутки |
| `check_remote_control_bridges` | Проверяет и восстанавливает мост `/remote-control` для активных задач | Каждые 2 минуты |
| `expire_stale_manual_queue_requests` | Отменяет запросы в `task_manual_request_queue`, зависшие в статусе `queued` дольше разумного порога, переводит в `cancelled` с уведомлением пользователя | Каждые 15 минут |

### 16.3 Требования к выполнению

- Каждый запуск периодической задачи обязан обновлять `last_run_at`, `last_run_status`, вычислять `next_run_at`.
- Ошибка выполнения периодической задачи не должна приводить к падению процесса Celery Beat — исключения перехватываются и логируются в `app_logs`.
- Каждая периодическая задача должна поддерживать принудительный запуск вне расписания (используется кнопкой «Запустить сейчас» в административном интерфейсе).

## 17. Логирование, обработка ошибок и идемпотентность («работа из коробки»)

### 17.1 Принцип

Технологический стек и архитектура обязаны сами обеспечивать надёжность типовых сценариев — повторные запуски Celery-задач, сетевые сбои, параллельные обращения — не полагаясь на аккуратность каждого отдельного разработчика при написании конкретного модуля.

### 17.2 Логирование

- Все backend-компоненты используют единую конфигурацию структурированного логирования (`structlog` или эквивалент), формат — JSON, с обязательными полями: `timestamp`, `level`, `source`, `task_id` (если применимо), `message`.
- Критичные события (необработанные исключения, сбои периодических задач, ошибки взаимодействия с Claude Agent SDK, ошибки git-операций) дополнительно сохраняются в таблицу `app_logs`.
- Обычные (не критичные) логи допустимо выводить только в stdout контейнера — ротацию и хранение обеспечивает стандартный драйвер логирования Docker.
- В административном разделе «Мониторинг» обязателен просмотр `app_logs` с фильтрами по уровню, источнику, задаче и диапазону дат.

### 17.3 Обработка исключений

- На уровне backend обязателен единый middleware/обработчик необработанных исключений, приводящий любую ошибку к стандартизированному формату ответа API (код ошибки, человекочитаемое сообщение, `request_id` для сопоставления с записью в `app_logs`).
- Каждая Celery-задача оборачивается в блок перехвата исключений, гарантирующий: запись ошибки в `app_logs`, корректное обновление статуса связанной задачи/ноды (не оставлять запись в статусе `running` при падении процесса), применение соответствующей retry-политики, если применимо.
- Ошибки взаимодействия с внешними системами (GitLab API, MCP-серверы, Claude Agent SDK) обязаны различать временные сбои (подлежат retry) и постоянные сбои (требуют немедленного уведомления без бесполезных повторов).

### 17.4 Идемпотентность

- Каждая Celery-задача, изменяющая состояние, обязана перед выполнением проверять текущее состояние сущности в БД и корректно завершаться без побочных эффектов, если целевое состояние уже достигнуто.
- Для операций, критичных к повторному выполнению (пуш в Git, отправка push-уведомления, обработка очереди ручных запросов), используется распределённая блокировка на основе Redis (`SET NX` с TTL) по ключу, включающему идентификатор задачи и тип операции.
- Все статусные переходы задачи выполняются через явную проверку текущего статуса перед изменением (compare-and-swap на уровне транзакции БД).

### 17.5 Логические связки, обязательные к проверке при реализации

- Переход задачи в `done` невозможен, пока хотя бы одна включённая нода пайплайна не имеет записи в `node_logs` со статусом `success`.
- Переход задачи в `failed` обязан сохранять точный `order_index` сбоя в `tasks.last_failed_order_index`.
- Очистка контекста сессии обязана быть невозможна, пока есть хотя бы одна запись `node_logs` со статусом `running` или `awaiting_decision`.
- Обработка очереди `task_manual_request_queue` обязана быть защищена той же распределённой блокировкой, что и обращения к сессии.
- Сохранение MCP-сервера с `has_stateful_resource = true` без указанного `isolation_mode` — запрещено.

## 18. Уведомления и real-time обновления

### 18.1 Каналы доставки

| Канал | Назначение | Технология |
|---|---|---|

### 18.2 События, требующие обязательного уведомления

- Переход задачи в `awaiting_input` или `plan_review`.
- Переход задачи в `failed`.
- Обнаружение разрыва моста `/remote-control` без успешного автоматического восстановления.
- Неудачная попытка автоматического запуска по расписанию.
- Завершение задачи со статусом `done`.
- Завершение выполнения системного промта библиотеки со статусом `failed`.
- Отмена запроса из очереди по истечении срока ожидания.

### 18.3 Требования к отображению

- Задачи, ожидающие решения (`awaiting_input`, `plan_review`), визуально выделяются в списке задач на дашборде постоянным маркером.
- Счётчик таких задач отображается в постоянной навигации, видимой с любого экрана.

## 19. Управление доступом и безопасность

### 19.1 Аутентификация

- Единственный метод входа — Google OAuth.
- Регистрация нового пользователя разрешена только для email, присутствующего в таблице `allowed_emails`.
- Первый пользователь, зарегистрировавшийся в системе, автоматически получает роль `admin`.

### 19.2 Ролевая модель

| Роль | Права |
|---|---|
| `user` | Собственные задачи, пайплайны, библиотека промтов, шаблоны; просмотр собственного профиля |
| `admin` | Все права `user` + `allowed_emails`, назначение ролей, системные настройки, MCP-серверы, мониторинг, расписание периодических задач |

### 19.3 Изоляция выполнения скрипт-нод

- Контейнер скрипт-ноды не должен иметь доступа к сети без исключений.
- Контейнеру монтируется исключительно директория репозиториев текущей задачи в режиме read-write.
- Ограничение ресурсов контейнера (память, CPU) обязательно.

### 19.4 Хранение секретов

- Deploy-ключи репозиториев, значения переменных окружения, помеченные как секретные, и данные авторизации MCP-серверов хранятся в базе данных в зашифрованном виде.
- Ключ шифрования хранится вне базы данных.
- Отображение секретных значений в интерфейсе по умолчанию скрыто, раскрывается по явному действию пользователя.

### 19.5 Множественные LLM-аккаунты

- Параллельное выполнение задач под одним и тем же Anthropic-аккаунтом разрешено и является ожидаемым штатным режимом работы системы, а не исключением — что прямо мотивирует обязательность требований раздела 10 к изоляции MCP-инструментов с состоянием.
- Каждый LLM-аккаунт использует изолированную конфигурационную директорию (`CLAUDE_CONFIG_DIR`), не пересекающуюся с директориями других аккаунтов.

## 20. Развёртывание

### 20.1 Требования к простоте установки и переносимости

Развёртывание на VDS обязано требовать минимум ручных действий администратора и не предполагать ручной настройки зависимостей, помимо базовой установки Docker. Смена сервера должна сводиться к переносу файла `.env` и volume-данных, без изменений кода или повторной ручной настройки окружения.

### 20.2 Детальная последовательность развёртывания технологического стека

1. Проверка и установка Docker + Docker Compose plugin на хосте, если отсутствуют.
2. Клонирование репозитория проекта в целевую директорию на хосте (например, `/opt/tracker`).
3. Генерация `.env` из `.env.example` — все секреты генерируются автоматически через `openssl rand`.
4. Интерактивный запрос только критичных значений: домен, email для выпуска TLS-сертификата, Google OAuth Client ID/Secret.
5. Сборка Docker-образов: backend, frontend, `tracker-runner-python`, `tracker-runner-bash`.
6. Поднятие инфраструктурных сервисов первыми: PostgreSQL и Redis — с проверкой готовности (healthcheck) перед стартом зависимых сервисов.
7. Применение миграций базы данных — автоматически в entrypoint backend-контейнера при старте, идемпотентно.
8. Заполнение начальных данных (seed) — дефолтный список `periodic_tasks`, дефолтные Docker-образы раннеров.
9. Старт прикладных сервисов: backend API, Celery worker, Celery Beat, frontend, reverse-proxy — с зависимостями через `depends_on` с условием healthcheck.
10. Автоматическое получение TLS-сертификата reverse-proxy (Caddy) по домену, указанному на шаге 4.
11. Первый вход администратора через браузер, Google OAuth, автоматическое назначение роли `admin` первому пользователю.

### 20.3 Структура репозитория для развёртывания

| Путь | Назначение |
|---|---|
| `docker-compose.yml` | Базовое описание всех сервисов |
| `docker-compose.prod.yml` | Override для production (реплики воркеров, лимиты ресурсов, restart-политики) |
| `.env.example` | Шаблон переменных окружения с комментариями по каждому значению |
| `deploy/install.sh` | Единственный скрипт, запускаемый вручную администратором |
| `deploy/caddy` | Конфигурация reverse-proxy |
| `backend/` | Код backend, Dockerfile |
| `frontend/` | Код frontend, Dockerfile сборки статики |
| `runners/` | Dockerfile-описания образов для script-нод |
| `alembic/` | Миграции базы данных |

### 20.4 Требования к персистентности и переносимости между серверами

- Данные PostgreSQL, репозитории задач (включая директории профилей MCP-инструментов, раздел 10.3) и пользовательские файлы задач — в именованных Docker-volumes.
- Перенос на новый сервер: снятие бэкапа PostgreSQL и архивирование volume-директорий → перенос архивов и файла `.env` → выполнение `deploy/install.sh` с флагом восстановления → восстановление дампа БД и распаковка архивов. Процедура документируется в `docs/migration.md`.
- Встроенный сервис резервного копирования PostgreSQL по расписанию, настраиваемый через `.env`.

### 20.5 Требования к привилегированным операциям

- Управление системными Linux-пользователями — изолированный `user-provisioner`-сервис с ограниченными привилегиями.
- Доступ Celery worker к Docker-демону хоста — через монтирование `docker.sock`, задокументированный компромисс, не требующий `--privileged`-режима для самого worker-контейнера.

## 21. Требования к тестированию

### 21.1 Обязательное покрытие

| Уровень | Что покрывается |
|---|---|
| Unit-тесты | Рендеринг шаблонных переменных (включая неприменение к слэш-командам), логика переходов статусов, retry, шифрование секретов, идемпотентность, валидация MCP-серверов с `has_stateful_resource` |
| Integration-тесты | Взаимодействие с Claude Agent SDK (мокирование, включая `canUseTool`-callback для `ExitPlanMode`), выполнение скрипт-нод, работа с БД, механизм автозапуска, обработка очереди ручных запросов, рендеринг `isolation_path_template` с реальным путём задачи |
| E2E-тесты | Полный цикл: создание задачи → отключение части нод → автозапуск по расписанию → прохождение включённых нод, включая `plan_prompt` → запуск и остановка системного промта из библиотеки → отправка свободного промта → достижение статуса `done` |

### 21.2 Обязательные сценарии проверки

1. Пайплайн из всех пяти типов нод, включая `plan_prompt`, с передачей `{{node.script_output}}` и `{{node.plan_text}}` в последующие ноды, с частью нод отключённых на уровне задачи.
2. Задача с `auto_start_enabled = true` и `scheduled_start_at` в прошлом — проверка однократного срабатывания автозапуска.
3. Нода `plan_prompt` с `auto_accept_plan = false` — проверка перехода в `plan_review`, отображения виджета выбора с тремя вариантами, обработки решения «Доработать план» без расхода `max_retries`.
4. Нода `plan_prompt` с `auto_accept_plan = true` — проверка автоматического продолжения без остановки задачи.
5. Запуск системного промта библиотеки в момент, когда сессия занята нодой пайплайна — проверка постановки в `task_manual_request_queue`, корректной FIFO-обработки по освобождении сессии.
6. Многократный запуск одного системного промта, включая принудительную остановку кнопкой «■».
7. Отправка свободного параметризованного промта с проверкой корректного рендеринга переменных и записи с `trigger_type = freeform_manual`.
8. Исчерпание попыток retry для скрипт-ноды пайплайна с переходом в `failed`, фиксацией `last_failed_order_index`, последующим «Перезапустить с текущей ноды» с проверкой, что только ноды после точки сбоя доступны для изменения `is_enabled`.
9. Превышение `timeout_seconds` для запуска из библиотеки — проверка автоматического перехода в `failed` без последующего retry.
10. Сценарий смерджа родительской ветки с проверкой автоматического ребейза дочерней ветки.
11. Ручное нажатие кнопки переподключения удалённой сессии при статусе `remote_control_status = disconnected` с проверкой перехода в `connected`.
12. Две параллельно выполняющиеся задачи, обе используют MCP-сервер с `has_stateful_resource = true` — проверка, что обе задачи успешно завершают обращение к инструменту без ошибки блокировки профиля, независимо от выбранного `isolation_mode`.
13. Принудительная остановка задачи в момент активного обращения к Playwright-инструменту — проверка, что периодическая задача `purge_orphaned_playwright_processes` находит и завершает осиротевший процесс, а повторный запуск той же задачи после остановки не получает ошибку блокировки профиля.

### 21.3 Требования к качеству кода

- Минимальный порог покрытия тестами бизнес-логики (`services/`) — не ниже 85%.
- Все Celery-задачи обязаны быть идемпотентными — повторный запуск при сбое не должен приводить к дублированию побочных эффектов.

## 22. Ограничения и явные допущения (для избежания неоднозначностей реализации)

- Очистка рабочей директории репозиториев задачи выполняется только вручную, только в терминальном статусе задачи — автоматическое удаление любого вида запрещено.
- Контекст сессии Claude Code сохраняется по умолчанию между всеми обращениями к ней (ноды пайплайна, системные промты, свободные промты) и не сбрасывается автоматически ни при retry, ни при переходе между нодами — единственный способ сброса: явная нода `clear_context` в пайплайне или ручная кнопка на странице задачи, и только при отсутствии активно выполняющихся/ожидающих решения обращений.
- Слэш-команды (текст, начинающийся с `/`) никогда не проходят через шаблонизатор проекта — правило действует одинаково в пайплайне, библиотеке и свободном вводе.
- Обращения к одной сессии Claude Code строго последовательны; параллельные ручные запросы обслуживаются очередью FIFO, а не параллельным выполнением.
- Отключение ноды пайплайна на уровне конкретной задачи не изменяет сам пайплайн-шаблон и не создаёт запись в истории выполнения для этой ноды.
- После перехода задачи в `failed` донастройка состава включённых нод разрешена только для нод, ещё не начинавших выполнение в данном прогоне — уже пройденные и упавшая нода зафиксированы.
- Повторный запуск системного промта библиотеки не ограничен политикой retry — количество запусков полностью определяется пользователем; таймаут при этом применяется идентично пайплайну.
- Нода режима планирования (`plan_prompt`) доступна только в составе пайплайна; финальный уровень автономности после утверждения плана определяется выбором пользователя в момент принятия конкретного плана, а не заранее фиксированной конфигурацией ноды.
- Механизм программного восстановления моста `/remote-control` для сессии, управляемой через `ClaudeSDKClient`, требует технической верификации на раннем этапе реализации — пользовательский сценарий (кнопка, статус) фиксирован независимо от результата этой верификации.
- **MCP-серверы, управляющие ресурсом с ограничением на единовременное использование (браузерные профили и аналогичное), не могут быть сконфигурированы с общим для всех задач persistent-профилем — это запрещено конфигурацией системы, а не оставлено на усмотрение администратора при настройке конкретного сервера.** Единственно допустимые режимы — эфемерный изолированный профиль на каждый запуск либо профиль, физически привязанный к директории конкретной задачи.
- Автоматический запуск по расписанию гарантированно обнаруживает наступление `scheduled_start_at` не чаще, чем раз в 5 минут; для более точного попадания во время старта интервал должен быть уменьшен через таблицу `periodic_tasks` на этапе настройки конкретного инстанса.
- Оба канала ввода в сессию (`claude.ai/code` и любое поле трекера) работают без взаимной блокировки; ответственность за отсутствие дублирующей отправки одного и того же сообщения лежит на пользователе.
- Backend не выполняет самостоятельный доступ к содержимому страниц Confluence, указанных в поле «Гайд» — это зона ответственности LLM через MCP.
- Параллельное выполнение нескольких задач под одним LLM-аккаунтом разрешено явно и является ожидаемым штатным режимом работы системы.
- Скрипт-ноды выполняются без доступа к сети без исключений, независимо от того, являются ли они частью пайплайна или библиотеки системных промтов.
