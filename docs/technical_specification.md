## 1. Назначение и общая концепция

### 1.1 Что такое продукт

AI-трекер задач — веб-приложение для управления автоматизированными задачами разработки, которые выполняются автономным AI-агентом (Claude Code) через программное управление сессиями. Пользователь создаёт задачу, привязывает к ней один или несколько Git-репозиториев, выбирает пайплайн (последовательность шагов-нод) и запускает выполнение — вручную или по расписанию. Каждая нода пайплайна — это промт, слэш-команда, изолированный скрипт, служебная очистка контекста сессии, либо нода режима планирования, формирующая план реализации перед началом активных изменений. Помимо пайплайна, задача располагает собственной библиотекой параметризированных промтов, выполняемых многократно и в произвольный момент.

### 1.2 Ключевые пользовательские сценарии

1. Пользователь создаёт задачу, указывает репозитории (с ролями read-only/read-write), выбирает пайплайн и один из своих LLM-аккаунтов. LLM-аккаунт нужен, только если в пайплайне есть ноды, которые выполняет LLM: задача из одних скриптов работает без него. Форму задачи можно заполнить из Jira по ключу (раздел 15.6): код, название, описание и ссылка берутся из задачи Jira, вложения копируются в артефакты.
2. При выборе пайплайна пользователь видит список его нод и может отключить любые ноды именно для этой задачи, не изменяя переиспользуемый пайплайн-шаблон, отметить ноды, после которых задача должна остановиться, чтобы пообщаться с агентом в диалоге, и вставить между нодами свои промты — только для этой задачи.
3. Пользователь либо запускает выполнение немедленно, либо назначает дату и время автоматического запуска.
4. Пайплайн последовательно выполняет включённые ноды; ответ или вывод предыдущей ноды подставляется в следующую через шаблонные переменные.
5. Если пайплайн содержит ноду режима планирования, выполнение приостанавливается по завершении формирования плана: если пользователь заранее включил автопринятие плана — выполнение продолжается автоматически; если нет — задача переходит в статус ожидания решения по плану, и пользователь выбирает дальнейшее действие через виджет выбора в интерфейсе.
6. Если LLM-агенту в любой другой момент требуется уточнение (в том числе с вариантами ответа) — задача переходит в статус ожидания ввода, пользователь отвечает через поле трекера или через виджет выбора.
7. В любой момент, независимо от состояния пайплайна, пользователь может выполнить произвольный системный промт из библиотеки задачи, остановить его, либо ввести собственный параметризированный промт в свободное текстовое поле. Если сессия занята выполнением ноды пайплайна — запрос ставится в очередь и выполняется автоматически, как только сессия освобождается.
8. Если нода пайплайна или системный промт обращается к браузеру через MCP-инструмент (например, Playwright), эта задача не конфликтует с любой другой параллельно выполняющейся задачей за общий браузерный профиль — у каждой задачи собственный изолированный профиль инструмента.
9. Если веб-мост к `claude.ai/code` (просмотр сессии) обрывается, пользователь нажимает кнопку переподключения на карточке задачи.
10. После завершения задачи изменения запушены в соответствующие ветки Git-репозиториев; результат пользователь проверяет, в том числе подключив файлы своих задач как диск по SFTP (раздел 19.6), а рабочая директория репозиториев вручную очищается пользователем после проверки результата. Файлы для агента пользователь загружает в артефакты задачи и забирает оттуда результаты, которые сохранил агент (раздел 14.3).
11. Администратор управляет списком разрешённых пользователей, шаблонами репозиториев, глобальными переменными окружения, библиотекой системных промтов, конфигурацией MCP-серверов и расписанием фоновых задач — всё через UI.

### 1.3 Технологический фундамент

- Управление сессиями Claude Code — исключительно через официальный **Claude Agent SDK для Python** (`claude-agent-sdk`), класс `ClaudeSDKClient`. Прямое управление CLI-процессом через псевдотерминал не используется.
- Каждая задача имеет ровно одну сессию Claude Code на весь свой жизненный цикл. Контекст сессии сохраняется между всеми нодами пайплайна, всеми запусками системных промтов и всеми свободными промтами, не очищается автоматически. Очистка происходит только по явному действию пользователя или ноде `clear_context`.
- Обращения к сессии всегда строго последовательны — сессия не принимает второй запрос, пока не завершён предыдущий (раздел 6).
- Каждая запущенная сессия доступна для просмотра через веб-интерфейс `claude.ai/code` (мост `/remote-control`); вмешательство в работу агента выполняется только через интерфейс трекера.
- MCP-инструменты, поддерживающие постоянное состояние выполнения (браузерные профили, файловые блокировки и аналогичные ресурсы с ограничением на единственного одновременного пользователя), обязаны конфигурироваться с изоляцией на уровне задачи — раздел 10.

## 2. Архитектура системы

### 2.1 Общая схема компонентов

| Компонент | Назначение |
|---|---|
| **Backend API** | REST/WebSocket API, бизнес-логика, оркестрация задач |
| **Frontend SPA** | Веб-интерфейс пользователя и администратора |
| **Celery Worker** | Периодические фоновые задачи (раздел 16), очередь `celery` |
| **Celery Worker сессий** | Сессии задач — Claude Code, скрипт-ноды, git-операции (раздел 6.1), своя очередь `sessions`: сессия занимает процесс воркера часами, включая паузу и ожидание решения, и не должна задерживать периодические задачи. Число процессов (`SESSION_WORKER_CONCURRENCY`) — верхняя граница одновременно выполняющихся задач, остальные ждут в `queued` |
| **Celery Beat** | Планировщик периодических фоновых задач; расписание читает из таблицы `periodic_tasks` (раздел 16.1) |
| **PostgreSQL** | Основное хранилище данных, включая логи и историю выполнения нод |
| **Redis** | Брокер сообщений Celery, кеш, распределённые блокировки, pub/sub для WebSocket |
| **Reverse Proxy (Caddy)** | Автоматический TLS, маршрутизация запросов |
| **Docker Runner-образы** | Изолированные окружения для script-нод (Python, Bash) |
| **Образ сессии `tracker-session`** | Окружение процесса Claude Code CLI: воркер сессий запускает его в одноразовом контейнере на время жизни процесса CLI (раздел 19.3). Содержит CLI той же версии, что и Claude Agent SDK воркера, и инструменты агента (git, Python, Node.js, ripgrep) |
| **SFTP-шлюз** | Доступ пользователей к файлам своих задач по SFTP (подключение как диска через sshfs и аналоги): вход по SSH-ключу из профиля трекера, без системных Linux-пользователей и привилегий на хосте (разделы 19.6, 20.5) |

### 2.2 Рекомендованный технологический стек

| Слой | Технология | Обоснование |
|---|---|---|
| Backend framework | FastAPI (async) | Совместим с асинхронным Claude Agent SDK; автогенерация OpenAPI-схемы |
| ORM и миграции | SQLAlchemy 2.x (async) + Alembic | Версионируемые, идемпотентные миграции |
| Фоновые задачи | Celery + Redis | Retry «из коробки», совместимость с динамическим расписанием через Celery Beat |
| База данных | PostgreSQL 15+ | `jsonb` для гибких полей, надёжные транзакции для критичных переходов статусов |
| Frontend | React 19 + Vite + TanStack Query + shadcn/ui | Меньше самописного кода синхронизации состояния с сервером |
| Real-time | WebSocket (нативный, через FastAPI) + Web Push | Транспорт поверх уже используемого Redis pub/sub |
| Логирование | `structlog` (структурированные JSON-логи) + запись критичных событий в PostgreSQL (`app_logs`) | Фильтрация в админ-панели без парсинга текстовых файлов |
| Контейнеризация | Docker + Docker Compose | Обязательное требование раздела 20 |

### 2.3 Принцип разделения backend/frontend

Backend и frontend — раздельные кодовые базы, взаимодействующие только через документированный HTTP/WebSocket API. Frontend не имеет прямого доступа к базе данных, файловой системе сервера или Docker. Все операции, требующие серверных привилегий (git-операции, запуск контейнеров, управление сессиями Claude Code), выполняются исключительно на backend-стороне.

### 2.4 Разделение ответственности backend-модулей

| Модуль | Ответственность |
|---|---|
| `api/` | HTTP-эндпоинты, валидация входных данных, сериализация ответов |
| `services/` | Бизнес-логика: оркестрация пайплайнов, работа с сессиями, git-операции |
| `db/` | ORM-модели, миграции |
| `clients/` | Обёртки над Claude Agent SDK, GitLab API, Jira REST API (раздел 15.6), MCP-серверами |
| `tasks/` | Celery-задачи (асинхронные и периодические) |
| `ws/` | WebSocket-обработчики для real-time уведомлений |
| `sftp_gateway/` | SFTP-шлюз: SSH-сервер, вход по ключу, виртуальная файловая система задач (правила доступа — в `services/`) |
| `app_logging/` | Единая точка конфигурации структурированного логирования и записи в `app_logs` (не `logging/`: пакет с этим именем перекрыл бы модуль `logging` стандартной библиотеки Python) |

#### Таблица `task_nodes` (снимок нод пайплайна для конкретной задачи)

При привязке пайплайна к задаче для каждой ноды создаётся запись-снимок, позволяющая отключать конкретные ноды именно для данной задачи, не затрагивая сам пайплайн как переиспользуемый шаблон.

| Поле | Тип | Описание |
|---|---|---|
| `id` | UUID | Первичный ключ |
| `task_id` | FK → tasks | |
| `node_id` | FK → nodes | Ссылка на ноду пайплайна-шаблона или на свою ноду задачи |
| `order_index` | integer | Копия порядка на момент привязки (защищает от смещения порядка при последующем редактировании шаблона); вставка своей ноды сдвигает порядок последующих нод снимка |
| `is_enabled` | boolean, default `true` | Пользовательское включение/отключение ноды именно для этой задачи |
| `pause_after` | boolean, default `false` | Пауза после ноды: после её успешного выполнения задача переходит в `paused` (раздел 13.1, 14.1); у ноды `clear_context` значение не действует |
| `created_at` | timestamp | |

Требование к редактируемости: пока задача в статусе `new` — редактируется свободно. После первого перехода из `new` редактирование запрещено, **за исключением** статуса `failed`: в этом состоянии разрешено редактировать `is_enabled` только для нод, ещё не приступавших к выполнению: с `order_index` строго больше `tasks.last_failed_order_index`, а также ноды на самой точке перезапуска, если по ней в текущем прогоне нет записи `node_logs` пайплайна (остановка на паузе после предыдущей ноды). Предшествующие ноды и сама упавшая нода недоступны для редактирования. Те же правила действуют для вставки, правки и удаления своих нод задачи (раздел 13.2). Требование не касается `pause_after`: это управление прогоном, а не состав нод, поле меняется в любом статусе (раздел 13.2).

### 3.2 Требования к целостности данных

- Удаление пайплайна, используемого хотя бы одной задачей, запрещено на уровне API — вместо удаления предлагается архивация. Пайплайн используется задачей, пока он к ней привязан (`tasks.pipeline_id`) и пока его ноды использует хотя бы одна задача (см. ниже про ноды): после «Вернуть в новые» и смены пайплайна прежний остаётся в истории `task_nodes`/`node_logs`.
- Архивный пайплайн и архивный промт библиотеки к задаче не привязываются: API отвечает 409. Уже привязанные к задаче остаются в ней и выполняются. При дублировании задачи (раздел 14.2) архивный пайплайн исходной задачи отклоняет дублирование (409), а архивные промты библиотеки в копию не переносятся.
- Удаление ноды-системного промта, привязанной хотя бы к одной задаче через `task_library_prompts`, запрещено — только архивация.
- Ноду, которую использует хотя бы одна задача (запись `task_library_prompts`, снимок `task_nodes`, история `node_logs` или запрос в `task_manual_request_queue`), удалить нельзя — API отвечает 409: промт библиотеки вместо удаления архивируется, ноде пайплайна включается «Пропуск по умолчанию» (`is_skipped`).
- Свою ноду задачи (раздел 13.1), по которой уже есть запись `node_logs`, удалить нельзя — API отвечает 409, её отключают. Ноду пайплайна из снимка задачи через API задачи нельзя ни удалить, ни изменить её текст — 409, её только отключают.
- LLM-аккаунт, выбранный хотя бы у одной задачи, удалить нельзя — API отвечает 409.
- MCP-сервер, подключённый хотя бы к одному шаблону (`template_mcp_servers`), удалить нельзя — API отвечает 409: сначала его отключают в шаблонах. Шаблон, назначенный репозиторию по умолчанию (`repositories.default_template_id`), удалить нельзя — 409; его собственные связи с MCP-серверами удаляются вместе с ним.
- Репозиторий, привязанный хотя бы к одной задаче, в том числе завершённой, удалить нельзя — API отвечает 409: привязка `task_repositories` (ветка, статус пуша и MR) — история задачи и удаляться вместе с репозиторием не должна. Пока задача активна (не `done`/`failed`), репозиторий нельзя и переименовать: имя — каталог клона, и следующий запуск ушёл бы в новый пустой клон.
- Все значения, помеченные как секретные, хранятся в БД в зашифрованном виде (симметричное шифрование с ключом из переменной окружения сервера, не в самой БД).
- При привязке пайплайна к задаче создание записей `task_nodes` обязано выполняться атомарно в одной транзакции вместе с изменением `tasks.pipeline_id` — частичное создание снимка недопустимо.
- Сохранение MCP-сервера с `has_stateful_resource = true` и `isolation_mode = none` (или `NULL`) запрещено на уровне валидации API — раздел 10.2.

## 4. Глобальный принцип: параметризованные промты и непараметризованные команды

Это сквозное правило, применяемое одинаково во всех частях системы — в нодах пайплайна (включая `plan_prompt`), в системных промтах библиотеки и в свободном пользовательском вводе.

| Категория ввода | Проходит через шаблонизатор `{{...}}` | Примеры |
|---|---|---|
| Обычный промт (`plain_prompt`, `plan_prompt`) | Да | `prompt_template` ноды пайплайна, текст системного промта библиотеки, текст в свободном поле ввода на странице задачи |
| Слэш-команда (`slash_command`, начинается с `/`) | **Нет** | `command_invocation` передаётся в сессию Claude Code буквально; аргументы команды (`$1`, `$2`, `$ARGUMENTS`) разворачивает сам Claude Code средствами файла команды в `.claude/commands/`, а не backend трекера |

**Практическое следствие:** если пользователю нужно передать в слэш-команду значение переменной задачи (например, код задачи), он обязан подставить это значение вручную при заполнении поля `command_invocation` на этапе создания ноды/промта — автоматическая подстановка `{{task.code}}` для слэш-команд не выполняется. Это ограничение фиксируется в подсказке интерфейса при выборе типа ноды «Слэш-команда», чтобы не создавать ложных ожиданий у пользователя.

### 5.1 Требования к рендерингу

- Рендеринг выполняется непосредственно перед отправкой в SDK или запуском контейнера — не заранее; для MCP-конфигурации с изоляцией (раздел 10) рендеринг выполняется перед стартом сессии задачи.
- Если переменная указана в шаблоне, но недоступна в контексте выполнения (например, `{{node.script_output}}` в первой ноде пайплайна) — сохранение пайплайна должно завершаться ошибкой валидации, а не рантайм-сбоем. Проверка выполняется при каждом изменении состава пайплайна — создании, изменении (в том числе порядка) и удалении любой его ноды — для всех нод пайплайна; если изменение лишает какую-либо ноду источника переменной, оно отклоняется (422) с именем этой ноды.
- Переменные `{{node.*}}` недоступны для вставки в контексте библиотеки промтов и свободного поля ввода (нет фиксированной позиции «предыдущей ноды»).
- Функция предпросмотра рендеринга обязательна для всех трёх мест ввода параметризованного текста: конструктор пайплайна, редактор системного промта библиотеки, свободное поле ввода на странице задачи. Предпросмотр в конструкторе пайплайна проверяет `{{node.*}}` по позиции ноды так же, как сохранение: доступны переменные нод, стоящих раньше неё, и `{{node.llm_output_last_n}}` — с параметром N сохранённой ноды. Тот же предпросмотр есть в диалоге своего промта задачи (раздел 13.1): если передана задача без пайплайна или нода — своя нода задачи, предыдущие ноды берутся из её снимка `task_nodes` (раньше позиции `order_index` из запроса, без самой редактируемой ноды). Предпросмотр с `scope = pipeline` проверяет переменные по позиции и тогда, когда передана задача, — после этого текст рендерится по её истории.
- Значения секретных переменных (`is_secret = true`) и всех переменных уровня задачи (их значение в интерфейсе скрыто, раздел 15.2) подставляются в текст, уходящий в сессию, но в предпросмотре и в `node_logs.rendered_prompt` показываются как `••••••` (раздел 19.4).

## 6. Управление сессиями Claude Code

### 6.1 Жизненный цикл сессии

- Сессия создаётся ровно один раз при первом запуске задачи (переход в статус `in_progress` из `new`/`queued`).
- Объект клиента сессии (`ClaudeSDKClient`) хранится как персистентная сущность в рамках выполнения Celery-задачи и переиспользуется всеми последующими нодами пайплайна, всеми запусками системных промтов и всеми свободными промтами до завершения задачи или явной команды очистки контекста.
- `session_id`, присваиваемый Claude Agent SDK, сохраняется в поле `tasks.session_id` сразу после создания сессии.
- Рабочая директория сессии — директория репозиториев задачи; каталог артефактов задачи (раздел 14.3) передаётся сессии как дополнительная разрешённая директория (`add_dirs`): агент читает загруженные пользователем файлы и сохраняет туда результаты.
- Процесс Claude Code CLI работает не в контейнере воркера, а в отдельном одноразовом контейнере сессии (раздел 19.3): воркер владеет `ClaudeSDKClient` и обменивается с CLI через stdin/stdout контейнера, поэтому callback разрешений, потоковый вывод, запись в БД и git-операции остаются в воркере. Контейнер живёт столько же, сколько процесс CLI, и пересоздаётся вместе с ним (переподключение моста, восстановление после падения CLI, очистка контекста, пересказ родителя).
- При повторном запуске задачи после статуса `failed` используется уже существующий `session_id` — сессия не пересоздаётся, если явно не выбрана очистка контекста.

### 6.2 Строгая последовательность обращений к сессии

Один объект `ClaudeSDKClient` не может параллельно обрабатывать два запроса. Любое обращение к сессии — выполнение ноды пайплайна, запуск системного промта библиотеки, отправка свободного промта, ответ на `awaiting_input`/`plan_review` — обязано проходить через единый внутрипроцессный семафор (mutex) на уровне Celery-задачи, обслуживающей конкретную сессию. Детали обработки конкурентных ручных запросов описаны в разделе 7.3.

### 6.3 Доступ к сессии через `claude.ai/code`

- При старте задачи, наряду с созданием сессии через SDK, инициируется мост `/remote-control`, делающий сессию доступной для просмотра через веб-интерфейс `claude.ai/code`.
- Вмешательство в работу агента — ответ на `awaiting_input`, выбор в `plan_review`, запуск системного промта, свободный промт — выполняется только через поля ввода трекера. Ввод через `claude.ai/code` не поддерживается: такие сообщения не попадают в чат-ленту трекера и в `node_logs`, а ответ агента на них не учитывается пайплайном. Технически запретить ввод на стороне `claude.ai/code` трекер не может — ограничение организационное и указано в интерфейсе рядом с кнопкой переподключения.
- **Важное техническое допущение, подлежащее верификации на этапе реализации:** команда `/remote-control` в реальном использовании может подразумевать интерактивное продолжение текущей CLI-сессии, а не исключительно программный вызов через готовый API. Перед проектированием кнопки переподключения (раздел 6.5) и автоматического мониторинга (раздел 6.6) обязателен отдельный технический этап проверки: обладает ли процесс, управляемый через `ClaudeSDKClient`, предсказуемым программным способом установления/восстановления моста, или это требует эмуляции интерактивного ввода команды в поток стандартного ввода дочернего процесса. Результат проверки может потребовать корректировки внутренней реализации разделов 6.5–6.6 без изменения пользовательского сценария (кнопка и статус в UI остаются, меняется только внутренний механизм вызова).

### 6.4 Хранение истории диалога

- Полная история диалога сессии физически хранится Claude Code в формате построчного JSON, путь строится на основе изолированной конфигурационной директории (`CLAUDE_CONFIG_DIR`), привязанной к конкретному `llm_accounts.claude_config_dir`.
- Реплики дополнительно дублируются в `node_logs` — во избежание потери данных при удалении файлов истории по истечении срока хранения Claude Code: ответ хода записывается по его завершении, а если ход прерван (остановка, таймаут, падение процесса CLI) — записывается полученная к этому моменту часть ответа.
- Перед каждым подключением к сессии воркер выставляет `cleanupPeriodDays` в `settings.json` конфигурационной директории аккаунта не меньше значения `CLAUDE_SESSION_RETENTION_DAYS` (по умолчанию 36500 дней — задачи в системе не удаляются); остальные ключи файла сохраняются, больший срок, заданный вручную, не уменьшается.
- Срок автоматического удаления истории сессий на сервере должен быть переопределён в конфигурации (`~/.claude/settings.json` соответствующего `CLAUDE_CONFIG_DIR`) на значение не менее срока хранения задач в системе.

### 6.5 Ручное переподключение моста `remote-control`

На карточке задачи присутствует кнопка **«🔗 Переподключить удалённую сессию»**, доступная, пока у задачи есть живая сессия Claude Code (статусы `in_progress`, `paused`, `plan_review`, `awaiting_input`, `rebase_conflict` и выбран LLM-аккаунт), независимо от текущего значения `remote_control_status`. Нажатие запускает новую попытку установить мост `/remote-control` для активной сессии задачи и обновляет статус в интерфейсе (`reconnecting`, затем `connected` или `disconnected`): воркер, владеющий сессией, между обращениями к ней перезапускает процесс CLI с продолжением той же сессии и флагом моста. Факт восстановления моста не гарантируется — SDK не даёт достоверного способа его проверить, поэтому статус отражает лишь успешный перезапуск процесса. Если у задачи нет активной сессии, кнопка сообщает об этом и ничего не меняет. Кнопка не заменяет автоматический мониторинг (раздел 6.6), а дополняет его — пользователь может переподключиться профилактически, даже когда автоматика ещё не зафиксировала разрыв. Кнопка визуально акцентируется (например, изменением цвета) при `remote_control_status = disconnected`.

### 6.6 Автоматический мониторинг состояния моста

- Периодическая задача `check_remote_control_bridges` (раздел 16) проверяет состояние моста для всех задач в статусах `in_progress`/`paused`/`awaiting_input`/`plan_review`/`rebase_conflict` — во всех, где воркер владеет сессией.
- Признак живой сессии — пульс воркера: пока воркер держит сессию, он обновляет ключ в Redis с ограниченным сроком жизни (ключ одновременно — блокировка владельца сессии, раздел 17.4). Нет пульса — процесс сессии считается потерянным; попытка восстановления — запрос воркеру на перезапуск процесса CLI (как у кнопки, раздел 6.5). Уведомление о разрыве отправляется один раз.
- При обнаружении разрыва выполняется до двух автоматических попыток восстановления с задержкой.
- Если автоматическое восстановление не удалось — поле `remote_control_status` устанавливается в `disconnected`, пользователю отправляется уведомление.
- Пульса нет и после исчерпания попыток — воркер, владевший сессией, потерян (перезапуск сервиса при обновлении, сбой процесса): задача переводится в `failed` так же, как при ошибке сессии (раздел 17.3) — незавершённые записи `node_logs` закрываются, `last_failed_order_index` указывает первую непройденную ноду, автор получает уведомление о сбое. После этого доступны «Перезапустить с текущей ноды» и «Вернуть в новые». Пульс проверяется у всех задач со статусом, в котором воркер владеет сессией, в том числе у задач без LLM-аккаунта (у них нет моста, но есть воркер).
- Статус моста отображается независимо от общего статуса задачи (задача может продолжать выполняться, даже если мост временно недоступен).

### 6.7 Саммари родительской задачи

Если у задачи включён `use_parent_summary` и указан `parent_task_id`, перед первым обращением к новой сессии задачи формируется пересказ истории родительской задачи. Пересказ составляет сессия самого родителя — по запросу в момент старта дочерней задачи:

- Если сессией родителя сейчас владеет его воркер (статусы `in_progress`, `paused`, `plan_review`, `awaiting_input`, `rebase_conflict`), запрос на пересказ ставится в очередь ручных запросов родителя (раздел 7.3), а дочерняя задача ждёт его выполнения. Ожидание не ограничено по времени; дочернюю задачу можно остановить кнопкой «Остановить». Если запрос отменён или родитель вышел из активных статусов до его выполнения, пересказ делается по следующему пункту.
- Если родитель свободен и у него есть сессия, пересказ выполняется в ответвлении (fork) его сессии: история родителя при этом не меняется, инструменты в этом ходе запрещены.
- Если сессии у родителя нет (не запускался, контекст очищен, история удалена), дочерняя задача стартует без саммари, а в её чат-ленте появляется пометка о причине.

Ход пересказа отображается в ленте родителя с пометкой «пересказ для дочерней задачи». Пересказ сохраняется отдельным артефактом (`task_parent_summaries`) и отправляется первым сообщением новой сессии дочерней задачи с пометкой «саммари родительской задачи». Повторный запуск дочерней задачи пересказ не запрашивает и не отправляет повторно. Пока пересказ для работающей дочерней задачи не готов, очистка директории репозиториев родителя запрещена: ответвление его сессии работает в этой директории.

## 7. Библиотека системных промтов

### 7.1 Концепция

Системный промт — нода с `pipeline_id = NULL`, хранящаяся как переиспользуемый элемент, доступный для добавления в любую задачу. В отличие от нод пайплайна, системные промты не выполняются автоматически и не имеют фиксированного порядка — пользователь запускает их вручную, когда считает нужным, произвольное количество раз, в любой последовательности.

### 7.2 Управление библиотекой

- Создание, редактирование и архивация системных промтов доступны через отдельный раздел «Библиотека промтов» — форма идентична форме создания ноды пайплайна (раздел 3.1, таблица `nodes`), за исключением полей `order_index` и `is_skipped`, которые для библиотечных промтов не имеют смысла.
- Системный промт может иметь тип `plain_prompt`, `slash_command` или `script`. Типы `clear_context` и `plan_prompt` для библиотеки бессмысленны (это разовые пайплайн-действия) и не должны предлагаться при создании библиотечного промта.

### 7.3 Использование промта в задаче и очередь при занятой сессии

- Пользователь добавляет промт из общей библиотеки в список задачи (создаётся запись `task_library_prompts`); один и тот же промт может быть добавлен к разным задачам одновременно.
- Список системных промтов задачи отображается списком строк, одинаковым на любой ширине экрана. Строка слева направо: кнопка **▶ Выполнить**, кнопка **■ Остановить**, название промта и под ним время последнего запуска (у промта, который ещё не запускался, время не показывается), справа — текущий статус (`не запускался`, `в очереди`, `выполняется`, `успех`, `ошибка`, `остановлен`). Кнопка ▶ недоступна, пока у задачи нет активной сессии (раздел 8.2).
- **Если сессия свободна** в момент нажатия «▶ Выполнить» — запрос выполняется немедленно, создаётся запись `node_logs` (`trigger_type = library_manual`).
- **Если сессия занята** выполнением ноды пайплайна или другим ручным запросом — запрос не отклоняется и не выполняется параллельно, а помещается в `task_manual_request_queue` со статусом `queued`; `task_library_prompts.last_run_status` для этого промта переводится в `queued`, что видно пользователю в таблице. То же правило действует для отправки свободного промта (раздел 8) — при занятой сессии текст сохраняется в очередь с `request_type = freeform_prompt`.
- Сразу по завершении текущего занимающего сессию обращения оркестратор обязан проверить очередь `task_manual_request_queue` и обработать самый старый по времени `queued`-запрос (`FIFO`) **прежде**, чем переходить к следующей ноде пайплайна — это обеспечивает предсказуемую очерёдность и не даёт ручным запросам пользователя «застревать» позади длинной цепочки автоматических нод.
- Пользователь может отменить ещё не обработанный запрос из очереди — статус меняется на `cancelled`, запрос не выполняется. Если других запросов этого промта в задаче не осталось, `task_library_prompts.last_run_status` становится `stopped` (то же — при отмене по таймауту ожидания, раздел 16.2).
- Кнопка **■ Остановить** активна как для `running`, так и для `queued` состояния (во втором случае эквивалентна отмене из очереди).
- Повторный запуск одного и того же системного промта возможен неограниченное количество раз — `max_retries` к запускам из библиотеки не применяется: пользователь сам управляет количеством и моментом запуска.

### 7.4 Таймаут выполнения библиотечных промтов

Поле `timeout_seconds` ноды применяется к запускам из библиотеки точно так же, как к нодам пайплайна: если выполнение (ожидание ответа LLM или завершения скрипта) превышает установленное время, оно принудительно прерывается, соответствующая запись `node_logs` автоматически переводится в статус `failed`, `task_library_prompts.last_run_status` обновляется до `failed`. Разница с пайплайном — только в отсутствии последующего автоматического retry: пользователь при необходимости запускает промт заново вручную кнопкой «▶ Выполнить».

### 7.5 Выполнение в общей сессии

Выполнение системного промта происходит в той же активной сессии Claude Code, что и выполнение пайплайна задачи — контекст общий, с учётом строгой последовательности обращений (раздел 6.2) и очереди (раздел 7.3).

## 8. Свободный параметризованный промт на странице задачи

### 8.1 Назначение

Отдельно от библиотеки системных промтов, на странице задачи должно быть доступно текстовое поле для одноразового ввода параметризованного промта без сохранения его как переиспользуемой сущности — для случаев, когда пользователю нужно быстро что-то спросить или попросить сессию сделать разовое действие.

### 8.2 Требования к реализации

- Поле поддерживает подстановку тех же переменных, что определены в разделе 5, кроме `{{node.*}}` (нет привязки к конкретной предыдущей ноде).
- Перед отправкой пользователь может просмотреть, как выглядит текст после подстановки переменных.
- При свободной сессии запрос выполняется немедленно, создаётся запись `node_logs` с `trigger_type = freeform_manual`, `node_id = NULL`, `triggered_by` — текущий пользователь.
- При занятой сессии запрос ставится в очередь (раздел 7.3), пользователь видит визуальный индикатор «В очереди» рядом с полем ввода вместо немедленного результата.
- Отправленный текст и последующий ответ отображаются в общей чат-ленте сессии на равных с остальными типами сообщений, с визуальной пометкой источника («отправлено вручную»).
- Данное поле не привязано к какому-либо статусу задачи (в отличие от поля ответа при `awaiting_input`) — доступно для отправки в любой момент, пока сессия активна.

## 9. Режим планирования (Plan Mode)

### 9.1 Концепция

Отдельный тип ноды `plan_prompt` переводит активную сессию в режим планирования Claude Agent SDK (`permission_mode = "plan"`) перед отправкой рендеренного промта. В этом режиме агент вправе исследовать репозиторий и код, но не может редактировать файлы или выполнять изменяющие команды — только сформировать план реализации. Завершение планирования агент сигнализирует служебным вызовом инструмента `ExitPlanMode`, содержащим текст сформированного плана.

### 9.2 Обработка завершения планирования

Backend перехватывает вызов `ExitPlanMode` через механизм разрешений SDK — тот же, что обслуживает универсальный виджет выбора (раздел 9.6), на инфраструктуре которого построены и варианты решения по плану (раздел 9.3), — и обрабатывает его по следующей логике:

1. **Если `tasks.auto_accept_plan = true`** (переключатель выставлен пользователем заранее, до или во время выполнения пайплайна, но до наступления момента завершения планирования) — backend автоматически подтверждает план, сохраняет его текст в `node_logs.pending_plan_text` соответствующей записи с итоговым статусом `success`, переключает `tasks.current_permission_mode` на выбранный по умолчанию рабочий режим, и пайплайн продолжает выполнение следующей ноды без остановки и без уведомления, кроме отметки в истории.
2. **Если `tasks.auto_accept_plan = false`** — задача переходит в статус `plan_review`, соответствующая запись `node_logs` получает статус `awaiting_decision`, поле `pending_plan_text` заполняется текстом плана, поле `pending_options` заполняется вариантами дальнейшего действия. Выполнение пайплайна приостанавливается до получения решения пользователя. Отправляется уведомление.

### 9.3 Варианты решения пользователя

Пользователю предлагается выбор через универсальный виджет выбора (см. отдельный раздел про механизм ниже в этом же разделе), включающий как минимум следующие варианты:

- **«Принять план и продолжить автоматически»** — эквивалентно ручному включению `auto_accept_plan` для дальнейшего выполнения оставшейся части пайплайна; после выбора этого варианта `current_permission_mode` переключается в `acceptEdits` или `bypassPermissions`.
- **«Принять план, подтверждать каждое действие»** — план принимается, `current_permission_mode` становится `default`: каждое действие агента, которое требует разрешения (команды shell, запись файлов и т. п.), ждёт решения пользователя «Разрешить»/«Запретить» в виджете выбора (раздел 9.6); задача на это время переходит в `awaiting_input`.
- **«Доработать план»** — эквивалентно возврату `deny` в SDK по вызову `ExitPlanMode`; пользователь получает возможность ввести дополнительный текст с пожеланиями к доработке (переиспользуется то же текстовое поле ввода, что и для ответа на `awaiting_input`), этот текст передаётся сессии как фидбек, режим планирования не завершается, задача возвращается в `in_progress` с ожиданием нового вызова `ExitPlanMode`.

Пользователь выбирает вариант непосредственно в интерфейсе задачи, рядом с окном ввода — аналогично тому, как выбор происходил бы в CLI.

Принятие плана — любым из двух вариантов «Принять…» или автоматически по `auto_accept_plan` (раздел 9.2) — завершает ноду `plan_prompt`: агент получает ответ «план принят, реализацию выполнит следующий запрос» и заканчивает текущий ход без изменений; до конца этого хода инструменты агента отклоняются (кроме `AskUserQuestion`), а запись `node_logs` ноды плана остаётся `success`. Реализацию выполняют следующие ноды пайплайна, текст принятого плана им доступен через `{{node.plan_text}}`.

### 9.4 Режим разрешений после утверждения плана

Конкретный `permission_mode`, устанавливаемый после утверждения плана, определяется выбором пользователя из предложенных вариантов (раздел 9.3), а не фиксированным значением в конфигурации ноды — уровень автономности дальнейшего выполнения осознанно выбирается пользователем в момент принятия конкретного плана, а не заранее на этапе конструирования пайплайна. Режим сохраняется в `tasks.current_permission_mode` в момент принятия, а живая сессия переключается из `plan` в этот режим сразу после завершения хода ноды плана — он действует со следующей ноды.

### 9.5 Ограничения ноды `plan_prompt`

- Доступна только внутри пайплайна (`pipeline_id` заполнен); как самостоятельный элемент библиотеки не существует (аналогично `clear_context`).
- Ссылка `{{node.plan_text}}` (раздел 5) доступна только в нодах, следующих за `plan_prompt`, и содержит финальный утверждённый текст плана.
- Ретрай применяется только к техническим сбоям вызова SDK (сетевые ошибки, таймаут ожидания ответа), но не к решению пользователя «Доработать план» — повторная доработка не считается неудачной попыткой и не расходует счётчик `max_retries`.

### 9.6 Универсальный виджет выбора — общий механизм для уточняющих вопросов агента

Механизм разрешений Claude Agent SDK вызывает единый программный callback перед выполнением любого проверяемого инструмента, включая как `ExitPlanMode` (описан выше), так и общий инструмент уточняющих вопросов с вариантами ответа (`AskUserQuestion`). Поскольку оба случая технически используют одну и ту же точку перехвата на стороне SDK, интерфейс трекера обязан обрабатывать их единым UI-механизмом, а не двумя изолированными реализациями:

- **Если `pending_options` заполнено** (агент предложил конкретные варианты ответа, включая случай завершения плана) — интерфейс отображает рядом с полем ввода набор кнопок по числу вариантов, с текстом из `pending_options[].label`. Выбор кнопки отправляет `pending_options[].id` как решение, дополнительное текстовое пояснение пользователь может ввести опционально.
- **Если `pending_options` пусто, но `pending_question` заполнен** — это обычный открытый уточняющий вопрос без вариантов; интерфейс отображает только текстовое поле ввода, без кнопок, что полностью соответствует стандартному поведению `awaiting_input`.
- Текст вопроса (`pending_question`) показывается всегда, в том числе над кнопками вариантов.
- **`AskUserQuestion`** приходит в формате SDK: список `questions`, у каждого вопроса — текст, варианты (`label`) и признак множественного выбора. Вопросы задаются пользователю по очереди в одной и той же записи `node_logs`; на каждый можно выбрать вариант (с необязательным комментарием) или ответить своим текстом. Сессии возвращаются ответы `answers` — «текст вопроса → выбранный вариант или свой текст». При множественном выборе пользователь выбирает один вариант или перечисляет несколько своим текстом.
- **Подтверждение действия** (режим `default`, раздел 9.3): вопрос «Агент хочет выполнить …» с описанием команды или файла и вариантами «Разрешить» и «Запретить»; комментарий к «Запретить» передаётся агенту.
- После ответа запись `node_logs` снова в статусе `running`; ответ сохраняется в `user_input_text` (для нескольких вопросов — строками «вопрос: ответ»).
- Статус `plan_review` является, с точки зрения UI-рендеринга, частным случаем описанного механизма: он всегда сопровождается непустым `pending_options` и дополнительно — заполненным `pending_plan_text`, который отображается как выделенный блок плана над виджетом выбора, а не просто как обычная реплика в чат-ленте.
- Callback разрешений SDK, получив вызов инструмента с вариантами, обязан асинхронно дождаться решения пользователя, не блокируя при этом остальную систему — реализуется как ожидание на объекте синхронизации (`asyncio.Event`/эквивалент), разрешаемом обработчиком API-эндпоинта приёма решения пользователя.
- Ответ пользователя, полученный через любой из двух каналов (кнопка выбора в трекере, текстовый ввод в трекере), обязан транслироваться в один и тот же внутренний метод завершения ожидания — независимо от канала, откуда пришло решение. Ответ через `claude.ai/code` не поддерживается (раздел 6.3).
- На время ожидания задача находится в статусе `plan_review` (план) или `awaiting_input` (вопрос) и после решения возвращается в статус, из которого ушла в ожидание, — `in_progress` или `paused` (вопрос может задать и ручной промт, выполняемый на паузе).

## 10. Изоляция MCP-инструментов с состоянием (Playwright и аналогичные)

### 10.1 Проблема

Ряд MCP-серверов управляет ресурсом, допускающим единовременное использование только одним процессом — типовой пример: Playwright MCP по умолчанию хранит состояние браузера (cookies, авторизацию) в общем persistent-профиле на диске, который физически может удерживать только один запущенный экземпляр браузера одновременно. При параллельном выполнении нескольких задач трекера, каждая из которых пытается воспользоваться таким MCP-сервером с общей конфигурацией, вторая и последующие задачи получают ошибку блокировки профиля/ресурса, а не параллельное выполнение. Поскольку архитектура трекера прямо предполагает параллельное выполнение множества задач (в том числе под одним LLM-аккаунтом — раздел 19.5), эта проблема гарантированно проявится в продукте при использовании таких MCP-серверов без специальной настройки, а не является гипотетическим краевым случаем.

### 10.2 Обязательное правило конфигурации

- Каждый MCP-сервер в таблице `mcp_servers` обязан быть явно помечен полем `has_stateful_resource`. Администратор проставляет это значение при добавлении сервера в систему (раздел 15.5); для Playwright и любого MCP-сервера, управляющего браузерным профилем, файловой блокировкой или аналогичным единолично используемым ресурсом, значение обязано быть `true`.
- Если `has_stateful_resource = true`, поле `isolation_mode` обязано быть заполнено одним из двух допустимых значений — сохранение записи с `isolation_mode = NULL`/`none` в этом случае запрещено на уровне валидации API (раздел 3.2), форма администратора обязана явно требовать выбор режима изоляции прежде, чем разрешить сохранение такого MCP-сервера.
- **Режим `isolated_flag`** — MCP-сервер запускается с параметром эфемерного профиля (для Playwright — флаг изоляции, создающий временный in-memory профиль на каждый запуск браузера, без сохранения состояния между запусками). Подходит, если задачам не требуется сохранять авторизацию/cookies между отдельными вызовами инструмента в рамках одной сессии.
- **Режим `per_task_data_dir`** — MCP-сервер запускается с явным путём к директории профиля, рендерящимся из `isolation_path_template` (раздел 3.1) с подстановкой `{{task.repos_path}}` (раздел 5) — то есть физический профиль браузера/ресурса помещается внутрь директории репозиториев конкретной задачи (например, `/data/repos/RR-XXXXX/.mcp-profiles/playwright/`), а не в общесистемную директорию. Подходит, если в рамках одной задачи требуется сохранять состояние браузера (например, авторизацию на тестовом стенде) между несколькими последовательными обращениями к инструменту.
- Выбор конкретного режима — ответственность администратора при настройке MCP-сервера, оба варианта гарантируют отсутствие конфликта между параллельно выполняющимися задачами, поскольку в обоих случаях у каждой задачи заведомо собственный, не пересекающийся с другими задачами ресурс.
- MCP-серверы подключаются к сессии по сети (`mcp_servers.url`), поэтому backend передаёт серверу режим изоляции и путь профиля задачи в HTTP-заголовке `X-Tracker-Isolation-Path` (`ephemeral` для `isolated_flag`, отрендеренный путь — для `per_task_data_dir`). Соблюдение этой изоляции на стороне конкретного MCP-сервера обеспечивает администратор, настраивающий сервер.
- Общий persistent-профиль без изоляции, используемый одновременно несколькими задачами, запрещён конфигурацией системы — это не рекомендация, а обязательное требование, реализуемое валидацией на уровне API создания/редактирования MCP-сервера.

### 10.3 Жизненный цикл профиля в режиме `per_task_data_dir`

- Директория профиля создаётся автоматически при первом обращении задачи к соответствующему MCP-серверу — явного шага провижининга при старте задачи не требуется.
- Директория профиля физически расположена внутри директории репозиториев задачи (`{{task.repos_path}}`, раздел 5), и поэтому удаляется автоматически при очистке рабочей директории репозиториев задачи (ручной кнопкой, только в терминальном статусе) — отдельная логика очистки профилей MCP не создаётся, это естественное следствие уже принятой структуры директорий.

### 10.4 Осиротевшие процессы браузера

Принудительное прерывание выполнения (таймаут ноды, остановка пользователем, retry, сбой оркестратора) в момент, когда MCP-инструмент удерживает открытый процесс браузера, может оставить процесс работающим в фоне после завершения родительской задачи — независимо от выбранного режима изоляции, поскольку сам факт принудительного прерывания родительского процесса не гарантирует корректного закрытия дочернего процесса браузера. Осиротевший процесс браузера в режиме `per_task_data_dir` дополнительно может держать файловую блокировку профиля, препятствуя следующему запуску той же задачи после перезапуска ноды. Обслуживается периодической задачей `purge_orphaned_playwright_processes` (раздел 16.2) по аналогии с уже существующей `purge_orphaned_docker_containers`. Процессы браузера работают на стороне сетевого MCP-сервера, которым backend не управляет, поэтому в текущей топологии задача только фиксирует запуск и является точкой расширения: поиск и завершение процессов появятся вместе с протоколом управления, который предоставит конкретный MCP-сервер.

### 10.5 Ответственность backend при подготовке сессии задачи

Перед стартом сессии задачи backend обязан сформировать итоговую конфигурацию всех MCP-серверов, доступных через шаблон репозитория задачи (`templates.mcp_server_ids`), подставив в `isolation_path_template` фактическое значение `{{task.repos_path}}` для конкретной задачи, и передать получившуюся конфигурацию при инициализации `ClaudeSDKClient`. Ссылка на общесистемный путь профиля без подстановки переменной задачи в этой конфигурации является ошибкой реализации и обязана отлавливаться на этапе integration-тестирования (раздел 21.1).

## 11. Типы нод и механика их выполнения

### 11.1 Общий принцип

Тип ноды определяет способ выполнения, но не создаёт отдельную сущность в БД — все типы хранятся в единой таблице `nodes` с полем `node_type` (раздел 3.1).

### 11.2 Тип «Обычный промт» (`plain_prompt`)

Рендерится `prompt_template`, результат отправляется в активную сессию через метод отправки сообщения Claude Agent SDK. Ответ считывается потоково, сохраняется в `node_logs.llm_output_text`.

### 11.3 Тип «Слэш-команда» (`slash_command`)

Команда должна существовать как файл в `.claude/commands/` одного из репозиториев задачи, скопированный туда на этапе подготовки репозитория из шаблона. Значение поля `command_invocation` отправляется в сессию буквально, без обработки шаблонизатором проекта.

### 11.4 Тип «Скрипт» (`script`)

Выполняется без обращения к LLM, в изолированном Docker-контейнере.

- Контейнер запускается без сетевого доступа, без исключений.
- Контейнеру монтируются только директория репозиториев текущей задачи и каталог её артефактов (раздел 14.3), оба в режиме read-write и по тем же путям, что в worker (`{{task.repos_path}}`, `{{task.artifacts_path}}`). Worker сам работает в контейнере, а контейнер скрипта создаёт демон хоста, поэтому worker по `docker inspect` своего контейнера определяет, что смонтировано в корень репозиториев и в корень артефактов: volume — каталог задачи монтируется его подпутём (`--mount type=volume,...,volume-subpath=<код задачи>`, Docker Engine 26+), каталог хоста — его подкаталогом. Имена volume нигде не задаются вручную.
- Переменные окружения передаются в контейнер явно: все переменные задачи в порядке раздела 5 (глобальные, затем `scope = repository` репозиториев задачи, затем уровень задачи) со значениями после расшифровки. Токен GitLab — системная настройка (раздел 15.5), а не переменная окружения, и в контейнер не попадает. Текст скрипта шаблонизатор не обрабатывает, поэтому пути задачи скрипт получает в окружении: `TASK_REPOS_PATH` (директория репозиториев, она же рабочая директория) и `TASK_ARTIFACTS_PATH` (каталог артефактов); переменные задачи с такими именами их не перекрывают. Ключи, не подходящие под имя переменной окружения `[A-Za-z_][A-Za-z0-9_]*`, не передаются. Один ключ в нескольких репозиториях задачи — ошибка запуска ноды, как и при подстановке в промт (раздел 5).
- Текст скрипта записывается во временный файл в служебной поддиректории репозиториев задачи перед запуском.
- Образ и интерпретатор определяются полем `script_language`, могут быть переопределены полем `docker_image`.
- `stdout` и код возврата сохраняются в `node_logs`, доступны следующим нодам через `{{node.script_output}}`.
- Превышение `timeout_seconds` прерывает выполнение и запускает логику retry.

### 11.5 Тип «Очистить контекст сессии» (`clear_context`)

Доступен только внутри пайплайна. При выполнении текущая сессия SDK корректно завершается, создаётся новая сессия, новый `session_id` записывается в `tasks.session_id`. Недоступна, если существует хотя бы одна запись `node_logs` со статусом `running`/`awaiting_decision`.

### 11.6 Тип «Режим планирования» (`plan_prompt`)

Подробно описан в разделе 9. Сессия временно переводится в `permission_mode = "plan"`, по завершении — либо автоматически, либо по решению пользователя переключается в рабочий режим.

### 11.7 Логика повторных попыток (retry)

Применяется только к нодам, выполняемым в рамках пайплайна (`trigger_type = pipeline`); не применяется к запускам из библиотеки и к решению «Доработать план».

- Количество попыток — `max_retries` (по умолчанию 3), задержка растёт экспоненциально от `retry_base_delay_seconds`.
- Для `script`-нод повторная попытка пересоздаёт контейнер с нуля.
- Для `plain_prompt`/`slash_command`/`plan_prompt`-нод повторная попытка переиспользует ту же активную сессию.
- После исчерпания всех попыток задача переходит в `failed`, поле `tasks.last_failed_order_index` фиксируется значением `order_index` упавшей ноды.

## 12. Автоматический запуск задачи по расписанию

### 12.1 Пользовательский сценарий

На вкладке «Обзор» доступны поле даты/времени автозапуска (`scheduled_start_at`) и переключатель «Запускать автоматически» (`auto_start_enabled`). Пока переключатель выключен, поле даты неактивно и игнорируется системой, даже если ранее было заполнено.

### 12.2 Механизм проверки

Периодическая задача `check_scheduled_tasks_for_autostart` выполняется каждые 5 минут:

1. Выбирает все задачи со статусом `new`, `auto_start_enabled = true` и `scheduled_start_at <= текущее время`.
2. Для каждой найденной задачи инициирует тот же процесс запуска, что и ручная кнопка «Выполнить».
3. Немедленно после успешной постановки в очередь статус задачи меняется с `new` на `queued` — это обеспечивает идемпотентность: повторный проход периодической задачи в течение того же окна не найдёт задачу повторно.

### 12.3 Требования к обработке ошибок

Если инициация запуска для конкретной задачи завершилась ошибкой, это не должно прерывать обработку остальных задач в той же пачке — ошибка логируется в `app_logs` с привязкой к `task_id`, задача остаётся в статусе `new` для повторной попытки на следующем цикле, пользователю отправляется уведомление о неудачной попытке автозапуска.

## 13. Выбор нод пайплайна для конкретной задачи и история их выполнения

### 13.1 Отключение нод на уровне задачи

При выборе пайплайна на странице задачи интерфейс отображает полный список нод выбранного пайплайна в порядке `order_index`, каждая — с чекбоксом, включённым по умолчанию. Снятие галочки создаёт или обновляет соответствующую запись `task_nodes.is_enabled = false`.

Пока задача в статусе `new`, пайплайн можно сменить: прежний снимок `task_nodes` заменяется снимком нового пайплайна в той же транзакции, вместе с `tasks.pipeline_id`. Нода попадает в снимок задачи не больше одного раза (уникальность `task_id` + `node_id`); одновременные привязки не складывают снимки. После запуска пайплайн меняется только через возврат задачи в `new` (раздел 14.1).

У каждой ноды задачи есть отметка «пауза после» (`task_nodes.pause_after`): после успешного выполнения такой ноды воркер сначала обрабатывает накопившиеся ручные запросы и команды, затем переводит задачу в `paused` так же, как по кнопке «Приостановить» (раздел 14.1), — сессия удерживается, ручные запросы на паузе выполняются сразу, «Продолжить» запускает следующую ноду, «Остановить» переводит задачу в `failed` с точкой перезапуска сразу за этой нодой (`last_failed_order_index` = её `order_index` + 1): перезапуск продолжит со следующей включённой ноды, а на точку перезапуска можно вставить свой промт (раздел 13.2). Если пауза по кнопке уже запрошена, задача встаёт на паузу один раз. Упавшая, остановленная или отключённая нода паузу не вызывает. У ноды `clear_context` отметка не действует — после неё пайплайн продолжается в новой сессии (раздел 11.5), интерфейс переключатель для неё не показывает. Отметка у последней ноды останавливает задачу до пуша и перехода в `done` (раздел 14.1).

Сразу после любой ноды снимка или в его начало можно вставить свой промт — промт (`plain_prompt`) или слэш-команду (`slash_command`), нужные только этой задаче (`nodes.task_id`, раздел 3.1). Название и текст обязательны; у слэш-команды текст хранится в `command_invocation` и не шаблонизируется (правило 2), у промта — в `prompt_template`. Пайплайн-шаблон не меняется: новая нода получает `order_index` сразу за выбранной (в начале — наименьший `order_index` снимка), у нод снимка с этим и бо́льшим `order_index` он увеличивается на 1; одновременные вставки упорядочены блокировкой строки задачи. Новая нода включена, отметку «пауза после» можно задать сразу при вставке. Своя нода выполняется как нода пайплайна — с retry, записью в `node_logs` (`trigger_type = pipeline`) и переменными `{{node.*}}` (её ответ — `{{node.llm_output}}` для следующих нод), и переход в `done` требует её успеха, как у любой включённой ноды (раздел 17.5); таймаут, число попыток и задержка retry копируются из «Системных настроек» в момент вставки. Перед сохранением вставки, правки или удаления по составу задачи «как будет» проверяются шаблоны всех своих нод: каждой `{{node.*}}` должна предшествовать нода подходящего типа; при ошибке изменение не сохраняется (422). Ноды пайплайна повторно не проверяются — они проверены при сохранении пайплайна, а свои ноды только добавляют им источников. Текст можно заполнить из неархивного промта или слэш-команды библиотеки: копируются название, тип и текст, связи с промтом библиотеки нет. У своей ноды можно изменить название, тип и текст или удалить её; нода, по которой уже есть запись `node_logs`, не удаляется — её отключают. «Вернуть в новые» оставляет свои ноды в снимке. Смена пайплайна в `new` заменяет снимок целиком вместе со своими нодами: свои ноды без записей `node_logs` удаляются, с записями — остаются в `nodes` только для истории и в снимок не попадают. «Дублировать задачу» копирует снимок с отметками включения и «пауза после», а свои ноды — новыми записями `nodes` новой задачи с теми же текстом и параметрами выполнения.

### 13.2 Редактируемость после запуска и после сбоя

- Пока задача в статусе `new` — редактируется `is_enabled` для любой ноды.
- После первого запуска (переход из `new`) — редактирование запрещено полностью.
- **Исключение:** если задача находится в статусе `failed`, разрешено редактировать `is_enabled` только для нод, ещё не приступавших к выполнению в рамках текущего прогона: с `order_index`, строго большим `tasks.last_failed_order_index`, и для ноды на самой точке перезапуска, если по ней в текущем прогоне нет записи `node_logs` пайплайна — так бывает после «Остановить» на паузе после ноды и после сбоя за последней нодой. Нода, на которой произошёл сбой, и все предшествующие ей недоступны для изменения — по ним уже существует зафиксированная история выполнения.
- Вставка, правка и удаление своих нод подчиняются тем же правилам: в `new` — в любом месте; в `failed` — вставка только на позиции ещё не начинавших выполнение нод: новая нода получает `order_index` больше `tasks.last_failed_order_index` (после упавшей ноды или после любой ноды за ней, но не в начало) или равный ему, если нода на точке перезапуска не начинала выполняться — после «Остановить» на паузе свой промт вставляется сразу за нодой с паузой и выполнится первым при перезапуске; правка и удаление — только своих нод на таких же позициях; в остальных статусах — нельзя (409). Во время выполнения уточнение отправляют свободным промтом (раздел 8).
- Отметка «пауза после» (`pause_after`) меняется в любом статусе, в том числе во время выполнения: оркестратор перечитывает её по завершении ноды. Отметка у уже пройденной ноды на текущий прогон не влияет.

### 13.3 Поведение оркестратора при пропущенных нодах

Оркестратор пайплайна при выполнении итерирует по записям `task_nodes` в порядке `order_index`, пропуская записи с `is_enabled = false` без создания записи в `node_logs` для них. Переменные вида `{{node.script_output}}`, ссылающиеся на пропущенную ноду, должны быть отловлены на этапе валидации пайплайна как потенциальный риск — интерфейс обязан предупреждать пользователя при отключении ноды, если на её вывод ссылается любая из последующих активных нод.

### 13.4 История выполнения нод

Таблица `node_logs` является единой историей выполнения для всех источников — нод пайплайна, системных промтов библиотеки и свободных промтов.

- Каждая попытка выполнения ноды пайплайна создаёт отдельную запись `node_logs` с инкрементом `attempt_number` — история не перезаписывается.
- История доступна на вкладке «Логи» страницы задачи с фильтрацией по конкретной ноде, статусу и `trigger_type`.
- Для административного мониторинга должна быть доступна сводная выборка по всем задачам: какая нода, в какой задаче, когда и с каким итоговым статусом выполнялась — реализуется как отдельный отчётный view/эндпоинт поверх `node_logs`, без создания дублирующей таблицы.

## 14. Статусы задачи и переходы

### 14.1 Диаграмма статусов

```
new ──► queued ──► in_progress ──► done
 ▲        │            │  ▲   │
 └────────┘            │  │   ▼
 (отменить             │  │  plan_review ──► in_progress (после решения по плану)
  постановку)          │  │
                       ▼  │
                 awaiting_input ──► in_progress (после ответа/выбора)
                       │
                       ▼
                     paused ──► in_progress (кнопка "Продолжить")
                       │
                       ▼
                 rebase_conflict ──► in_progress или paused (после автообработки)
                       │
                       ▼
                    failed ──► in_progress (кнопка "Перезапустить с текущей ноды")

failed, done ──► new (кнопка "Вернуть в новые": сменить пайплайн и запустить заново)
```

Дополнительно к стрелкам диаграммы:
- `in_progress` переходит в `paused` по кнопке «Приостановить» — после завершения текущей ноды — и после успешной ноды с отметкой «пауза после» (раздел 13.1). «Остановить» на паузе после ноды переводит задачу в `failed` с `last_failed_order_index` на единицу больше `order_index` этой ноды. Пауза после последней ноды наступает до пуша: «Продолжить» пушит ветки и завершает задачу в `done`, «Остановить» переводит в `failed` с `last_failed_order_index` на единицу больше последней ноды снимка — «Перезапустить с текущей ноды» ничего не повторяет и доводит задачу до `done`.
- `in_progress` и `paused` переходят в `rebase_conflict`, если ребейз рабочей ветки на сменившуюся базовую (раздел 16.2) упал на конфликте или в рабочей директории остались незакоммиченные изменения — тогда ребейз выполняет агент, как при конфликте; в `failed` — по кнопке «Остановить» или после сбоя, в том числе после потери воркера, владевшего сессией (раздел 6.6).
- `rebase_conflict` переходит в `failed`, если автообработка не разрешила конфликт.
- `paused` переходит в `plan_review`/`awaiting_input`, если ручной промт, выполняемый на паузе, задал вопрос; после решения задача возвращается в `paused`.
- `failed` и `done` переходят в `new` по кнопке «Вернуть в новые»: так после запуска меняют пайплайн и состав нод. Точка перезапуска (`last_failed_order_index`) и автозапуск сбрасываются; сессия, история `node_logs` и рабочая ветка сохраняются, «Запустить» проходит пайплайн с начала. Момент возврата записывается в `tasks.reset_at`: выполнения нод прошлого прогона не засчитываются новому ни при перезапуске после сбоя, ни при переходе в `done`. Сессия хранится в каталоге своего LLM-аккаунта (раздел 19.5), поэтому смена LLM-аккаунта у задачи, уже имевшей сессию, забывает `session_id` — следующий запуск начнёт новую сессию. Задачу с живой сессией сначала останавливают («Остановить» → `failed`).

### 14.2 Описание статусов

| Статус | Значение | Доступные действия пользователя |
|---|---|---|
| `new` | Задача создана, не запущена | Выполнить, редактировать поля и состав включённых нод |
| `queued` | Поставлена в очередь Celery | Отменить постановку |
| `in_progress` | Активно выполняется | Приостановить, остановить, запустить промт из библиотеки, отправить свободный промт |
| `paused` | Приостановлена пользователем: пауза наступает после завершения текущей ноды (по кнопке или по отметке «пауза после» у ноды), сессия сохраняется, следующая нода не начинается | Продолжить, остановить, запустить промт из библиотеки, отправить свободный промт (ручные запросы на паузе выполняются сразу) |
| `plan_review` | Нода `plan_prompt` завершила формирование плана, ожидается решение пользователя | Выбор варианта через универсальный виджет выбора |
| `awaiting_input` | Ожидает ответа пользователя на текущей ноде (с вариантами выбора или свободным текстом) | Ввести ответ или выбрать вариант |
| `rebase_conflict` | Требуется разрешение конфликта при ребейзе на обновлённую базовую ветку | Автоматическая обработка, отображение прогресса: агент в сессии задачи разрешает конфликт, успех возвращает задачу в `in_progress` (или в `paused`, если она стояла на паузе), неудача переводит в `failed` |
| `failed` | Нода исчерпала попытки retry, пользователь нажал «Остановить» (текущее обращение к сессии прерывается) или автообработка конфликта ребейза не удалась. Неразрешённый конфликт сохраняется в `task_repositories.merge_status = conflict`: перезапуск сначала снова разрешает его, а не пушит ветку без ребейза | Перезапустить с текущей ноды (с возможностью донастройки ещё не пройденных нод), очистить контекст, вернуть в новые (сменить пайплайн), посмотреть трейс |
| `done` | Пайплайн выполнен полностью, изменения запушены | Очистить директорию репозиториев, дублировать задачу (архивное не переносится — раздел 3.2), вернуть в новые (сменить пайплайн и запустить заново) |

### 14.3 Требования к обработке переходов

- Переход в `plan_review` или `awaiting_input` обязан немедленно вызывать: обновление статуса в БД, WebSocket-событие для подключённых клиентов, push-уведомление подписанным пользователям, визуальную подсветку задачи на дашборде.
- Очистка рабочей директории репозиториев доступна пользователю только вручную, кнопкой в интерфейсе, и только когда статус задачи терминальный (`done` или `failed`). Автоматическое удаление директории запрещено.
- Артефакты задачи — файлы, которые пользователь загружает для агента (на странице задачи или по SFTP) и которые агент или script-нода сохраняют как результат. Хранятся в отдельном volume `user_files` (`/data/user-files/<код задачи>/` в контейнерах backend, worker и SFTP-шлюза), не подлежат удалению при очистке репозиториев — это раздельные директории с разным жизненным циклом — и переносятся между серверами (раздел 20.4).
- Артефакты доступны в любом статусе задачи. Через трекер файл загружается целиком (существующий с тем же путём заменяется) размером не больше `ARTIFACT_MAX_UPLOAD_MB` (по умолчанию 100 МБ, больше — 413); незавершённая загрузка не заменяет прежний файл. Путь — относительно каталога артефактов: абсолютный путь, `..` и выход за каталог через символическую ссылку отклоняются (422). Список показывает обычные файлы (до 1000), символические ссылки не обходятся. Удаление и замена по пути символической ссылки действуют на саму ссылку, файл, куда она указывает, не меняется.

| Администрирование | Пользователи, доступ, системные настройки, MCP-серверы, мониторинг (только `admin`) |

### 15.2 Страница задачи — детальные требования

Страница обязана разделять на две независимые визуальные зоны, не влияющие на высоту друг друга: зону статичных данных задачи (поля, репозитории, переменные) и зону диалога (лента ввода/вывода сессии).

**Шапка задачи** дополнительно содержит:
- Кнопку **«🔗 Переподключить удалённую сессию»** — присутствует, пока у задачи есть живая сессия Claude Code (раздел 6.5; у задачи без LLM-аккаунта сессии и моста нет), независимо от статуса моста, с визуальным акцентом при `remote_control_status = disconnected`.

**Вкладка «Обзор»** дополнительно содержит:
- Блок «Автозапуск»: переключатель `auto_start_enabled` и поле выбора даты/времени `scheduled_start_at`, поле неактивно, пока переключатель выключен.
- При выборе пайплайна — раскрывающийся список его нод в порядке выполнения, каждая строка с чекбоксом включения (по умолчанию включены все), редактируется только пока задача в статусе `new`; после `failed` чекбоксы доступны только для ещё не начинавших выполнение нод (раздел 13.2), остальные отображаются как заблокированные с пояснением «уже выполнено». При попытке отключить ноду, вывод которой используется последующей активной нодой — предупреждение с указанием конкретной зависимой ноды. В каждой строке, кроме `clear_context`, — переключатель «⏸ пауза после»: доступен в любом статусе, в том числе во время выполнения (раздел 13.1); пока сохраняется изменение строки или проверяются зависимые ноды, чекбоксы, переключатели и кнопки «Изменить»/«Удалить» недоступны. Под названием ноды — её тип, у своей ноды вместо типа — «свой промт». Кнопки «+ Промт» стоят в начале списка и после каждой ноды — только там, где вставка разрешена (раздел 13.2). Они открывают диалог: «Заполнить из библиотеки» (если в библиотеке есть промты или слэш-команды), название, тип (промт или слэш-команда), текст промта с подсказкой переменных и предпросмотром (раздел 5.1) или строка слэш-команды. Ошибка сохранения показывается уведомлением, диалог остаётся открытым. У своей ноды, которую можно править, — кнопки «Изменить» и «Удалить»; удаление — после подтверждения.
- Переключатель `auto_accept_plan` («Принять план и продолжить в auto режиме») — доступен как до запуска, так и во время выполнения задачи; учитывается в момент, когда очередная нода `plan_prompt` завершает формирование плана.
- Блок «Артефакты»: файлы каталога артефактов задачи (путь, размер, дата изменения), загрузка одного или нескольких файлов, скачивание, удаление с подтверждением (раздел 14.3). Пока у задачи живая сессия, список обновляется сам — по событиям статуса и периодически; так же — пока копируются вложения задачи из Jira (раздел 15.6).
- Ссылка «Открыть в Jira», если задача импортирована из Jira (раздел 15.6).
- Кнопка «Сменить пайплайн» в карточке нод, пока задача в `new` (раздел 13.1); кнопка «Вернуть в новые» в шапке задачи в `failed`/`done` (раздел 14.1).
- Блок «Системные промты задачи»: список добавленных из библиотеки промтов (кнопки ▶/■, название, время последнего запуска, статус, включая `в очереди`; раскладка строки — раздел 7.3), кнопка «+ Добавить промт из библиотеки».

**Вкладка «Диалог»** (лента сессии; на любой ширине экрана вкладка называется одинаково — раздел 15.3) дополнительно содержит:
- Свободное текстовое поле параметризованного промта, отдельное от поля ответа на `awaiting_input`/`plan_review` — визуально разграничены. У задачи без LLM-аккаунта поле недоступно с пояснением (раздел 3.1).
- Универсальный виджет выбора (раздел 9.6): при переходе в `plan_review` или в `awaiting_input` с непустыми вариантами — рядом с полем ввода отображается набор кнопок вместо (или в дополнение к) текстового поля. Для `plan_review` дополнительно отображается выделенный блок с полным текстом плана над виджетом выбора.
- Индикатор «В очереди» рядом с полем свободного ввода и в таблице системных промтов — когда запрос помещён в `task_manual_request_queue`.

**Требования к чат-ленте (вкладка «Диалог»):**
- Реплики отображаются в хронологическом порядке, визуально различая: сообщения пользователя, ответы LLM, вывод скрипт-нод, блоки плана.
- Каждый блок вывода по умолчанию свёрнут до короткого превью с возможностью разворачивания по клику — полный текст не должен автоматически растягивать страницу.
- Поле ввода ответа зафиксировано (sticky) в нижней части чат-панели независимо от прокрутки ленты, активно только при статусе `awaiting_input`/`plan_review`, либо всегда — для свободного поля ввода (раздел 8).
- Предусмотрена возможность разворачивания всей чат-ленты в полноэкранный режим просмотра.
- Ответ LLM отображается с оформлением Markdown, как в Claude Code CLI: заголовки, абзацы, списки, жирный текст, код в строке (в том числе внутри жирного), блоки кода с подсветкой и таблицы — рамкой с жирной шапкой и выравниванием колонок по строке-разделителю (`:---`, `:---:`, `---:`); широкая таблица прокручивается по горизонтали внутри своего блока. HTML из ответа не исполняется; копирование и скачивание отдают исходный текст.
- Реплики агента внутри одного ответа (до и после вызова инструмента) разделяются абзацем. Решение пользователя (по плану, ответ на вопрос, разрешение действия) стоит в ленте там, где агент его запросил (`node_logs.decision_output_offset`): текст до запроса — выше, ответ агента после решения — ниже.
- Ответ, полученный со стороны сессии в процессе генерации, отображается потоково (по мере поступления от SDK), а не единым блоком после завершения.
- Каждая нода на вкладке «Диалог» имеет отдельную кнопку открытия полного вывода именно этой ноды (в боковой панели или отдельном оверлее), независимо от общей чат-ленты — с возможностью копирования и скачивания текста.
- Сообщения, отправленные через `claude.ai/code`, в ленту не попадают: там сессия доступна только для просмотра (раздел 6.3). Служебные реплики помечены источником: «отправлено вручную», «промт из библиотеки», «пересказ для дочерней задачи», «саммари родительской задачи».

### 15.3 Требования к адаптивности

Интерфейс обязан корректно отображаться и оставаться полностью функциональным в диапазоне ширины экрана от 375px (мобильные устройства) до 2560px (широкие мониторы).

| Диапазон ширины | Требование к раскладке |
|---|---|
| ≥ 1280px | Двухколоночная раскладка: панель данных задачи слева, чат-панель справа, обе видны одновременно |
| 768–1279px | Раскладка на основе табов верхнего уровня «Обзор / Диалог / Логи», как на экранах уже 768px; ширина рабочей области — по ширине экрана |
| < 768px | Раскладка на основе табов верхнего уровня, чат занимает весь экран при активной вкладке «Диалог», поле ввода отображается только в этой вкладке |

- Все интерактивные элементы обязаны иметь размер зоны нажатия не менее 44x44px на устройствах с сенсорным вводом. Исключение — экраны высотой до 540px (телефон в альбомной ориентации): чтобы оставить место под основной текст и чат, вертикальные размеры элементов сокращаются, а зона нажатия — не менее 36x36px (выше минимума WCAG 2.5.8 в 24px); вертикальная прокрутка страницы в этом режиме допустима.
- Раскрытие детального просмотра одной ноды на мобильных устройствах выполняется через выезжающую снизу панель (bottom sheet), а не через модальное окно, дублирующее десктопную раскладку.
- Кнопки универсального виджета выбора (раздел 9.6) на мобильном экране отображаются полноширинным вертикальным стеком, а не горизонтальным рядом, для соблюдения минимального размера зоны нажатия.
- Список системных промтов задачи на мобильном экране — тот же список строк, что и на широком (раздел 7.3): название сокращается многоточием, кнопки ▶/■ и статус остаются в строке.

### 15.4 Конструктор пайплайна и редактор библиотеки промтов — требования к форме ноды

Общая форма для обоих контекстов (создание ноды пайплайна и создание системного промта библиотеки) — различие в наборе доступных полей:

| Поле формы | Пайплайн | Библиотека |
|---|---|---|
| Название, описание | Да | Да (описание обязательно) |
| Тип ноды | Все 5 типов (`plain_prompt`, `slash_command`, `script`, `clear_context`, `plan_prompt`) | Только `plain_prompt`, `slash_command`, `script` |
| Порядок выполнения | Да | Нет (не применимо) |
| Пропуск по умолчанию (`is_skipped`) | Да | Нет |
| Политика retry (`max_retries`, задержка) | Да (не применяется к `plan_prompt` при отказе пользователя от плана) | Нет (пользователь управляет запуском вручную) |
| Поле «Гайд» (URL Confluence) | Да | Да |
| Таймаут (`timeout_seconds`) | Да | Да (применяется идентично пайплайну) |

Подсказка по доступным переменным для вставки в текстовое поле промта не включает `{{node.*}}`, если форма открыта в контексте библиотеки или свободного ввода. Для поля `command_invocation` (слэш-команда) подсказка по переменным не отображается вовсе — явно указано текстом «команда передаётся в сессию без изменений». При выборе типа `plan_prompt` форма дополнительно отображает информационную подсказку о том, что нода доступна только внутри пайплайна и не может быть сохранена как элемент библиотеки.

### 15.6 Импорт задачи из Jira

Пользователь заполняет форму новой задачи из задачи Jira по её ключу, чтобы не переносить описание вручную.

- **Подключение** — адрес Jira задаёт администратор в «Системных настройках» (`system_settings.jira_url`, раздел 15.5): сервер, к которому обращается backend, пользователь не выбирает. Доступ — личный: в профиле пользователь указывает email (для Jira Cloud) и личный токен (Jira Cloud — API token, Jira Server/Data Center — personal access token). Токен хранится зашифрованным и не возвращается API (раздел 19.4). Без адреса Jira или без токена импорт недоступен (422 с подсказкой).
- **Получение задачи** — backend по запросу пользователя читает задачу через Jira REST API v2 (`GET /rest/api/2/issue/{ключ}`, работает и для Cloud, и для Server/Data Center) от имени этого пользователя. Это единственное обращение backend к Atlassian: содержимое страниц Confluence из поля «Гайд» по-прежнему читает только LLM через MCP (раздел 22).
- **Что копируется** — только то, для чего у задачи есть поля: ключ → код задачи (проверяется по правилам раздела 3.1), summary → название, description → описание, ссылка на задачу → `tasks.jira_issue_url`, вложения → артефакты задачи (раздел 14.3). Одноимённые вложения сохраняются все: второе и следующие получают суффикс (`image (2).png`). Вложение запрашивается только с сервера Jira из настроек: из ссылки Jira берутся путь и параметры, поэтому токен пользователя не уходит на другой хост, а Base URL Jira, отличный от адреса в настройках (внутренний адрес, явный порт), не мешает копированию. Вложение больше `ARTIFACT_MAX_UPLOAD_MB` или не скачавшееся пропускается, запись об этом попадает в `app_logs`; сбой копирования вложений не отменяет создание задачи.
- **Интерфейс** — в форме «Новая задача» поле «Ключ Jira» и кнопка «Заполнить из Jira»: поля формы заполняются, пользователь может их поправить и добавить репозитории, пайплайн и LLM-аккаунт как обычно; вложения копирует в артефакты фоновая Celery-задача сразу после создания задачи — ответ «задача создана» их загрузки не ждёт, а пока копирование идёт, карточка «Артефакты» показывает «Копируются вложения из Jira» и обновляет список сама (флаг копирования — в Redis, его снимает фоновая задача по окончании или сбою; TTL — страховка на случай потерянной задачи). На вкладке «Обзор» задачи — ссылка на задачу Jira.
- **Ошибки** — задача не найдена в Jira — 404; Jira отклонила токен — 502 с сообщением «проверьте токен в профиле»; Jira ответила не JSON (страница входа SSO, неверный адрес) — 502 с подсказкой проверить адрес и токен; Jira недоступна — 502.

## 16. Периодические фоновые задачи

### 16.1 Механизм хранения расписания

Расписание периодических задач хранится в таблице `periodic_tasks`, а не хардкодится в коде. Планировщик Celery Beat должен использовать динамический источник расписания, читающий записи из этой таблицы и подхватывающий изменения без перезапуска процесса Celery Beat. Изменение расписания выполняется через административный интерфейс, без деплоя. Тип расписания (`interval`/`crontab`) задан задачей и не меняется — правится его значение: интервал — целое число секунд больше нуля, cron — 5 полей «минута час день_месяца месяц день_недели»; неверное значение отклоняется при сохранении.

### 16.2 Перечень задач для первичного заполнения (seed)

| Название | Описание | Период по умолчанию |
|---|---|---|
| `check_scheduled_tasks_for_autostart` | Находит задачи со статусом `new`, `auto_start_enabled = true` и наступившим `scheduled_start_at`, инициирует их запуск | Каждые 5 минут |
| `check_llm_account_limits` | Возвращает в `active` LLM-аккаунты в `rate_limited`, у которых истекло окно лимита (`rate_limit_resets_at`). Сам статус `rate_limited` выставляет воркер по событию лимита, которое CLI присылает в поток сессии: отдельного API опроса лимитов вне сессии у SDK нет | Каждые 5 минут |
| `cleanup_stale_worktrees` | Находит задачи в терминальном статусе старше N дней (по умолчанию 14, от последнего изменения задачи) с неочищенной директорией, отправляет автору push-напоминание — не чаще раза в 7 дней на задачу (ключ Redis `SET NX` с TTL) | Раз в сутки |
| `detect_awaiting_input_timeout` | Повторно уведомляет автора задачи, находящейся в `awaiting_input`/`plan_review` дольше порога (по умолчанию 4 часа) — не чаще раза за порог на задачу (ключ Redis `SET NX` с TTL) | Каждый час |
| `sync_gitlab_merge_status` | Обновляет `task_repositories.merge_status` по данным GitLab API | Каждые 10 минут |
| `rebase_child_branches_on_parent_merge` | При обнаружении смерджа родительской ветки переключает базовую ветку дочерних задач на базовую ветку родителя. Рабочую директорию задачи эта задача не трогает — в ней в это время может работать агент: задачам с живой сессией (`in_progress`, `paused`, `plan_review`, `awaiting_input`) она ставит отметку `task_repositories.rebase_requested_at`, а ребейз выполняет воркер задачи в ближайшей точке между нодами (раздел 14.1); задачи в `new`/`queued` склонируют свежую базу при старте, в `done`/`failed` — не ребейзятся. Конфликт или незакоммиченные изменения переводят задачу в `rebase_conflict` (раздел 14.2). Сбой по одной задаче не прерывает обработку остальных | Каждые 10 минут |
| `purge_orphaned_docker_containers` | Останавливает зависшие контейнеры скрипт-нод, пережившие таймаут. Контейнер помечается при запуске меткой `tracker.deadline` — старт + `timeout_seconds` ноды + 2 минуты запаса; останавливается только контейнер с прошедшим дедлайном, так что долгий, но живой скрипт не прерывается. Контейнер без метки — зависший, если работает дольше 10 минут. Контейнер сессии (раздел 19.3) помечен меткой `tracker.task` и останавливается, если у его задачи нет пульса воркера (раздел 6.6) | Каждые 15 минут |
| `purge_orphaned_playwright_processes` | Находит и завершает осиротевшие процессы браузера (Playwright и аналогичные MCP-инструменты с состоянием), пережившие принудительное прерывание родительской задачи; при режиме `per_task_data_dir` дополнительно снимает файловую блокировку профиля, если она осталась висеть после завершения процесса. Пока MCP-серверы подключаются по сети и не дают протокола управления процессами, задача — точка расширения: фиксирует запуск без действий (раздел 10.4) | Каждые 15 минут |
| `rotate_task_logs` | Выгружает записи `node_logs` задач в `done` старше порога давности в сжатые JSONL-файлы в volume `log_archive` (по файлу на задачу и запуск) и удаляет их из БД только после того, как файл записан; в интерфейсе задачи старая история после этого недоступна. Задачи в `failed` не ротируются: их перезапуск опирается на историю выполнения | Раз в неделю |
| `revoke_stale_sshfs_keys` | Помечает для ротации SSH-ключи активных пользователей, по которым не было входа в SFTP-шлюз дольше 90 дней (`users.ssh_key_last_used_at`): владельцу приходит push-напоминание заменить или удалить ключ — не чаще раза в 90 дней (ключ Redis `SET NX` с TTL). Ключ не удаляется; ключи без единого входа не помечаются | Раз в сутки |
| `health_check_mcp_servers` | Обновляет `mcp_servers.is_healthy` | Каждые 10 минут |
| `deprovision_inactive_users` | Блокирует пользователей, чьи email удалены из `allowed_emails`: `users.is_active = false` (вход, API и SFTP-шлюз закрыты — шлюз проверяет `is_active` при входе и на каждой операции), в `app_logs` пишется запись с `os_username`. Повторный запуск идемпотентен. Администратор не блокируется, если иначе в системе не останется ни одного активного администратора, — вместо этого в `app_logs` пишется ошибка | Раз в сутки |
| `check_remote_control_bridges` | Проверяет и восстанавливает мост `/remote-control` для активных задач; задачу, чей воркер потерян (нет пульса после попыток восстановления), переводит в `failed` (раздел 6.6) | Каждые 2 минуты |
| `expire_stale_manual_queue_requests` | Отменяет запросы в `task_manual_request_queue`, зависшие в статусе `queued` дольше 30 минут, переводит в `cancelled` с уведомлением пользователя. Зависшим считается только запрос задачи без живой сессии (не `queued`, `in_progress`, `paused`, `plan_review`, `awaiting_input`, `rebase_conflict`): у работающей задачи запрос дождётся своей очереди за долгой нодой или решением пользователя | Каждые 15 минут |

### 16.3 Требования к выполнению

- Каждый запуск периодической задачи обязан обновлять `last_run_at`, `last_run_status`, вычислять `next_run_at`.
- Ошибка выполнения периодической задачи не должна приводить к падению процесса Celery Beat — исключения перехватываются и логируются в `app_logs`.
- Каждая периодическая задача должна поддерживать принудительный запуск вне расписания (используется кнопкой «Запустить сейчас» в административном интерфейсе).

## 17. Логирование, обработка ошибок и идемпотентность («работа из коробки»)

### 17.1 Принцип

Технологический стек и архитектура обязаны сами обеспечивать надёжность типовых сценариев — повторные запуски Celery-задач, сетевые сбои, параллельные обращения — не полагаясь на аккуратность каждого отдельного разработчика при написании конкретного модуля.

### 17.2 Логирование

- Все backend-компоненты используют единую конфигурацию структурированного логирования (`structlog` или эквивалент), формат — JSON, с обязательными полями: `timestamp`, `level`, `source`, `task_id` (если применимо), `message`. Формат одинаков для API, воркеров Celery и Beat и для записей библиотек (uvicorn, Celery, предупреждения Python): у них `source` — имя логгера; `task_id` получают все события, записанные при обработке задачи воркером сессии и фоновыми задачами по задаче, в том числе события общих сервисов (git, сессия, скрипт-ноды).
- Критичные события (необработанные исключения, сбои периодических задач, ошибки взаимодействия с Claude Agent SDK, ошибки git-операций) дополнительно сохраняются в таблицу `app_logs`.
- SFTP-шлюз пишет в `app_logs` (`source = sftp`) успешный вход и отказ во входе известному пользователю (один раз на соединение); попытки входа под неизвестным логином и файловые операции — только в stdout.
- Обычные (не критичные) логи допустимо выводить только в stdout контейнера — ротацию и хранение обеспечивает стандартный драйвер логирования Docker.
- В административном разделе «Мониторинг» обязателен просмотр `app_logs` с фильтрами по уровню, источнику, задаче и диапазону дат.

### 17.3 Обработка исключений

- На уровне backend обязателен единый middleware/обработчик необработанных исключений, приводящий любую ошибку к стандартизированному формату ответа API (код ошибки, человекочитаемое сообщение, `request_id` для сопоставления с записью в `app_logs`). Необработанное исключение (ответ 500) записывается в `app_logs` с `source = api`, `request_id`, методом, путём и трейсом; запись ограничена 2 секундами, и её сбой (в том числе недоступная БД) ответ не меняет.
- Каждая Celery-задача оборачивается в блок перехвата исключений, гарантирующий: запись ошибки в `app_logs`, корректное обновление статуса связанной задачи/ноды (не оставлять запись в статусе `running` при падении процесса), применение соответствующей retry-политики, если применимо. Если процесс воркера сессии погиб целиком и перехватить исключение было некому, задачу переводит в `failed` проверка пульса (раздел 6.6).
- Ошибки взаимодействия с внешними системами (GitLab API, MCP-серверы, Claude Agent SDK) обязаны различать временные сбои (подлежат retry) и постоянные сбои (требуют немедленного уведомления без бесполезных повторов):
  - **Claude Agent SDK, нода пайплайна.** Постоянные сбои — ответ с ошибкой `authentication_failed`, `billing_error` или `invalid_request` и отсутствие CLI (`CLINotFoundError`): нода падает без повторов, задача переходит в `failed`, автор получает уведомление (раздел 18.2). Временные — `rate_limit`, `server_error`, прочие ошибки ответа, таймаут ноды и падение процесса CLI посреди хода: повтор по retry-политике ноды (раздел 11.7); после падения процесса воркер перед повтором поднимает новый процесс CLI, продолжающий ту же сессию. Запуски из библиотеки и свободный промт не повторяются в любом случае (раздел 7.4). Ненулевой код возврата и таймаут скрипта — временные сбои (раздел 11.4).
  - **GitLab API** (`sync_gitlab_merge_status`). Временные сбои — сетевые ошибки, ответы 5xx, 408 и 429: репозиторий пропускается, остальные синхронизируются, повтор — на следующем запуске. Отклонённый токен (401, 403) — сбой всей интеграции, токен один на систему: синхронизация прерывается и приостанавливается на сутки, в `app_logs` один раз пишется ошибка для администратора, авторам задач уведомления не отправляются. Прочие ответы 4xx — постоянный сбой конкретного репозитория: ошибка пишется в `app_logs`, автор задачи получает уведомление, и репозиторий не опрашивается сутки — без повторных запросов и уведомлений. После паузы попытка повторяется (администратор мог исправить токен или путь проекта).
  - **MCP-серверы.** Backend обращается к ним только в `health_check_mcp_servers`: результат проверки — флаг `is_healthy`, проверка повторяется по расписанию.

### 17.4 Идемпотентность

- Каждая Celery-задача, изменяющая состояние, обязана перед выполнением проверять текущее состояние сущности в БД и корректно завершаться без побочных эффектов, если целевое состояние уже достигнуто.
- Для операций, критичных к повторному выполнению (пуш в Git, обработка очереди ручных запросов), используется распределённая блокировка на основе Redis (`SET NX` с TTL) по ключу, включающему идентификатор задачи и тип операции.
- Повтор push-уведомления исключается тем, что уведомление отправляется только после фиксации однократного изменения состояния, а не отдельной блокировкой:
  - переход статуса задачи (`awaiting_input`/`plan_review`, `failed`, `done`) — после успешного compare-and-swap статуса; повторная попытка того же перехода не проходит и уведомления не отправляет;
  - завершение запуска промта библиотеки с ошибкой — один раз на запуск, после записи итогового статуса `node_logs`;
  - отмена запроса из очереди по сроку ожидания — при переводе запроса из `queued` в `cancelled` одним `UPDATE` с условием на текущий статус: пересёкшиеся запуски не отменяют и не уведомляют дважды;
  - разрыв моста — только когда `remote_control_status` впервые становится `disconnected`; повторные проверки при том же статусе уведомление не отправляют;
  - постоянный сбой синхронизации с GitLab — один раз за паузу опроса репозитория, ключ Redis `SET NX` с TTL (раздел 17.3);
  - напоминания `cleanup_stale_worktrees` и `detect_awaiting_input_timeout` — один раз за интервал на задачу, ключ Redis `SET NX` с TTL (раздел 16.2);
  - неудачный автозапуск — на каждую неудачную попытку (раздел 12.3): задача остаётся в `new`, и следующая неудачная попытка — новое событие.
- Все статусные переходы задачи выполняются через явную проверку текущего статуса перед изменением (compare-and-swap на уровне транзакции БД).
- У сессии задачи в каждый момент один владелец-воркер. Ключ пульса (раздел 6.6) — блокировка владельца: воркер захватывает его `SET NX` со своим токеном до начала работы с сессией, продлевает и снимает только свой ключ. Второй исполнитель той же задачи — повторная доставка сообщения Celery или продолжение после очистки контекста, пришедшее раньше, чем прежний владелец отпустил сессию, — ждёт освобождения ключа ограниченное время и завершается без побочных эффектов, если ключ так и не освободился. Срок видимости сообщений брокера (`visibility_timeout`) задан больше, чем сообщение может ждать свободного воркера сессий.

### 17.5 Логические связки, обязательные к проверке при реализации

- Переход задачи в `done` невозможен, пока хотя бы одна включённая нода пайплайна не имеет записи в `node_logs` со статусом `success`.
- Переход задачи в `failed` обязан сохранять точный `order_index` сбоя в `tasks.last_failed_order_index`.
- Очистка контекста сессии обязана быть невозможна, пока есть хотя бы одна запись `node_logs` со статусом `running` или `awaiting_decision`.
- Обработка очереди `task_manual_request_queue` обязана быть защищена той же распределённой блокировкой, что и обращения к сессии.
- Сохранение MCP-сервера с `has_stateful_resource = true` без указанного `isolation_mode` — запрещено.

## 18. Уведомления и real-time обновления

### 18.1 Каналы доставки

| Канал | Назначение | Технология |
|---|---|---|
| WebSocket | Мгновенное обновление статуса задачи в открытой вкладке браузера | Канал на задачу: `/ws/tasks/{task_id}/status` |
| Web Push | Уведомление, доставляемое даже при закрытой вкладке браузера | Service Worker + Push API, подписка запрашивается при первом входе |

Токен сессии WebSocket-канала передаётся первым сообщением `{"type": "auth", "token": ...}` (без него соединение закрывается через 5 секунд с кодом 4401), а не в адресе: адреса запросов попадают в журналы прокси и сервера. Доступ к каналу (активный автор задачи или `admin`, раздел 19.2) перепроверяется во время потока примерно раз в 10 секунд: заблокированный пользователь или потерявший доступ к задаче отключается (4401/4404).

Отправка Web Push ограничена по времени (10 секунд на подписку) и не останавливает процесс, который её вызвал: медленная push-служба не должна задерживать воркер сессии и его пульс (раздел 6.6). Неотправленное уведомление записывается в журнал и не прерывает отправку в остальные подписки.

### 18.2 События, требующие обязательного уведомления

- Переход задачи в `awaiting_input` или `plan_review`.
- Переход задачи в `failed`.
- Обнаружение разрыва моста `/remote-control` без успешного автоматического восстановления.
- Неудачная попытка автоматического запуска по расписанию.
- Завершение задачи со статусом `done`.
- Завершение выполнения системного промта библиотеки со статусом `failed`.
- Отмена запроса из очереди по истечении срока ожидания.
- Напоминание об очистке директории репозиториев и повторное напоминание о задаче, долго ожидающей решения (раздел 16.2).
- Постоянный сбой синхронизации статуса MR с GitLab (раздел 17.3).
- Напоминание о давно не использованном SSH-ключе SFTP-доступа — владельцу ключа (раздел 16.2).

### 18.3 Требования к отображению

- Задачи, ожидающие решения (`awaiting_input`, `plan_review`), визуально выделяются в списке задач на дашборде постоянным маркером.
- Счётчик таких задач отображается в постоянной навигации, видимой с любого экрана.

## 19. Управление доступом и безопасность

### 19.1 Аутентификация

- Единственный метод входа — Google OAuth. Один OAuth-клиент на backend и frontend: Client ID из `.env` (`GOOGLE_OAUTH_CLIENT_ID`) встраивается в сборку фронтенда при сборке образа, backend проверяет `id_token` по тому же Client ID.
- Регистрация нового пользователя разрешена только для email, присутствующего в таблице `allowed_emails`. Удаление email из списка блокирует уже зарегистрированного пользователя при ближайшем запуске `deprovision_inactive_users` (раздел 16.2); email последнего активного администратора удалить нельзя.
- Первый пользователь, зарегистрировавшийся в системе, автоматически получает роль `admin`.

### 19.2 Ролевая модель

| Роль | Права |
|---|---|
| `user` | Собственные задачи, пайплайны, библиотека промтов, шаблоны, LLM-аккаунты; просмотр собственного профиля; просмотр списка MCP-серверов для выбора в своих шаблонах |
| `admin` | Все права `user` + задачи, пайплайны, промты, шаблоны и LLM-аккаунты всех пользователей, `allowed_emails`, назначение ролей, системные настройки, управление MCP-серверами, мониторинг, расписание периодических задач |

«Собственные» — записи, автор которых (`created_by`) — сам пользователь. Чужая запись для `user` неотличима от несуществующей (ответ 404), в том числе в канале real-time обновлений задачи. К своей задаче `user` привязывает только свои пайплайны и промты библиотеки, родительской выбирает только свою задачу. LLM-аккаунт задачи — только один из аккаунтов её автора, в том числе когда задачу редактирует `admin`. Репозитории и переменные окружения — общие. Шаблон репозитория по умолчанию применяется к задачам любого пользователя, но `user` назначает репозиторию только свой шаблон. Счётчик задач, ожидающих решения (раздел 18.3), и push-уведомления — по собственным задачам, в том числе у `admin`. В SFTP-шлюзе видны те же задачи, что в API: у `user` — свои, у `admin` — все.

### 19.3 Изоляция выполнения скрипт-нод и сессии агента

- Контейнер скрипт-ноды не должен иметь доступа к сети без исключений.
- Контейнеру монтируются исключительно директория репозиториев и каталог артефактов текущей задачи в режиме read-write.
- Ограничение ресурсов контейнера (память, CPU) обязательно.
- Процесс Claude Code CLI выполняет команды агента (в автономном режиме — без подтверждения, раздел 9.4), поэтому работает в отдельном одноразовом контейнере сессии из образа `tracker-session`, а не в контейнере воркера:
  - монтируются только директория репозиториев задачи, каталог её артефактов и каталог LLM-аккаунта задачи (раздел 19.5) — по тем же путям, что в воркере; `docker.sock` и другие volume не монтируются;
  - процесс запускается от пользователя воркера (файлы задачи остаются доступны воркеру), с лимитами памяти и CPU, без `--privileged`;
  - переменные окружения передаются по белому списку (настройки CLI и SDK: `CLAUDE_*`, `ANTHROPIC_*`, прокси); секреты сервера (`SECRET_ENCRYPTION_KEY`, `SESSION_SECRET_KEY`, `DATABASE_URL`, `REDIS_URL` и прочие) в контейнер не попадают;
  - git-идентичность коммитов агента задаёт трекер (`GIT_AUTHOR_*`, `GIT_COMMITTER_*` — «AI Tracker», та же, что у ребейза воркером): своего git-конфига в контейнере нет;
  - сеть — только внешняя (API Anthropic, мост `claude.ai/code`, адреса MCP-серверов): контейнер не подключается к внутренней сети сервисов, Postgres, Redis и backend из него недоступны;
  - контейнер помечен меткой задачи и удаляется по завершении процесса CLI; пережившие свой воркер контейнеры убирает `purge_orphaned_docker_containers` (раздел 16.2).
- Git-операции воркера (клонирование, fetch, ребейз, пуш) выполняются в директориях, которые могут менять агент и скрипт-ноды, поэтому не исполняют ничего из репозитория: хуки отключены, глобальная и системная конфигурация git не читаются, а из локальной `.git/config` перед операцией удаляется всё, кроме белого списка ключей (формат репозитория, `remote.origin`, привязка веток); адрес `origin` восстанавливается из `repositories.git_url`.

### 19.4 Хранение секретов

- Deploy-ключи репозиториев, значения переменных окружения, помеченные как секретные, и данные авторизации MCP-серверов хранятся в базе данных в зашифрованном виде.
- Ключ шифрования хранится вне базы данных и доступен только процессам трекера (backend, worker, beat): в контейнеры скрипт-нод и сессии агента он не передаётся (раздел 19.3).
- Отображение секретных значений в интерфейсе по умолчанию скрыто, раскрывается по явному действию пользователя.
- Личный токен Jira пользователя (раздел 15.6) хранится зашифрованным и не возвращается API. Адрес Jira задаёт только администратор, вложения запрашиваются только с этого сервера.
- Секретные значения не показываются и косвенно: в предпросмотре промта и в сохранённом тексте промта (`node_logs.rendered_prompt`) они замаскированы (раздел 5.1). Токен GitLab API хранится в системных настройках (раздел 15.5), а не среди переменных окружения, поэтому через `{{env.*}}` недоступен.

### 19.5 Множественные LLM-аккаунты

- Параллельное выполнение задач под одним и тем же Anthropic-аккаунтом разрешено и является ожидаемым штатным режимом работы системы, а не исключением — что прямо мотивирует обязательность требований раздела 10 к изоляции MCP-инструментов с состоянием.
- Каждый LLM-аккаунт использует изолированную конфигурационную директорию (`CLAUDE_CONFIG_DIR`), не пересекающуюся с директориями других аккаунтов.
- Конфигурационные директории аккаунтов лежат внутри корня `CLAUDE_ACCOUNTS_ROOT` (volume `claude_accounts` worker-контейнера, по умолчанию `/data/claude-accounts`). Пользователь заводит аккаунт с путём внутри корня, затем администратор выполняет в этой директории вход в Claude: `docker compose exec -e CLAUDE_CONFIG_DIR=<директория> worker claude auth login` (CLI из `claude-agent-sdk` доступен в образе как `claude`). Вход выполняется только в директории уже заведённого аккаунта, поэтому чужой вход занять нельзя. Путь нормализуется; путь вне корня — 422, путь, совпадающий с директорией другого аккаунта или вложенный в неё (и наоборот), — 409.
- LLM-аккаунт принадлежит пользователю, который его завёл (`llm_accounts.created_by`). Пользователь может завести несколько аккаунтов и для каждой своей задачи выбирает один из них; аккаунты других пользователей ему недоступны (раздел 19.2). Задаче из одних скриптов аккаунт не нужен (раздел 3.1); сессия без аккаунта не запускается под конфигурацией worker по умолчанию.

### 19.6 Доступ к файлам задач по SFTP

- Пользователь подключает файлы своих задач по SFTP — в том числе как диск (sshfs, SSHFS-Win, Mountain Duck) — к SFTP-шлюзу трекера на порту `SFTP_PORT` (по умолчанию 2222). Системные Linux-пользователи не создаются: логин — `users.os_username`, единственный способ входа — SSH-ключ из профиля (`users.ssh_public_key`); пароль и keyboard-interactive не поддерживаются.
- Структура: в корне — каталоги задач, видимых пользователю (раздел 19.2); в каталоге задачи — `repos` (директория репозиториев задачи, только чтение) и `artifacts` (каталог артефактов, чтение и запись, раздел 14.3). Создание символических и жёстких ссылок, перенос файлов между задачами и любые изменения в `repos` отклоняются. Символические ссылки внутри каталога показываются как сами файлы, ссылки за пределы каталога задачи не показываются и не открываются; удаление и перенос ссылки действуют на саму ссылку, а не на её цель.
- Ключ, логин, блокировка пользователя и права на задачу проверяются при входе и на каждой операции: смена или удаление ключа, смена логина, блокировка и новые задачи действуют сразу, в том числе на уже открытые сессии, без отдельной синхронизации.
- Разрешена только подсистема SFTP: shell, exec, scp, PTY, проброс портов, агента и X11 отклоняются. Число одновременных соединений ограничено (10 с одного адреса, 100 всего), на вход отводится 30 секунд.

## 20. Развёртывание

### 20.1 Требования к простоте установки и переносимости

Развёртывание на VDS обязано требовать минимум ручных действий администратора и не предполагать ручной настройки зависимостей, помимо базовой установки Docker. Смена сервера должна сводиться к переносу файла `.env` и volume-данных, без изменений кода или повторной ручной настройки окружения.

### 20.2 Детальная последовательность развёртывания технологического стека

1. Проверка и установка Docker + Docker Compose plugin на хосте, если отсутствуют; Docker Engine — не ниже 26 (монтирование подпути volume, раздел 11.4), иначе установка останавливается.
2. Клонирование репозитория проекта в целевую директорию на хосте (например, `/opt/tracker`).
3. Генерация `.env` из `.env.example` — все секреты генерируются автоматически через `openssl rand`, в том числе пароль роли БД SFTP-шлюза `SFTP_DB_PASSWORD` (hex — входит в строку подключения).
4. Интерактивный запрос только критичных значений: домен, email для выпуска TLS-сертификата, Google OAuth Client ID/Secret, email первого администратора.
5. Сборка Docker-образов: backend, frontend, `tracker-runner-python`, `tracker-runner-bash`, `tracker-session` (окружение процесса Claude Code CLI, раздел 19.3).
6. Поднятие инфраструктурных сервисов первыми: PostgreSQL и Redis — с проверкой готовности (healthcheck) перед стартом зависимых сервисов.
7. Применение миграций базы данных — автоматически в entrypoint backend-контейнера при старте, идемпотентно.
8. Заполнение начальных данных (seed) — email первого администратора в `allowed_emails` (без него по разделу 19.1 войти не сможет никто), дефолтный список `periodic_tasks` (без администратора: `updated_by = NULL`), дефолтные Docker-образы раннеров; сбой заполнения останавливает установку.
9. Старт прикладных сервисов: backend API, Celery worker, Celery worker сессий, Celery Beat, SFTP-шлюз, frontend, reverse-proxy — с зависимостями через `depends_on` с условием healthcheck.
10. Автоматическое получение TLS-сертификата reverse-proxy (Caddy) по домену, указанному на шаге 4.
11. Первый вход администратора через браузер, Google OAuth, автоматическое назначение роли `admin` первому пользователю. Скрипт напоминает открыть в файрволе порт SFTP-шлюза.

### 20.3 Структура репозитория для развёртывания

| Путь | Назначение |
|---|---|
| `docker-compose.yml` | Базовое описание всех сервисов |
| `docker-compose.prod.yml` | Override для production (реплики воркеров, лимиты ресурсов, restart-политики) |
| `.env.example` | Шаблон переменных окружения с комментариями по каждому значению |
| `deploy/install.sh` | Единственный скрипт, запускаемый вручную администратором: установка, перенос (`--restore`, раздел 20.4) и обновление (`--update`, раздел 20.6) |
| `deploy/caddy` | Конфигурация reverse-proxy |
| `backend/` | Код backend, Dockerfile |
| `frontend/` | Код frontend, Dockerfile сборки статики |
| `runners/` | Dockerfile-описания образов для script-нод и образа сессии агента `tracker-session` |
| `alembic/` | Миграции базы данных |

### 20.4 Требования к персистентности и переносимости между серверами

- Данные PostgreSQL, репозитории задач (включая директории профилей MCP-инструментов, раздел 10.3), артефакты задач (volume `user_files`, раздел 14.3), архив ротированной истории `node_logs` (`log_archive`, раздел 16.2), директории LLM-аккаунтов со входами в Claude и историей сессий (`claude_accounts`, разделы 6.4, 19.5) и ключ хоста SFTP-шлюза (`sftp_host_keys` — отпечаток сервера не меняется при перезапуске и переносе) — в именованных Docker-volumes.
- Роль БД SFTP-шлюза дампом не переносится: её при каждом старте заново создаёт entrypoint backend по `SFTP_DB_PASSWORD`; если `.env` старого сервера этой переменной не содержит, восстановление дописывает сгенерированный пароль.
- Перенос на новый сервер: снятие бэкапа PostgreSQL и архивирование volume-директорий → перенос архивов и файла `.env` → выполнение `deploy/install.sh` с флагом восстановления → восстановление дампа БД и распаковка архивов. Процедура документируется в `docs/migration.md`.
- Встроенный сервис резервного копирования PostgreSQL по расписанию, настраиваемый через `.env`.

### 20.5 Требования к привилегированным операциям

- Доступ к файлам задач — SFTP-шлюз (раздел 19.6), отдельный сервис `sftp` из образа backend со своей командой, без миграций и без `docker.sock`. Системные Linux-пользователи и привилегии на хосте не нужны. Контейнер: файловая система только для чтения, `no-new-privileges`, из capabilities оставлены только `CHOWN`, `DAC_OVERRIDE`, `FOWNER` (работа с файлами, созданными backend и worker); volume `task_repos` подключён только для чтения, `user_files` — для записи.
- Шлюз подключается к БД ролью `tracker_sftp` с минимальными правами: чтение `users`, из `tasks` — только `code` и `created_by`, обновление `users.ssh_key_last_used_at`, добавление записей `app_logs`. Секреты (`env_variables`, ключи репозиториев, данные MCP) ей недоступны. Без подключения к БД этой ролью (например, не задан `SFTP_DB_PASSWORD`) шлюз не стартует и пишет ошибку в лог, а не принимает соединения, в которых не пройдёт ни один вход.
- Celery worker разделён на два сервиса: `worker` (очередь `celery`, периодические задачи) и `session-worker` (очередь `sessions`, сессии задач, `-O fair`, prefetch 1, число процессов — `SESSION_WORKER_CONCURRENCY` из `.env`, по умолчанию 4). Celery Beat запускается с планировщиком, читающим `periodic_tasks` (раздел 16.1).
- Доступ Celery worker к Docker-демону хоста — через монтирование `docker.sock`, задокументированный компромисс, не требующий `--privileged`-режима для самого worker-контейнера. Код, который пишут пользователь и агент, к `docker.sock` доступа не получает: скрипт-ноды и процесс Claude Code CLI работают в своих контейнерах (раздел 19.3). Образ backend/worker содержит клиент Docker, `git` и `ssh` — для script-нод и для клонирования и пуша репозиториев по deploy-ключу.

### 20.6 Обновление установленного сервера

- Обновление до свежего кода — тем же скриптом: `deploy/install.sh --update`. Он требует уже установленного трекера (репозиторий и `.env` на месте) и не задаёт вопросов.
- Последовательность: получение кода только перемоткой вперёд (`git pull --ff-only` — локальные правки на сервере не затираются молча) → дописывание в `.env` значений, которых не знала прежняя версия (пароль роли SFTP-шлюза) → сборка всех образов шага 5 раздела 20.2, в том числе раннеров и `tracker-session`, которые не входят в `docker-compose.yml` и иначе остались бы старыми или отсутствовали бы → запуск PostgreSQL и Redis → миграции → дозаполнение `periodic_tasks` (идемпотентно, добавляются только новые задачи) → перезапуск прикладных сервисов.
- Задачи, чьи сессии шли во время перезапуска, переходят в `failed` проверкой пульса (раздел 6.6) и продолжаются «Перезапустить с текущей ноды».

## 21. Требования к тестированию

### 21.1 Обязательное покрытие

| Уровень | Что покрывается |
|---|---|
| Unit-тесты | Рендеринг шаблонных переменных (включая неприменение к слэш-командам), логика переходов статусов, retry, шифрование секретов, идемпотентность, валидация MCP-серверов с `has_stateful_resource` |
| Integration-тесты | Взаимодействие с Claude Agent SDK (мокирование, включая `canUseTool`-callback для `ExitPlanMode`), выполнение скрипт-нод, работа с БД, механизм автозапуска, обработка очереди ручных запросов, рендеринг `isolation_path_template` с реальным путём задачи |
| E2E-тесты | Полный цикл: создание задачи → отключение части нод → автозапуск по расписанию → прохождение включённых нод, включая `plan_prompt` → запуск и остановка системного промта из библиотеки → отправка свободного промта → достижение статуса `done`. Выполняется на уровне backend: действия пользователя — через HTTP API, задачу выполняет настоящий воркер сессии, Claude Agent SDK имитируется (настоящая сессия Claude в CI недоступна) |
| Тесты frontend | Компоненты и утилиты интерфейса — Vitest в окружении jsdom и Testing Library. Проверяется то, что видит и делает пользователь: подписи и доступность кнопок по статусу задачи, виджет решения, формы с проверкой ввода, маскирование секретов; ответы API имитируются |

### 21.2 Обязательные сценарии проверки

1. Пайплайн из всех пяти типов нод, включая `plan_prompt`, с передачей `{{node.script_output}}` и `{{node.plan_text}}` в последующие ноды, с частью нод отключённых на уровне задачи.
2. Задача с `auto_start_enabled = true` и `scheduled_start_at` в прошлом — проверка однократного срабатывания автозапуска.
3. Нода `plan_prompt` с `auto_accept_plan = false` — проверка перехода в `plan_review`, отображения виджета выбора с тремя вариантами, обработки решения «Доработать план» без расхода `max_retries`.
4. Нода `plan_prompt` с `auto_accept_plan = true` — проверка автоматического продолжения без остановки задачи.
5. Запуск системного промта библиотеки в момент, когда сессия занята нодой пайплайна — проверка постановки в `task_manual_request_queue`, корректной FIFO-обработки по освобождении сессии.
6. Многократный запуск одного системного промта, включая принудительную остановку кнопкой «■».
7. Отправка свободного параметризованного промта с проверкой корректного рендеринга переменных и записи с `trigger_type = freeform_manual`.
8. Исчерпание попыток retry для скрипт-ноды пайплайна с переходом в `failed`, фиксацией `last_failed_order_index`, последующим «Перезапустить с текущей ноды» с проверкой, что только ноды после точки сбоя доступны для изменения `is_enabled`.
9. Превышение `timeout_seconds` для запуска из библиотеки — проверка автоматического перехода в `failed` без последующего retry.
10. Сценарий смерджа родительской ветки с проверкой автоматического ребейза дочерней ветки.
11. Ручное нажатие кнопки переподключения удалённой сессии — проверка, что кнопка запускает новую попытку установить мост и статус в интерфейсе обновляется (`reconnecting`, затем `connected` при успешном перезапуске процесса); факт восстановления самого моста не проверяется — SDK не даёт такой гарантии (раздел 6.5).
12. Две задачи используют MCP-сервер с `has_stateful_resource = true` — проверка на уровне backend, что каждая задача передаёт серверу собственную изоляцию профиля (`ephemeral` или свой путь внутри директории задачи) для обоих `isolation_mode` и успешно завершается; соблюдение изоляции самим MCP-сервером — зона администратора (раздел 10.2).

### 21.3 Требования к качеству кода

- Минимальный порог покрытия тестами бизнес-логики (`services/`) — не ниже 85%.
- Все Celery-задачи обязаны быть идемпотентными — повторный запуск при сбое не должен приводить к дублированию побочных эффектов.

## 22. Ограничения и явные допущения (для избежания неоднозначностей реализации)

- Очистка рабочей директории репозиториев задачи выполняется только вручную, только в терминальном статусе задачи — автоматическое удаление любого вида запрещено.
- Контекст сессии Claude Code сохраняется по умолчанию между всеми обращениями к ней (ноды пайплайна, системные промты, свободные промты) и не сбрасывается автоматически ни при retry, ни при переходе между нодами — единственный способ сброса: явная нода `clear_context` в пайплайне или ручная кнопка на странице задачи, и только при отсутствии активно выполняющихся/ожидающих решения обращений.
- Слэш-команды (текст, начинающийся с `/`) никогда не проходят через шаблонизатор проекта — правило действует одинаково в пайплайне, библиотеке и свободном вводе.
- Обращения к одной сессии Claude Code строго последовательны; параллельные ручные запросы обслуживаются очередью FIFO, а не параллельным выполнением.
- Отключение ноды пайплайна на уровне конкретной задачи не изменяет сам пайплайн-шаблон и не создаёт запись в истории выполнения для этой ноды.
- После перехода задачи в `failed` донастройка состава включённых нод разрешена только для нод, ещё не начинавших выполнение в данном прогоне — уже пройденные и упавшая нода зафиксированы.
- Повторный запуск системного промта библиотеки не ограничен политикой retry — количество запусков полностью определяется пользователем; таймаут при этом применяется идентично пайплайну.
- Нода режима планирования (`plan_prompt`) доступна только в составе пайплайна; финальный уровень автономности после утверждения плана определяется выбором пользователя в момент принятия конкретного плана, а не заранее фиксированной конфигурацией ноды.
- Механизм программного восстановления моста `/remote-control` для сессии, управляемой через `ClaudeSDKClient`, требует технической верификации на раннем этапе реализации — пользовательский сценарий (кнопка, статус) фиксирован независимо от результата этой верификации.
- **MCP-серверы, управляющие ресурсом с ограничением на единовременное использование (браузерные профили и аналогичное), не могут быть сконфигурированы с общим для всех задач persistent-профилем — это запрещено конфигурацией системы, а не оставлено на усмотрение администратора при настройке конкретного сервера.** Единственно допустимые режимы — эфемерный изолированный профиль на каждый запуск либо профиль, физически привязанный к директории конкретной задачи.
- Автоматический запуск по расписанию гарантированно обнаруживает наступление `scheduled_start_at` не чаще, чем раз в 5 минут; для более точного попадания во время старта интервал должен быть уменьшен через таблицу `periodic_tasks` на этапе настройки конкретного инстанса.
- Вмешательство в работу агента выполняется только через поля трекера; `claude.ai/code` используется для просмотра сессии (раздел 6.3).
- Backend не выполняет самостоятельный доступ к содержимому страниц Confluence, указанных в поле «Гайд» — это зона ответственности LLM через MCP. Исключение одно: задачу Jira по ключу backend читает сам, по явному запросу пользователя и его токеном (раздел 15.6).
- Параллельное выполнение нескольких задач под одним LLM-аккаунтом разрешено явно и является ожидаемым штатным режимом работы системы.
- Скрипт-ноды выполняются без доступа к сети без исключений, независимо от того, являются ли они частью пайплайна или библиотеки системных промтов.
