# TWG в Tracker

## Цель и устройство

TWG доступен всем пользователям через Claude Agent SDK: поиск, чтение, создание
и изменение Jira/Confluence в пределах прав личной учётной записи Atlassian.
Установка не зависит от проекта, шаблона репозитория или провайдера модели.

CLI и базовые навыки устанавливает официальный TWG при сборке `tracker-session`.
В репозитории хранятся установочный код и `runners/tracker-session/twg.lock.json`,
а не бинарники, токены или копии сторонних навыков. Установленные файлы и их
лицензии остаются в образе; локальные файлы компьютера разработчика не копируются.

Claude SDK подключает `/opt/tracker-twg` как локальный плагин. Его навыки имеют
пространство имён `twg:`. Установка от TWG 1.4.4 без авторизации содержит
`twg`, `twg-jira`, `twg-confluence`, `twg-setup` со всеми references и лицензиями.
Это не полный комплект из 13 навыков, установленный в старой локальной среде:
дополнительный набор зависит от авторизованного доступа и версии TWG. Не нужно
подменять его копиями с компьютера администратора. Команды CLI обнаруживаются
через `twg help`; отсутствие отдельного навыка не означает отсутствия команды.

## Личное подключение

Профиль → Подключения → Atlassian TWG: сайт вида `company.atlassian.net`, email
и личный API-токен Atlassian. Для серверного запуска используются поддерживаемые
TWG переменные `TWG_SITE`, `TWG_USER`, `TWG_TOKEN`; интерактивный OAuth в интерфейсе
Tracker этой реализацией не добавляется. Доступность конкретных Graph-команд
зависит от метода авторизации, прав и возможностей организации Atlassian.

Сохранение проверяет формат, но не вызывает внешнюю систему и не подтверждает
действительность токена. Проверка пользователем в задаче: `twg doctor --basic`,
затем чтение известной Jira-задачи или страницы Confluence. Проверка записи —
только на явно выбранном пользователем тестовом объекте, без автоматических
изменений production-документов.

REST API текущего пользователя:

| Метод | Путь | Назначение |
| --- | --- | --- |
| GET | `/profile/twg` | Сайт, email, признак сохранённого подключения и доступности TWG |
| PUT | `/profile/twg` | Сохранение сайта, email, токена; `token: null` сохраняет прежний секрет |
| DELETE | `/profile/twg` | Удаление своего подключения; повторное удаление допустимо |

При первом подключении и смене сайта/email нужен новый токен. Токен хранится
в `twg_connections.token_encrypted` существующим механизмом Fernet; ключ —
`SECRET_ENCRYPTION_KEY` вне БД. Ответы API не содержат секрет или шифротекст.
Миграция добавляет таблицу; резервная копия БД включает её автоматически.
При восстановлении нужен прежний ключ шифрования.


Воркер получает подключение по `task.created_by`, а не по пользователю,
запустившему операцию, выбранному LLM-аккаунту или создателю шаблона.
В Docker передаются только три разрешённых имени TWG-переменных. Значения
не помещаются в аргументы команды или JSON со спецификацией контейнера.
Общие `TWG_*` воркера не подхватываются без личного подключения задачи.
Файлы TWG в `/tmp/twg` живут в tmpfs конкретного контейнера; общего writable
профиля с токенами между пользователями нет. Секреты нельзя выводить в чат
или сохранять в артефактах и репозиториях.

Настройки считываются при подготовке воркера сессии для нового запуска задачи.
Восстановление соединения внутри уже работающего воркера использует прежний
снимок подключения. Для немедленного отзыва
действующего доступа отзовите токен в Atlassian и остановите соответствующие
задачи; удаление записи профиля не отзывает токен на стороне Atlassian.

## Развёртывание

1. Обычная сборка `docker build -t tracker-session:latest runners/tracker-session/`
   скачивает бинарник версии из lock-файла для Linux ARM64 или x64.
2. До выполнения бинарника проверяется SHA-256. Официальный `skills install`
   устанавливает базовые навыки без личных доступов. Состав и `contentRevision`
   каждого навыка сверяются с lock-файлом; несовпадение останавливает сборку.
3. `bash scripts/smoke_twg_image.sh` проверяет CLI, файлы плагина, лицензии,
   доступ непривилегированного пользователя и справку без сети и модели.
4. Штатный deploy уже собирает этот образ и применяет добавляющие миграции.
   Отдельной установки TWG или правки шаблонов на сервере не требуется.
5. После релиза каждый пользователь отдельно сохраняет подключение в профиле.

Сборке нужен доступ к официальному CDN Atlassian; при его недоступности или
несовпадении контрольных сумм новый образ не выпускается. Предыдущий работающий
релиз не обновляет свои файлы из CDN самостоятельно.

## Обновление и откат

Обновление TWG — отдельное изменение lock-файла через обычную ветку и ревью:

1. Изучить официальный changelog и стабильный manifest, выбрать конкретную версию.
2. Получить официальный `SHA256SUMS-v<версия>`, обновить обе Linux-суммы.
   Не использовать непроверенный бинарник или URL `latest`.
3. Во временной среде без токенов выполнить официальный `skills install`,
   проверить состав и изменения инструкций. Внести ожидаемые `contentRevision`
   из `.twg-install.json` в lock-файл. Не копировать навыки в репозиторий.
4. Собрать и проверить обе архитектуры, выполнить smoke и проверки проекта.
5. После ревью выпустить обычный релиз Tracker. Уже запущенный контейнер задачи
   остаётся на прежнем образе до следующего подключения процесса.

`twg upgrade`, `setup`, `login` и изменение пакета из сессии задачи не входят
в этот процесс. Навыки установлены root и доступны агенту для чтения. Проверку
версии/состава обеспечивает сборка; автоматическое обновление зависимостей TWG
во время задачи не требуется.

Откат выполняется штатным откатом релиза Tracker: deploy восстанавливает
предыдущий образ сессии. Личные настройки остаются в БД. Старый код не читает
добавленную таблицу; удалять её при откате кода не требуется.

Для оперативного отключения новых подключений задайте `TRACKER_TWG_ENABLED=false`
в `.env` и пересоздайте backend и воркеры через штатное развёртывание. Плагин и
личные доступы TWG не передаются новым процессам; сохранённые подключения не
стираются. Доступные MCP продолжают работать независимо.

Истёкший/отозванный API-токен заменяет сам пользователь в профиле. Постоянная
ошибка 401/403 требует проверки токена, прав и ограничений Atlassian, а не
переустановки образа или заимствования чужих доступов.
