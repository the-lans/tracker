# Ресурсы Tracker: локальные нагрузочные замеры, 2026-11-02

Результаты и рекомендация относятся к трём одновременно выполняющимся небольшим задачам разработки. Предыдущая рекомендация «минимум 16 ГБ» не подтверждается измерениями: она ошибочно опиралась на максимальные лимиты контейнеров.

## Что запускалось

Использованы существующие RR-QA-63, RR-QA-64 и RR-QA-65. Новые задачи не создавались. Перед каждым прогоном очищался рабочий каталог, ветки локального QA Git-сервера возвращались на `qa-base`, контекст агента сбрасывался. Старая история сохранена. Перед изменениями сделаны дамп PostgreSQL и Git bundle в `.qa/ram-benchmark/`.

Каждая задача выполняла штатный пайплайн: сбор контекста Bash → план → реализация `divide` в Python и unittest → отдельная тестовая script-нода → очистка контекста → итог. План принимался автоматически. Код коммитился и отправлялся в локальный QA Git-сервер. Модель — `gpt-6.1-sol` через существующую OAuth-подписку QA Codex, а не через платный API-ключ. Другой аккаунт был временно отключён, чтобы исключить переключение на Claude.

Во всех прогонах учитывались backend, frontend/nginx, Caddy, PostgreSQL, Redis, worker, session-worker, beat, SFTP, CLIProxyAPI, llm-gateway, backup и временные CLI/script-контейнеры. Фоновый worker работал с `--concurrency=1`, session-worker — с `--concurrency=3`. Исходный фоновый worker создавал 10 дочерних процессов по числу CPU Docker VM; это давало ненужный расход памяти.

Сторонние контейнеры, клиенты нагрузки, измеритель и QA-моки/Git-сервер в сумму не включались. В production Git/Jira находятся вне сервера Tracker. Системная память ОС и Docker daemon также не включалась.

## Условия и методика

- Локальная Docker Desktop Linux VM: arm64, 10 CPU, 7,75 ГиБ RAM, Docker Engine 29.5.2. Это не сервер AlmaLinux 10 и не x86-64: точный расход ОС и производительность целевого SSD здесь не проверены.
- Замеры cgroup v2 выполнялись раз в секунду. RAM без inactive_file = `memory.current - inactive_file`, аналогично подходу Docker CLI; отдельно сохранён полный `memory.current`. Показаны максимумы одновременно наблюдаемого расхода, а не сумма несовпадающих пиков сервисов.
- `baseline` и `baseline2`: сервисы без общего лимита RAM/CPU; контейнер CLI имеет штатный потолок 4 ГиБ, script-контейнер — 512 МиБ. Эти лимиты не являются расходом.
- `limited1` и `limited2`: единая родительская cgroup `/tracker-benchmark`, **1536 МиБ RAM + 4096 МиБ swap + квота 2 CPU на весь стек вместе**.
- `swap1`: та же cgroup, **1024 МиБ RAM + 4096 МиБ swap + квота 2 CPU на весь стек вместе**. Прогон прерван лимитом OAuth-подписки Codex: провайдер вернул HTTP 429 `usage_limit_reached`, все три задачи завершились `failed` в планировании. OOM отсутствовал, пик swap — 437 МиБ. Поэтому полный сценарий на 1 ГиБ НЕ подтверждён; второй прогон с этим бюджетом не запускался.
- Временным CLI и script-контейнерам явно передавались общий cgroup parent и `--memory-swap=-1`; ограничение общего swap задавалось родительской cgroup. Этим проверено, что динамические контейнеры не обходят общий бюджет.
- В VM добавлялся временный swap-файл 4 ГиБ на Docker volume; штатный swap VM 1 ГиБ оставался. Дополнительный swap после тестов отключается и удаляется.
- Проверялась раздача HTML/JS/CSS через Caddy → nginx и REST API списка задач, трёх карточек, их нод и логов с интервалом 5 с, без кеша клиента. HTTP-нагрузка добавлена во время первого baseline; второй baseline и последующие прогоны проходили с ней целиком.
- Три WebSocket-подключения к карточкам добавлены во время limited1; limited2 и swap1 проходили с ними целиком. Проверялись реальные `output_delta` и смены статусов. React исполняется на клиенте; браузерный рендер и память браузера в серверный RAM не входят.
- В каждом прогоне во время работы агентов запускался штатный `pg_dump | gzip`. Тестовая БД маленькая, дампы порядка 128–160 КиБ. Отправка в S3 не тестировалась.

## Измерения

Четыре успешных прогона — 12 выполненных задач, 36 успешных LLM-ходов и 12 отдельных успешных тестовых script-нод. `swap1` — неполный прогон, его время не сравнивать со временем полных прогонов.

| Прогон | Время, с | RAM без inactive_file, МиБ | RAM с кешем, МиБ | Swap, МиБ | Средние CPU | Успех | OOM |
|---|---:|---:|---:|---:|---:|---:|---:|
| baseline | 249.5 | 1619.6 | 1743.2 | 0.6 | 0.34 | 3/3 | 0 |
| baseline2 | 221.5 | 1687.4 | 1770.6 | 0.6 | 0.38 | 3/3 | 0 |
| limited1 | 261.4 | 1494.0 | 1514.7 | 0.0 | 0.39 | 3/3 | 0 |
| limited2 | 248.5 | 1517.3 | 1530.9 | 22.9 | 0.35 | 3/3 | 0 |
| swap1 | 100.7 | 1020.8 | 1022.2 | 437.1 | 0.29 | 0/3 | 0 |

Для ограниченных прогонов общий лимит проверен также непосредственно по родительской cgroup; её значения находятся в JSON и CSV. Разница с суммой контейнеров возможна из-за несинхронного чтения и остаточных страниц завершившихся контейнеров. CPU — измеренные средние ядра; квота ограниченных прогонов равна двум ядрам. Короткие секундные оценки могут чуть превышать 2 из-за границ периодов квоты.

Время завершения агентов зависит от удалённой модели и числа её действий, поэтому разницу времени между прогонами нельзя целиком приписывать swap. Эти прогоны подтверждают выполнение сценария и отзывчивость UI при конкретном бюджете; это не статистический SLA.

## Конфигурация сервера

По четырём полным успешным прогонам практичный экономный старт — **2 vCPU / 2 ГБ RAM / 4–8 ГБ swap / SSD 40–60 ГБ**, с возможностью увеличения RAM. Проверен бюджет приложения 1,5 ГиБ; оставшиеся около 0,5 ГиБ для AlmaLinux Minimal и Docker — оценка, требующая проверки на самом VPS.

| Вариант | CPU | RAM VPS | Swap | SSD | Статус |
|---|---:|---:|---:|---:|---|
| Экспериментальный минимум | 2 vCPU | 1,5 ГБ | 4–8 ГБ | 40 ГБ | Полный сценарий при бюджете приложения 1 ГиБ не проверен |
| Экономный старт | 2 vCPU | 2 ГБ | 4–8 ГБ | 40–60 ГБ | Два успешных прогона при 1,5 ГиБ RAM на приложение и трёх задачах |
| Больше запаса | 2–4 vCPU | 4 ГБ | 4–8 ГБ | 60–80 ГБ | Оценка для более тяжёлых задач и обслуживания; отдельный прогон VPS не выполнялся |

1 ГБ на весь VPS не рекомендую по этим данным: в таком бюджете нужно разместить ещё ОС и Docker, а не только приложение. Большой swap может помочь, но не доказывает приемлемую скорость любых сборок. 16 ГБ минимальным требованием не является. Целевой сервер: AlmaLinux 10 Minimal, SSD, Docker Engine + Compose, внешнее S3 для бэкапов. Для полного размера VPS к расходу приложения нужно добавить память ОС, Docker daemon и операций обслуживания. Даже если контейнеры успешно работают при лимите 1 ГиБ, это не означает, что весь сервер с AlmaLinux уместится в 1 ГиБ RAM.

Для малого сервера обязательна явная настройка числа процессов фонового воркера. Стандартная команда в `docker-compose.yml` не задаёт concurrency; на VPS с большим числом CPU он создаст лишние процессы. Для одной задачи можно дополнительно установить `SESSION_WORKER_CONCURRENCY=1`.

Сборка образов при установке/обновлении, компиляция больших Go/Java/JS-проектов, Playwright/Chromium и другие MCP-серверы в сценарий не входили. Результаты маленького qa-calc нельзя использовать как гарантию для трёх тяжёлых сборок. Сборку Docker-образов на минимальном VPS следует выполнять последовательно либо доставлять готовые образы.

## SSD и S3

Диск SSD 40–60 ГБ — стартовая оценка для небольшой установки: ОС, Docker-образы, рабочие каталоги, логи, временный бэкап и swap. Размер реальных репозиториев и артефактов нужно прибавить отдельно; тестовые рабочие данные имеют размер лишь десятки МиБ. S3 переносит хранение резервных копий за пределы VPS, но не заменяет локальный диск для Git и БД.

Встроенный backup сейчас пишет локальные дампы PostgreSQL. Для production нужен отдельный шаг отправки в S3, а также резервирование нужных volumes и защищённой копии `.env` с ключами шифрования. Эти работы здесь не выполнялись: задача была измерить ресурсы и предложить конфигурацию. Отправлять последовательно, с малой параллельностью; например, у rclone буферы multipart зависят от `transfers × s3-upload-concurrency × s3-chunk-size`. RAM реальной S3-загрузки ещё нужно измерить.

## Состояние после испытаний

Временные ограничения cgroup и изменения внутри session-worker сняты пересозданием контейнеров из исходных образов. Локально оставлены `worker --concurrency=1` и `session-worker --concurrency=3`, применённые через `.qa/ram-benchmark/compose.yml`; исходные Compose-файлы не изменены. Повторный запуск без этого override вернёт исходную параллельность. Аккаунт Claude снова включён; Codex исчерпал лимит подписки. Три переиспользованные задачи оставлены в `failed` после последнего прогона с HTTP 429; история четырёх успешных прогонов сохранена.

Временный swap-файл 4 ГиБ отключён, файл и его временный Docker volume удалены. Остановлены клиенты HTTP/WebSocket-нагрузки и измеритель. Удалены 16 неиспользуемых контейнеров, включая измеритель и контейнеры других неиспользуемых проектов; volumes и образы сохранены. Рабочий стек Tracker и необходимые QA Git/mocks оставлены запущенными.
