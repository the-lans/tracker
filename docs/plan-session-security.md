# План усиления входа и пользовательских сессий

Рабочая ветка: `fix/backend-without-docker-socket`.
Статус: реализация и проверки завершены. Production не обновлялся.
Отчёт: `docs/session-security-verification.md`.

## Цель и границы

Сразу закрывать доступ удалённым из допуска и заблокированным пользователям,
не позволять старым сессиям восстанавливаться после разблокировки, завершать
WebSocket по сроку токена и исключить хранение токена в JavaScript/localStorage.

Вход остаётся через Google OAuth. MFA не включаем и не требуем. Сохраняем
Fernet-токены и `users.session_version`; новую таблицу сессий, refresh-токены
и дополнительный сервис авторизации не вводим. Срок сессии остаётся 7 дней:
изменение срока не входит в согласованные четыре исправления.

Незакоммиченные изменения удаления Docker-сокета у backend сохраняются
в этой ветке и проверяются вместе с новым кодом. Развёртывание на production
выполняется отдельным шагом после проверок.

## 1. Немедленный отзыв доступа

Участки: `backend/api/users.py`, `backend/services/users.py`,
`backend/services/auth.py`, `backend/db/queries/users.py`.

- В одной транзакции удаления email из допуска деактивировать связанного
  пользователя и атомарно увеличить `session_version`.
- Сохранить существующий запрет удаления последнего доступного администратора.
- При ручной деактивации увеличивать версию только при переходе
  `is_active=true → false`; повторный одинаковый запрос не должен менять её.
- Использовать ту же операцию блокировки в периодической деактивации.
  Фоновая задача остаётся страховкой для изменений БД вне API.
- При входе проверять наличие email в допуске также для существующего
  пользователя. Не выдавать сессию уже исключённому из допуска пользователю.
- Не разрешать активацию пользователя, email которого отсутствует в допуске.
- Разблокировка не уменьшает и не сбрасывает версию: прежние токены остаются
  недействительными, требуется новый вход.
- Существующие проверки `is_active`, версии и роли сохраняются на каждом
  HTTP-запросе и при повторной проверке доступа WebSocket.

## 2. Защищённая cookie вместо Bearer/localStorage

Участки: `backend/api/auth.py`, `backend/api/dependencies.py`,
`backend/services/auth_tokens.py`; небольшой общий модуль cookie/Origin.

- `POST /auth/google` проверяет Google-токен и допуск как раньше, устанавливает
  cookie с токеном и возвращает только данные пользователя.
- Production-cookie: `__Host-tracker_session`, `HttpOnly`, `Secure`,
  `SameSite=Lax`, `Path=/`, без `Domain`; срок cookie совпадает со сроком токена.
- Для локального HTTP-стенда предусмотреть явно включаемый dev-режим:
  другое имя cookie без `__Host-` и без `Secure`. Production по умолчанию
  использует только защищённый режим.
- HTTP API получает сессию только из cookie. Удалить прежнюю авторизацию
  Bearer для пользовательского API, не оставлять скрытый запасной способ входа.
  Токены LLM-шлюза и сторонних интеграций этим изменением не затрагиваются.
- Добавить `GET /auth/me` для восстановления текущего пользователя после
  загрузки страницы; endpoint использует общую проверку сессии.
- Добавить `POST /auth/logout`, удаляющий cookie текущего браузера.
- `POST /auth/logout-all` увеличивает версию сессий и удаляет cookie.
- У ответов входа и чтения текущей сессии выставлять `Cache-Control: no-store`.
- При удалении cookie использовать то же имя, Path и режим, что при выдаче.

Семантика обычного выхода сохраняется: он завершает вход в текущем браузере.
Скопированный токен отзывается через «Выйти на всех устройствах» или блокировку
пользователя. Индивидуальный серверный отзыв устройств потребовал бы реестра
сессий и не входит в этот план.

## 3. Защита cookie-запросов от CSRF

Участки: общий HTTP middleware/dependency, `backend/main.py`, конфигурация
окружения, `frontend/src/lib/apiClient.ts`.

- Задать ожидаемый публичный Origin настройкой окружения; на production это
  `https://tracker.botelo.ru`. Не определять разрешённый Origin из произвольных
  `Host` или `X-Forwarded-Host` входящего запроса.
- Для всех изменяющих пользовательских API-запросов (`POST`, `PUT`, `PATCH`,
  `DELETE`), включая вход и выход, требовать точное совпадение Origin
  и собственный заголовок клиента `X-Tracker-Request: 1`.
- Пустой, чужой или `null` Origin и отсутствие заголовка приводят к 403
  до выполнения операции. Значение заголовка не является секретом:
  защиту обеспечивает совместная проверка Origin и политика браузера.
- Не включать разрешающий CORS для сторонних сайтов; OPTIONS не меняет данные.
- Проверить загрузку файлов и другие запросы не в JSON: они тоже передают
  защитный заголовок. GET/HEAD не должны выполнять изменяющие действия.
- Вебхуки и отдельные интеграционные API, если они присутствуют, инвентаризировать
  отдельно: не требовать браузерную cookie там, где используется собственная
  аутентификация; исключения не должны распространяться на пользовательский API.

## 4. Браузерный клиент и переход существующих пользователей

Участки: `frontend/src/stores/authContext.ts`, `authStore.tsx`, `LoginPage.tsx`,
`apiClient.ts`, `useTaskStatusSocket.ts`, компоненты выхода, API-типы и тестовые
фабрики/фикстуры.

- Удалить `session_token` из ответа входа и типов, поле `token` из AuthContext,
  чтение/запись токена в localStorage и формирование Bearer-заголовков.
- Явно использовать `credentials: same-origin` в обычных запросах и скачивании
  файлов. В изменяющих запросах добавлять заголовок защиты от CSRF.
- При запуске приложения получать пользователя через `/auth/me`; до результата
  показывать состояние загрузки, а не кратковременно открывать защищённый экран
  или перенаправлять на страницу входа.
- Удалять старый ключ `tracker.session` при старте клиента; не переносить
  старый токен из localStorage в cookie через дополнительный endpoint.
- Сохранять синхронизацию входа/выхода между вкладками через событие без
  секретных данных; при смене состояния перечитывать `/auth/me`.
- Защититься от запоздалого 401 старого запроса после нового входа:
  отслеживать локальное поколение сессии, не сравнивать секретные токены.
- При смене пользователя/выходе очищать приватный кэш запросов и закрывать
  WebSocket. Обычная кнопка выхода сначала вызывает серверный logout;
  не показывать успешный выход при сетевой ошибке удаления cookie.
- Сохранить отдельные кнопки «Выйти» и «Выйти на всех устройствах».

## 5. WebSocket: Origin, cookie, срок действия и отзыв

Участки: `backend/ws/tasks.py`, `backend/services/auth_tokens.py`,
`backend/services/access.py`, frontend WebSocket hook.

- Аутентифицировать соединение cookie из HTTP-handshake; перестать отправлять
  пользовательский токен первым WebSocket-сообщением и не принимать его из URL.
- До выдачи данных проверить точный Origin, срок токена, активность пользователя,
  версию сессий и право на задачу. Чужой или отсутствующий Origin отвергать.
- Сохранить время окончания токена в проверенных claims.
- Ограничить срок жизни потока оставшимся временем сессии: соединение закрывается
  по истечении токена независимо от частоты сообщений или опросов статуса.
- Проверять отзыв/блокировку с существующей периодичностью (около 10 секунд).
  Проверку выполнять до отправки очередных данных в соответствующем цикле.
- При закрытии отменять фоновые задачи и освобождать подписку Redis.
- На клиенте код потери авторизации должен прекращать переподключения,
  перечитывать состояние сессии и переводить на вход при 401.

## 6. Миграция и порядок выкладки

- Добавить одноразовую Alembic data migration, атомарно увеличивающую
  `session_version` всех существующих пользователей. Это отзовёт токены,
  ранее хранившиеся в localStorage; схема таблиц не меняется.
- Не уменьшать версии при downgrade: ранее отозванные токены не должны оживать.
- Обновить backend и frontend согласованно. Обновление браузера завершает
  переход; старый клиент получает отказ вместо поддержки прежнего Bearer-входа.
- Предупредить о повторном входе после выкладки. Пользовательские HTTP-сессии
  и задачи LLM — разные сущности: миграция не меняет задачи и не останавливает
  фоновые пайплайны.
- Прописать публичный Origin и production-cookie режим в Compose, `.env.example`
  и документации; проверить HTTPS и проксирование на production/локальном стенде.
- Откат оставляет повышенные версии сессий и требует нового входа; не возвращать
  старые версии и не восстанавливать прежние браузерные токены.

## 7. Проверки и критерии приёмки

Backend unit/integration:

- Вход разрешённому пользователю и отказ чужому, неподтверждённому или
  заблокированному аккаунту. Ответ входа не содержит токен.
- Все атрибуты cookie, её срок и корректное удаление; отсутствующая,
  подделанная, просроченная и отозванная cookie дают 401.
- Авторизация только старым Bearer-токеном не работает.
- Удаление допуска немедленно закрывает HTTP-доступ и отзыв действует на WS;
  повторная активация не возвращает действительность старых токенов.
- Защита последнего администратора и одновременные увеличения версии сессий.
- Нормальный Origin/заголовок допускают операцию; чужой/пустой/`null` Origin,
  отсутствующий заголовок и попытки подмены Host отклоняются без изменений БД.
- Открытый WebSocket закрывается по сроку и при отзыве, даже при непрерывном
  потоке событий; не оставляет Redis-подписок и фоновых asyncio-задач.
- Миграция отзывает старые токены; downgrade не отменяет отзыв.

Frontend unit/integration и браузер:

- Вход, перезагрузка страницы, несколько вкладок, обычный выход и выход везде.
- Нет токенов в localStorage, JSON ответов, WebSocket-сообщениях и URL;
  production-cookie не доступна через `document.cookie`.
- Загрузки/скачивания файлов и защищённые страницы работают с cookie.
- Поздний 401 не завершает новую сессию; после выхода приватный кэш очищен.
- WS переподключается после временного сетевого сбоя и прекращает попытки
  после потери авторизации.
- Позитивные и негативные сценарии CSRF в реальном браузере на HTTPS-стенде;
  отдельная проверка локального HTTP dev-режима.
- Полные backend unit/integration, frontend test/build, Ruff, mypy, TypeScript
  и проверки Compose/установщика на конечном состоянии ветки.
