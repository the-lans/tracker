# План реализации AI-трекера задач (по `docs/technical_specification.md`)

## Контекст

ТЗ (989 строк, 22 раздела) описывает полноценную систему управления задачами
для Claude Code: модель данных, оркестрацию сессий SDK, 5 типов нод пайплайна,
режим планирования, изоляцию MCP-инструментов, REST/WS API, фронтенд,
уведомления, админ-часть, деплой и тестирование. Пользователь явно запросил
**полный сквозной план на весь ТЗ**, а не MVP-срез, в порядке зависимостей
между разделами (модель данных → оркестрация сессий → типы нод → API →
фронтенд → уведомления → административная часть).

Перед этим планом в отдельных обсуждениях зафиксированы 5 архитектурных
решений, которые план ниже использует как данность (не переоткрывает):

1. **Remote control (раздел 6.3/6.5/6.6)** — по факту `docs/remote_control_findings.md`
   у `ClaudeSDKClient` нет способа узнать статус моста или переподключить его
   посреди сессии. Решение: `--remote-control` включается один раз при первом
   `connect()` задачи (через `ClaudeAgentOptions.extra_args`); кнопка
   «Переподключить» не вызывает reconnect в SDK (такого API нет) — воркер
   между ходами перезапускает процесс CLI с `resume=session_id` и тем же
   флагом (решение №8); `tasks.remote_control_status`
   — best-effort индикатор (жив ли процесс SDK), не гарантированно точный
   статус самого моста; `check_remote_control_bridges` соответственно проверяет
   живость процесса/сессии, а не сам мост.
2. Полный сквозной план (это его и покрывает).
3. **Git-хостинг — только GitLab**, буквально по ТЗ.
4. **Провижининг ОС-пользователей и Claude-аккаунтов — вне периметра.**
   `User-Provisioner` не реализуется; `os_username`/`llm_accounts.claude_config_dir`
   — поля, ссылающиеся на уже существующие вручную настроенные Linux-логины и
   `claude auth login`-сессии. Периодические задачи `deprovision_inactive_users`
   и `revoke_stale_sshfs_keys` реализуются как заглушки/no-op с логированием
   (провижининга, который они должны обслуживать, нет). SSH-ключ профиля и
   `deprovision_inactive_users` пересмотрены решением №16.
5. **Токен GitLab API — один общий на систему**, через `env_variables`
   (`scope = global`), не отдельное поле в `repositories`.
6. **«Приостановить» — отдельный статус `paused`** (решение 2026-10-19,
   внесено в ТЗ версии 4.2: разделы 3.1, 6.6, 14.1, 14.2). Пауза наступает после
   текущей ноды; сессия удерживается, ручные промты на паузе выполняются;
   переходы `in_progress ↔ paused`, `paused → failed | rebase_conflict`.
   «Остановить» прерывает текущее обращение и переводит задачу в `failed`
   (с `last_failed_order_index` прерванной или следующей ноды) — штатный
   перезапуск продолжает с неё. Команды pause/resume/stop API пишет в Redis
   (`services/task_control.py`), исполняет только воркер сессии (п. A/B ниже).
7. **`rebase_conflict` разрешает агент** в сессии задачи (решение
   2026-10-19, внесено в ТЗ версии 4.2: разделы 3.1, 14.2, 16.2): воркер в точке между нодами отправляет промт на ребейз и
   проверяет результат — успех возвращает в `in_progress` (или `paused`),
   неудача — `failed`. Дочерние задачи в `new`/`queued`/`done`/`failed` не
   ребейзятся: им только переключается `base_branch`. Признак конфликта —
   `task_repositories.merge_status = conflict`: он переживает уход в
   `failed`, и перезапуск сначала снова разрешает конфликт, а не пушит
   неперебазированную ветку.
8. **Мост `claude.ai/code` — только для просмотра** (решение 2026-10-20,
   внесено в ТЗ версии 4.3: разделы 1.2, 1.3, 6.3, 6.5, 9.6, 15.2, 22).
   Вмешиваться в работу агента можно только через поля трекера; реплики из
   `claude.ai/code` не импортируются в ленту и `node_logs`. Кнопка
   «Переподключить» пишет запрос в Redis (`services/task_control.py`),
   воркер в точке между ходами пересоздаёт процесс CLI
   (`ClaudeCodeSession.replace_client`) и ставит best-effort статус.
9. **Саммари родительской задачи** (решение 2026-10-20, ТЗ 4.3: разделы
   3.1, 6.7). Пересказ составляет сессия родителя по запросу при старте
   дочерней: через очередь ручных запросов родителя, пока его сессией
   владеет воркер (дочерняя ждёт), иначе — в ответвлении его сессии
   (`fork_session`), без сессии — дочерняя стартует с пометкой в ленте.
   Артефакт — `task_parent_summaries`, первое сообщение новой сессии
   дочерней задачи (`services/parent_summary.py`).
10. **E2E полного цикла — на уровне backend** (решение 2026-10-20, ТЗ 4.3:
    раздел 21.1): HTTP API и настоящий воркер сессии, Claude Agent SDK
    имитируется (`backend/tests/test_e2e_full_cycle.py`). Браузерного E2E
    нет — во фронтенде пока нет тестовой инфраструктуры.
11. **Обязательные сценарии 21.2 №12–13** (решение 2026-10-20, ТЗ 4.3).
    №12 проверяется на уровне backend: каждая задача передаёт MCP-серверу
    свою изоляцию в `X-Tracker-Isolation-Path`; соблюдать её — дело
    администратора сервера. №13 из обязательных убран: MCP-серверы
    подключаются по сети, процессами браузера backend не управляет, и
    `purge_orphaned_playwright_processes` остаётся точкой расширения.
12. **Переменные окружения: задача > репозиторий > глобальные** (решение
    2026-10-20, ТЗ 4.4: разделы 3.1, 5). Переменные `scope = repository`
    берутся из репозиториев задачи; один ключ в двух репозиториях задачи —
    ошибка до запуска (`start`, `restart`, автозапуск) и при подстановке.
    Переменные уровня задачи редактируются через `/tasks/{id}/env-variables`,
    значения скрыты (правило 8).
13. **«Активные сессии» профиля — сессии Claude Code задач пользователя**
    (решение 2026-10-20, ТЗ 4.4: раздел 15.1), не сессии входа: токены входа
    stateless и не перечисляются.
14. **`rotate_task_logs` — файлы и удаление** (решение 2026-10-20, ТЗ 4.4:
    разделы 16.2, 20.4): записи `node_logs` задач в `done` старше порога
    выгружаются в сжатые JSONL в volume `log_archive` и удаляются из БД
    только после записи файла (`services/log_rotation.py`). Задачи в
    `failed` не ротируются: перезапуск опирается на их историю.
15. **Механизмы, выбранные по ТЗ и коду** (ТЗ 4.4: разделы 6.4, 6.6, 16.2):
    срок хранения истории сессий — `cleanupPeriodDays` в `settings.json`
    аккаунта перед каждым подключением (`services/claude_config.py`); живость
    сессии для `check_remote_control_bridges` — пульс воркера в Redis
    (`services/session_heartbeat.py`); лимиты LLM-аккаунта — по
    `RateLimitEvent` из потока сессии, восстановление по времени сброса
    (`services/llm_accounts.py`).
16. **Итерация по остаткам сверки с ТЗ 4.4** (решение 2026-10-21):
    - по ТЗ реализуются: архивация промтов библиотеки в интерфейсе (7.2,
      3.2); доступ роли `user` только к собственным задачам (19.2);
      различение временных и постоянных сбоев внешних систем (17.3); выбор
      MCP-серверов шаблона для роли `user` (10.5, 19.2);
    - раскладка 768–1279px остаётся на вкладках «Обзор / Диалог / Логи» —
      интерфейс уже проверен, ТЗ 15.3 правится под реализацию;
    - SSH-ключ sshfs в профиле (15.1) и `deprovision_inactive_users` (16.2)
      реализуются в этой итерации — решение №4 для них пересмотрено;
    - `User-Provisioner` (2.1, 20.5) — позже, отдельной задачей; до неё по
      решению №4 пользователей Linux заводит администратор;
    - владение (19.2): задачи, пайплайны, промты библиотеки и шаблоны —
      личные, у каждой записи есть автор; `user` видит и меняет только своё,
      `admin` — всё. Записям без автора при миграции назначается первый
      администратор. Репозитории остаются общими; шаблон репозитория по
      умолчанию применяется к задачам любого пользователя, `user` выбирает
      его только среди своих шаблонов. Счётчик «ждут решения» и
      push-уведомления — по собственным задачам, в том числе у `admin`;
    - SSH-ключ: один публичный ключ на пользователя, формат проверяется,
      показывается отпечаток; `admin` видит ключ и `os_username` в разделе
      «Пользователи» и ставит ключ на сервер вручную до появления
      `User-Provisioner`;
    - `deprovision_inactive_users`: пользователю, чей email удалён из
      `allowed_emails`, ставится `is_active = false` (вход и API закрыты), в
      `app_logs` пишется `os_username` для ручной блокировки на сервере;
      удалить из `allowed_emails` email последнего активного администратора
      нельзя (409), чтобы система не осталась без администратора.
    - механика (выбор по ТЗ и коду): владение проверяет `services/access.py`
      (чужая запись — 404, у ноды пайплайна автор — автор пайплайна,
      существующим записям миграция назначила самого раннего администратора);
      `deprovision_inactive_users` не блокирует администраторов, если иначе
      не осталось бы ни одного активного, — страховка для email, удалённых
      до появления запрета (`services/users.py`); 17.3 — постоянные сбои SDK
      (`authentication_failed`, `billing_error`, `invalid_request`, нет CLI)
      не повторяются, после падения процесса CLI воркер поднимает новый
      процесс той же сессии и повторяет ноду
      (`services/failure_classification.py`, `pipeline_orchestrator.py`);
      постоянный сбой GitLab API по репозиторию — `app_logs`, push автору и
      сутки без опроса репозитория (ключ Redis, `services/gitlab_sync.py`);
      отклонённый токен (401/403) — одна запись `app_logs` для администратора
      и сутки паузы всей синхронизации без push авторам; 408 и 429 — временные;
      `revoke_stale_sshfs_keys` остаётся точкой расширения: данных об
      использовании ключей у трекера нет.

Дополнительно (моя собственная, не переспрошенная деталь, вытекающая из

## Архитектурные решения, зафиксированные заранее

Это самые рискованные с точки зрения «потом переписывать» места системы —
продуманы сейчас, до кода, чтобы Этапы 5/8/9/12 не пришлось переделывать
после того, как выяснится нестыковка на практике.

### A. Модель владения сессией: один долгоживущий Celery-таск, не цепочка

`ClaudeSDKClient` держит хэндл ОС-подпроцесса — он обязан жить в памяти
**одного** процесса всё время, пока задача `in_progress` (часы/дни, много
нод). Наивный вариант «одна Celery-задача на одну ноду пайплайна» не
работает: между вызовами `.delay()` Python-объект клиента не переживает —
пришлось бы каждый раз создавать новый процесс `claude`. Даже если
передавать `ClaudeAgentOptions.resume=session_id` (SDK это поддерживает —
переживает историю на диске, раздел 6.4), это прямо противоречит букве
раздела 6.1: «Объект клиента сессии... хранится как персистентная сущность...
и переиспользуется всеми последующими нодами».

**Решение:** оркестратор запускается как **одна Celery-задача на весь
активный жизненный цикл сессии** (`services/pipeline_orchestrator.run(task_id)`),
которая сама содержит `async with ClaudeSDKClient(...)` и цикл по нодам —
не возвращает управление Celery между нодами. Это буквально реализует
«мьютекс на уровне Celery-задачи, обслуживающей сессию» из раздела 6.2: пока
жива эта одна задача, никакой другой код процесса-воркера не может
одновременно трогать тот же объект `ClaudeSDKClient` — блокировка становится
структурной, а не через отдельный лок поверх нескольких независимых тасков.

### B. Как «ручные» действия попадают в уже бегущую сессию

Библиотечный промт/свободный промт/решение `awaiting_input`/`plan_review`
приходят через API (другой процесс/контейнер — `backend`, не `worker`).
Они не могут напрямую вызвать метод на объекте `ClaudeSDKClient`, который
живёт в памяти `worker`-процесса. Решение — то, что уже заложено в схеме
данных ТЗ, использовать буквально:

- API-эндпоинт только **пишет** в `task_manual_request_queue` /
  обновляет `node_logs.pending_options`/`user_input_text` и публикует
  событие в Redis pub/sub-канал `task:{task_id}:signal`.
- Долгоживущий Celery-таск (п. A) между шагами (и во время ожидания решения)
  подписан на этот канал через `redis.asyncio` — просыпается по событию, а
  не поллингом с фиксированным интервалом. Это и есть «эквивалент»
  `asyncio.Event`, о котором прямо говорит раздел 9.6 (`asyncio.Event` в
  чистом виде между процессами не работает — Redis pub/sub здесь именно
  тот эквивалент, который ТЗ явно допускает формулировкой).
- Один и тот же путь обрабатывает решение независимо от источника (кнопка
  в трекере, текст в трекере, действие через `claude.ai/code` — раздел 9.6,
  последний пункт): все три в итоге дописывают ту же запись и публикуют то
  же событие.

### C. Транзакции и сессии БД

Одна `AsyncSession` на unit of work: один HTTP-запрос в `api/` — одна
сессия с явным `commit()` в конце обработчика; один шаг оркестратора
(выполнение ноды, обработка одного элемента очереди) — тоже одна сессия.
Никаких implicit autocommit и никаких ORM-объектов, живущих дольше своей
сессии. `services/` не открывают сессию сами — получают её через DI
(FastAPI `Depends`) или явно передаются оркестратором.

### D. Иерархия исключений

`backend/services/errors.py`: `AppError` (база) → `ValidationError`,
`NotFoundError`, `ConflictError`, `ExternalServiceError` (с флагом
`is_transient: bool` — разделяет «подлежит retry» и «требует немедленного
уведомления», раздел 17.3). Middleware Этапа 1 маппит эту иерархию в
HTTP-коды один раз, а не в каждом роутере отдельно.

### E. Соглашения по коду — уже зафиксированы в репозитории

`.claude/commands/promt-format.md` уже содержит согласованный чеклист (типизация
везде, keyword-only аргументы после 5 позиционных, без алиасов таблиц в SQL,
`models/` только модели / логика работы с БД в `db`, IF NOT EXISTS в сырых
миграциях, параметризованные тесты для однотипных сценариев и т.д.) — каждый
этап обязан ему соответствовать; чеклист не переизобретается по новой на
каждом этапе, а просто применяется.

## Наблюдаемость и самопроверка в разработке

Цель — увидеть ошибку реализации сразу после запуска стека, а не через
отложенный баг-репорт. Два механизма, оба добавляются в Этапе 1 и растут
вместе с остальными этапами.

### Логирование неочевидных мест

Помимо стандартного per-request/per-task логирования, отдельные `structlog`
события (с полными параметрами, не просто "started"/"done") обязательны в
точках, где баг иначе будет молчаливым:

- захват/освобождение мьютекса сессии (п. A) — сколько ждали, кто держал;
- каждая попытка retry — номер попытки, вычисленная задержка, причина;
- рендеринг `isolation_path_template` — итоговый путь ДО передачи в SDK
  (раздел 10.5 прямо требует ловить общесистемный путь без подстановки —
  это невозможно поймать постфактум, если не залогировать сам момент рендера);
- каждый вызов `connect()` — какие `extra_args` фактически переданы (важно
  из-за remote-control, решение №1 — если поведение SDK изменится, это
  будет видно в логе, а не только по факту "мост не работает");
- каждый вызов `canUseTool`-callback — имя инструмента, решение, сколько
  ждали пользователя;
- публикация/получение событий Redis pub/sub из п. B — иначе гонки между
  API и воркером не отладить;
- git push/rebase — результат, конфликтующие файлы при `rebase_conflict`.

### Лёгкие метрики (дополнение к ТЗ, не входит в раздел 2.2 — явно вне ТЗ)

`prometheus-client` в backend + `/metrics`-эндпоинт (не требует изменений в
docker-compose для прод-режима, это отдельный локальный/staging-инструмент
разработчика): счётчики `nodes_executed_total{node_type,status}`,
`pipeline_duration_seconds`, `session_mutex_wait_seconds`,
`manual_queue_depth`, `retry_total{node_type}`. Не подключается к Grafana
как часть продукта — если понадобится, это отдельное решение вне этого
плана.

### Быстрый цикл проверки «поднял стек — сразу видно, что сломано»

- `scripts/seed_dev_data.py` — создаёт демо-пайплайн (по одной ноде каждого
  типа) и демо-задачу через реальные сервисы (не INSERT напрямую) сразу
  после того, как соответствующий этап реализован; растёт вместе с этапами
  2–10.
- `make smoke`: поднимает `docker compose up -d` весь стек, ждёт healthcheck,
  прогоняет `seed_dev_data.py`, запускает демо-пайплайн через API и
  проверяет, что задача доходит до `done` (или до ожидаемого не-done статуса
  для нод, требующих решения) за разумный таймаут — печатает точную ноду и
  ошибку, если что-то не прошло. Это то самое «запустить фронт и бек и сразу
  увидеть, что сломано», о котором просил пользователь.
- Начиная с Этапа 6 (когда появляется первый работающий пайплайн), `make
  smoke` — обязательный последний шаг проверки каждого этапа, дополнительно
  к unit/integration-тестам, перечисленным в самом этапе.

## Порядок этапов и обоснование

16 этапов, сгруппированных вокруг 7 блоков, которые назвал пользователь;
«соединительная ткань» (шаблонизатор, git-провижининг, аутентификация,
периодические задачи, деплой/тестирование) вставлена в точку, где она
структурно необходима как зависимость для следующего блока — иначе часть
этапов была бы непроверяемой в изоляции.
